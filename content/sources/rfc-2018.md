## Summary

The Standards Track spec (October 1996) for SACK. A cumulative ACK can
only say "I have everything up to here", so a sender learns about one
lost segment per round trip. SACK adds a TCP option where the receiver
lists the blocks of data it holds beyond the gap, so the sender resends
only what's missing.

## Key claims

- Cumulative ACKs force the sender to wait a round trip per loss or resend data that arrived. "This forces the sender to either wait a roundtrip time to find out about each lost packet, or to unnecessarily retransmit segments which have been correctly received" (1)
- SACK lets the receiver report everything that arrived. "the data receiver can inform the sender about all segments that have arrived successfully, so the sender need retransmit only the segments that have actually been lost." (1)
- Two options: SACK-permitted, sent on the SYN, and the SACK option itself. "The first is an enabling option, "SACK-permitted", which may be sent in a SYN segment" (1); "It MUST NOT be sent on non-SYN segments." (2)
- Each block is a left edge (first sequence number) and a right edge (the number just after the last byte). "Right Edge of Block ... This is the sequence number immediately following the last sequence number of this block." (3)
- SACK doesn't change the cumulative ACK. "The SACK option does not change the meaning of the Acknowledgement Number field." (3)
- Option space limits it to 4 blocks, 3 when timestamps are also used. "the 40 bytes available for TCP options can specify a maximum of 4 blocks" and "a maximum of 3 SACK blocks will be allowed in this case." (3)
- While it holds out-of-order data, the receiver ACKs every new segment, and each of these duplicate ACKs carries SACK. "The receiver SHOULD send an ACK for every valid segment that arrives containing new data, and each of these "duplicate" ACKs SHOULD bear a SACK option." (4)
- The first block must be the one holding the segment that triggered this ACK. "The first SACK block ... MUST specify the contiguous block of data containing the segment which triggered this ACK" (4)
- Blocks are repeated across ACKs so a lost ACK doesn't lose the information. "any segment remaining part of a non-contiguous block of data held by the data receiver is reported in at least three successive SACK options" (4)
- The sender marks SACKed segments and skips them when retransmitting. "the data sender will skip that segment during any later retransmission." (5)
- SACK is advisory: the receiver may throw SACKed data away (renege). "the data receiver is permitted to later discard data which have been reported in a SACK option." (3)
- So after a timeout the sender forgets SACK information, and it frees data only when the cumulative ACK passes it. "After a retransmit timeout the data sender SHOULD turn off all of the SACKed bits, since the timeout might indicate that the data receiver has reneged." (5); "the sender MUST NOT discard data before it is acknowledged by the Acknowledgment Number field in the TCP header." (8)
- Recovery shouldn't start on a single out-of-order report, to cope with reordering. "recovery is not triggered by a single ACK reporting out-of-order packets at the receiver." (5.1)
- Timeouts remain the fallback. "The use of time-outs as a fall-back mechanism for detecting dropped packets is unchanged by the SACK option." (5.1)
- Worked example, case 1: 8 segments of 500 bytes from 5000, last 4 dropped: the receiver just ACKs 7000 with no SACK option. (7, Case 1)
- Worked example, case 3: segments 2, 4, 6 and 8 dropped. After segment 8000 arrives the ACK is 5500 with blocks 8000-8500, 7000-7500, 6000-6500, newest first. (7, Case 3)

## My notes

- Case 1 is a tail loss: nothing after the hole, so SACK can't help.
  That's the gap TLP (RFC 8985) fills.
- D-SACK (RFC 2883, 2000) extends this to report duplicates; opened
  2026-09-29, abstract only, no note.
