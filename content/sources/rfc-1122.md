## Summary

The IETF's rules for what an Internet host must do at the link, IP and
transport layers. Section 1.1 is the clearest official statement of the
four-layer Internet model and the design assumptions behind it. Still in
force; the rfc-editor.org info page lists 9 RFCs that update it (RFC 9293
for TCP among them).

## Key claims

- The Internet protocol suite has four layers: application, transport, internet and link. "A host typically must implement at least one protocol from each layer." (1.1.3)
- The Internet's application layer covers what OSI splits into presentation and application. "The application layer of the Internet suite essentially combines the functions of the top two layers -- Presentation and Application -- of the OSI reference model." (1.1.3, Application Layer)
- DNS is an application-layer "support protocol". "Support protocols, used for host name mapping, booting, and management, include SNMP, BOOTP, RARP, and the Domain Name System (DNS) protocols." (1.1.3)
- The transport layer gives end-to-end service; TCP and UDP are the two main ones. "The transport layer provides end-to-end communication services for applications." (1.1.3, Transport Layer)
- IP makes no delivery promises. "IP datagrams may arrive at the destination host damaged, duplicated, out of order, or not at all." (1.1.3, Internet Layer)
- ICMP sits oddly: part of IP, but carried inside IP. "ICMP is a control protocol that is considered to be an integral part of IP, although it is architecturally layered upon IP" (1.1.3, Internet Layer)
- The link layer is whatever talks to the directly connected network. "We call this a link layer or media-access layer protocol." (1.1.3, Link Layer)
- Gateways (routers) keep no connection state; hosts do. "gateways are designed to be stateless, forwarding each IP datagram independently of other datagrams." (1.1.2 b)
- Reliability state lives in the hosts. "All state information required for end-to-end flow control and reliability is implemented in the hosts, in the transport layer or in application programs." (1.1.2 b)
- Routing is the routers' job, not the hosts'. "Routing complexity should be in the gateways." (1.1.2 c)
- Two hosts on the same network use the same protocols as two far apart. "Two hosts on the same network communicate with each other using the same set of protocols that they would use to communicate with hosts on distant networks." (1.1.2 a)
- A host decides "local or remote" by masking: if the destination's network bits match its own, send directly, otherwise to a gateway. "If the IP destination address bits extracted by the address mask match the IP source address bits extracted by the same mask, then the destination is on the corresponding connected network" (3.3.1.1)
- "The IP layer chooses the correct next hop for each datagram it sends." (3.3.1)
- A host must work with no gateways at all. "The host IP layer MUST operate correctly in a minimal network environment, and in particular, when there are no gateways." (3.3.1.1)

Added 2026-09-28 (audit) for `network-layers`:

- The application layer isn't split further, though some protocols layer inside themselves. "The Internet suite does not further subdivide the application layer, although some of the Internet application layer protocols do contain some internal sub-layering." (1.1.3, Application Layer)
- The common user protocols in 1989 were Telnet, FTP and SMTP. "SMTP   (electronic mail delivery)" (1.1.3, Application Layer)
- TCP is reliable and ordered with flow control; UDP is a datagram service. "UDP is a connectionless (\"datagram\") transport service." (1.1.3, Transport Layer)

Added 2026-09-29 for `tcp-keepalive` and `tcp-retransmission`:

- Keep-alives are optional, per connection, and off by default. "If keep-alives are included, the application MUST be able to turn them on or off for each TCP connection, and they MUST default to off." (4.2.3.6)
- They are only sent after an idle interval that defaults to at least two hours. "This interval MUST be configurable and MUST default to no less than two hours." (4.2.3.6)
- One unanswered probe isn't proof of death, because empty ACKs aren't retransmitted. "it MUST NOT interpret failure to respond to any specific probe as a dead connection." (4.2.3.6)
- Why TCP itself left them out: they can kill good connections during brief outages, waste bandwidth, and cost money. "it could: (1) cause perfectly good connections to break during transient Internet failures; (2) consume unnecessary bandwidth" (4.2.3.6, DISCUSSION)
- The probe carries SEG.SEQ = SND.NXT-1, outside the window, so the peer must answer with an ACK; a peer that lost the connection answers with RST. "If the peer has dropped the connection due to a network partition or a crash, it will respond with a RST instead of an acknowledgment segment." (4.2.3.6, DISCUSSION)
- Meant for servers that would otherwise hold resources for a crashed client. "A TCP keep-alive mechanism should only be invoked in server applications that might otherwise hang indefinitely and consume resources unnecessarily if a client crashes" (4.2.3.6, DISCUSSION)
- Giving up on retransmissions: R1 (tell IP, at least 3 retransmissions) and R2 (close, at least 100 seconds). "The value of R1 SHOULD correspond to at least 3 retransmissions, at the current RTO. The value of R2 SHOULD correspond to at least 100 seconds." (4.2.3.5)
