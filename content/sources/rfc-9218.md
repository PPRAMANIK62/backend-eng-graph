## Summary

The priority scheme that replaced HTTP/2's priority tree (2022). A
client sends a `Priority` header with an urgency from 0 to 7 and an
"incremental" flag, and can update it later with a frame. It works the
same on HTTP/2 and HTTP/3. Servers treat it as a hint.

## Key claims

- The RFC 7540 tree was dropped. "The design and implementation of RFC 7540 stream priority were observed to have shortcomings, as explained in Section 2." (1)
- Servers can ignore priority signals. "Servers can ignore client priority signals and still successfully serve HTTP responses." (1)
- The signals are suggestions only. "They are only a suggestion and do not guarantee any particular processing or transmission order for one response relative to any other response." (1)
- Urgency runs 0 to 7, lower is more urgent, default 3. "between 0 and 7 inclusive, in descending order of priority. The default is 3." (4.1)
- The incremental flag says a response is useful in pieces. "It indicates if an HTTP response can be processed incrementally, i.e., provide some meaningful output as chunks of the response arrive." (4.2)

- RFC 7540 had clients send a tree with weights. "RFC 7540 [RFC7540] stream priority allowed a client to send a series of priority signals that communicate to the server a "priority tree"" (1)
- The tree also set weights. "the structure of this tree represents the client's preferred relative ordering and weighted distribution of the bandwidth among HTTP responses." (1)

- Clients can update priority later with version-specific frames. "After sending a request, a client can change their view of response priority (see Section 6) by sending HTTP-version-specific frames as defined in Sections 7.1 and 7.2." (1)
- The Priority header works the same across HTTP versions. "Section 5 defines the Priority HTTP header field, which is an end-to-end priority signal that is independent of protocol version." (1)
