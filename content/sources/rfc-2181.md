## Summary

A 1997 set of fixes to RFC 1034/1035 where implementations had drifted
apart. The parts used here: records of one name and type form an
RRset and share one TTL; a CNAME name holds nothing else; MX and NS must
point at real names with address records, never at aliases.

## Key claims

- Records in an RRset must all have the same TTL. "Consequently the use of differing TTLs in an RRSet is hereby deprecated, the TTLs of all RRs in an RRSet must be the same." (5.2)
- Different TTLs in one RRset could give partial answers from caches. "This can, however, cause partial replies (not marked "truncated") from a caching server, where the TTLs for some but not all the RRs in the RRSet have expired." (5.2)
- An alias has exactly one canonical name and (apart from DNSSEC records) no other data. "There may be only one such canonical name for any one alias." (10.1)
- MX and NS values must not be aliases. "The domain name used as the value of a NS resource record, or part of the value of a MX resource record must not be an alias." (10.3)
- More than one PTR per name is allowed. "There is no implication in that section that only one PTR record is permitted for a name." (10.2)

Added for `dns-records` audit:

- Definition of an RRset: same label, class and type. "Such a group of records is hereby defined to be a Resource Record Set (RRSet)." (5)
- A query returns the whole RRset. "A query for a specific (or non-specific) label, class, and type, will always return all records in the associated RRSet - whether that be one or more RRs." (5.1)
- MX and NS targets need address records of their own. "This domain name must have as its value one or more address records." (10.3)

## My notes

- The "no CNAME at the zone apex" rule follows from 10.1 plus the fact
  that the apex always holds SOA and NS records. RFC 9460 states the
  consequence directly.
