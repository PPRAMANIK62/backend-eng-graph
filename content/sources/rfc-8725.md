## Summary

The IETF best current practice for JWTs (BCP 225, 2020), written after
several widely published attacks. Section 2 lists the attacks; section 3
the practices that stop them.

## Key claims

- Attacks came from under-specified mechanisms and misuse. "Such attacks are the result of under-specified security mechanisms, as well as incomplete implementations and incorrect usage by applications." (1. Introduction)
- alg none. "The algorithm can be changed to "none" by an attacker, and some libraries would trust this value and "validate" the JWT without checking any signature." (2.1)
- RS256 to HS256 confusion. "some libraries would try to validate the signature using HMAC-SHA256 and using the RSA public key as the HMAC shared secret" (2.1)
- Weak HMAC keys can be brute-forced offline. "Such keys are vulnerable to offline brute-force or dictionary attacks once an attacker gets hold of such a token" (2.2)
- Substitution: a token meant for one service replayed at another. "There are attacks in which one recipient will be given a JWT that was intended for it and will attempt to use it at a different recipient for which that JWT was not intended." (2.7)
- Claims used for lookups can carry injection or SSRF. "Any of these claims can be used by an attacker as vectors for injection attacks or server-side request forgery (SSRF) attacks." (2.9)
- Allowlist algorithms. "Libraries MUST enable the caller to specify a supported set of algorithms and MUST NOT use any other algorithms when performing cryptographic operations." (3.1)
- One key, one algorithm. "Moreover, each key MUST be used with exactly one algorithm, and this MUST be checked when the cryptographic operation is performed." (3.1)
- No passwords as HMAC keys. "In particular, human-memorizable passwords MUST NOT be directly used as the key to a keyed-MAC algorithm such as "HS256"." (3.5)
- Keys must belong to the issuer. "When a JWT contains an "iss" (issuer) claim, the application MUST validate that the cryptographic keys used for the cryptographic operations in the JWT belong to the issuer." (3.8)
- Validate the audience when an issuer serves many parties. "the relying party or application MUST validate the audience value, and if the audience value is not present or not associated with the recipient, it MUST reject the JWT." (3.9)
- kid can be an injection vector; jku/x5u can be SSRF. "Similarly, blindly following a "jku" (JWK set URL) or "x5u" (X.509 URL) header, which may contain an arbitrary URL, could result in server-side request forgery (SSRF) attacks." (3.10)
- Explicit typing. "Explicit typing is RECOMMENDED for new uses of JWTs." (3.11)
- alg exists for agility. "Signed JSON Web Tokens carry an explicit indication of the signing algorithm, in the form of the "alg" Header Parameter, to facilitate cryptographic agility." (2.1)
- Different kinds of JWT from one issuer need mutually exclusive rules. "If more than one kind of JWT can be issued by the same issuer, the validation rules for those JWTs MUST be written such that they are mutually exclusive, rejecting JWTs of the wrong kind." (3.12)
- Where JWTs are used. "One application area in which JWTs are commonly used is representing digital identity information, such as OpenID Connect ID Tokens [OpenID.Core] and OAuth 2.0 [RFC6749] access tokens and refresh tokens, the details of which are deployment-specific." (1. Introduction)
- none only when something else protects the token. "The "none" algorithm should only be used when the JWT is cryptographically protected by other means." (3.2)
- OIDC issuers publish keys via metadata. "OpenID Connect [OpenID.Core] issuer values are "https" URLs that reference a JSON metadata document that contains a "jwks_uri" value that is an "https" URL from which the issuer's keys are retrieved as a JWK Set [RFC7517]." (3.8)
- kid lookups and injection. "Applications should ensure that this does not create SQL or LDAP injection vulnerabilities by validating and/or sanitizing the received value." (3.10)
- Explicit typing prevents confusion between kinds of JWT. "Explicit JWT typing is accomplished by using the "typ" Header Parameter." (3.11)
