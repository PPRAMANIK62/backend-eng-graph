## Summary

The IETF working-group draft that standardises the Idempotency-Key
request header, read at version -07 (2025). Not an RFC: the
datatracker listed it as expired when this was written. It defines
the header's syntax, key uniqueness, expiry, an optional request
fingerprint, the responses for a completed duplicate, a concurrent
duplicate, a missing key and a reused key, and lists APIs that already
use the header.

## Key claims

- The problem: a POST that timed out leaves the client unsure. "The client is left uncertain about the status of the resource." (1)
- Per RFC 9110, OPTIONS, HEAD, GET, PUT and DELETE are idempotent, POST and PATCH aren't. "Per [RFC9110], the methods OPTIONS, HEAD, GET, PUT and DELETE are idempotent while methods POST and PATCH are not." (1)
- Definition of the key. "An idempotency key is a unique value generated by the client which the resource uses to recognize subsequent retries of the same request." (2)
- Syntax: a Structured Header String. "Its value MUST be a String (Section 3.3.3 of [RFC8941])." (2.1)
- A key must not be reused with a different payload. "The idempotency key MUST be unique and MUST NOT be reused with another request with a different request payload." (2.2)
- UUIDs recommended. "It is RECOMMENDED that a UUID [RFC4122] or a similar random identifier be used as an idempotency key." (2.2)
- Example value. `Idempotency-Key: "8e03978e-40d5-43e8-bc93-6894a57f9324"` (2.2)
- The server may expire keys and should publish its policy. "The resource SHOULD define such expiration policy and publish it in the documentation." (2.3)
- An optional fingerprint from the payload, for example a checksum. "An idempotency fingerprint MAY be used in conjunction with an idempotency key to determine the uniqueness of a request." (2.4)
- A client can't assume a server honours the header without knowing. "Without a priori knowledge, a general client cannot assume the server will respect this request." (2.5.1)
- Duplicate after completion: return the earlier result, success or error. "The resource SHOULD respond with the result of the previously completed operation, success or an error." (2.6)
- Duplicate while the first is still running: a conflict error. "The request was retried before the original request completed. The resource SHOULD respond with a resource conflict error." (2.6)
- Missing key where required: 400. "the resource SHOULD reply with an HTTP 400 status code with body containing a link pointing to relevant documentation." (2.7)
- Reused key with a different payload: 422. "If there is an attempt to reuse an idempotency key with a different request payload, the resource SHOULD reply with a HTTP 422 status code" (2.7)
- Retry while the original is processing: 409. "If the request is retried, while the original request is still being processed, the resource SHOULD reply with an HTTP 409 status code with body containing problem description." (2.7)
- Implementations listed include Stripe, Adyen, Dwolla, Interledger, WorldPay, Yandex, http4s, Finastra, Datatrans. "Organization: Stripe" (4)
- Low-entropy keys let an attacker fetch other clients' cached results. "When an idempotency implementation allows low entropy keys, attackers MAY determine other keys and use them to fetch existing idempotent cache entries, belonging to other clients." (5)
- Scope the lookup with client-specific attributes. "For example, a composite key MAY be implemented by combining the idempotency key sent by the client with other client specific attributes known only to the resource." (5)
- Status re-checked on the datatracker page: version 07 is still the latest, listed as "Expired Internet-Draft (httpapi WG)", "Expired & archived", not an RFC.

## My notes

- The draft omits TRACE from its list of idempotent methods; RFC 9110
  9.2.2 includes it (all safe methods are idempotent).
- Still a draft, so no status code here is a standard yet. Say "the
  draft suggests".
