## Summary

The spec (2011, Standards Track) that defines an origin (scheme, host,
port), explains the principles of the same-origin policy, and defines
the Origin request header. The Fetch Standard now supersedes its Origin
header semantics, but the principles in section 3 still describe the
policy.

## Key claims

- Two URIs share an origin if scheme, host and port match. "Roughly speaking, two URIs are part of the same origin (i.e., represent the same principal) if they have the same scheme, host, and port." (3.2)
- The scheme is in the tuple so HTTP content can't attack HTTPS content. "Including the scheme in the origin tuple is essential for security." (3.2, Q&A)
- The full host, not the registered domain, because trust varies by deployment. "Although the DNS has hierarchical delegation, the trust relationships between host names vary by deployment." (3.2, Q&A)
- Origin granularity is partly an accident of history. "In some sense, the origin granularity is a historical artifact of how the security model evolved." (3.2)
- A page grants its privileges to scripts it includes. "In this way, the document grants all the privileges it has to the resource designated by the URI." (3.1)
- Objects (DOM and other APIs) are shared only within one origin. "Specifically, content retrieved from one URI can access objects associated with content retrieved from another URI if, and only if, the two URIs belong to the same origin, e.g., have the same scheme, host, and port." (3.4.1)
- Media type limits what content can do; untrusted content served as an image carries less authority than HTML. "For example, serving user-generated content as image/png is less risky than serving user-generated content as text/html." (3.3)
- Reading from another origin is generally forbidden. "Generally, reading information from another origin is forbidden." (3.4.2)
- But using some cross-origin resources is allowed: run scripts, show images, apply styles. "For example, an origin is permitted to execute script, render images, and apply style sheets from any origin." (3.4.2)
- Resources can opt in to being read, via CORS. "Network resources can also opt into letting other origins read their information, for example, using Cross-Origin Resource Sharing [CORS]." (3.4.2)
- Sending information to another origin is allowed. "Sending information to another origin is permitted." (3.4.2)
- That permission is what makes CSRF possible. "Similarly, the ability to send network requests to another origin gives rise to cross-site request forgery vulnerabilities [CSRF]." (3.4.3)
- Blocking cross-origin requests would break links. "For example, an HTML user agent that blocked cross-origin network requests would prevent its users from following hyperlinks, a core feature of the web." (3.4.3)
- Embedding leaks a little, like image dimensions. "For example, the ability to display images from another origin leaks their height and width." (3.4.3)
- The Origin header names the origin that caused the request. "the Origin header field indicates the origin(s) that "caused" the user agent to issue the request" (7.2)
- Privacy-sensitive contexts send "null". "Whenever a user agent issues an HTTP request from a "privacy-sensitive" context, the user agent MUST send the value "null" in the Origin header field." (7.3)
- The policy leans on DNS for http. "In practice, the same-origin policy relies upon the Domain Name System (DNS) for security because many commonly used URI schemes, such as http, use DNS-based naming authorities." (8.1)
- Cookies predate origins and use a different unit of isolation. "However, many technologies in use today, such as cookies [RFC6265], pre-date the modern web origin concept." (8.2)
- Script injected into a page runs with the page's origin (the ambient authority problem behind XSS). "If an attacker can inject script content into an HTML document, those scripts will run with the authority of the document's origin" (8.3)
- Different isolation units lead to bugs. "These technologies often have different isolation units, leading to vulnerabilities." (8.2)
- https resists DNS compromise because of certificates. "Some URI schemes, such as https, are more resistant to DNS compromise because user agents employ other mechanisms, such as certificates, to verify the source of content retrieved from these URIs." (8.1)
