## Summary

Netflix's CDC framework. The transaction log has limited retention, so
CDC also needs the full current state; existing tools either lock
tables, stop the log while dumping, or risk "time travel" (an older row
version arriving after a newer one). DBLog reads tables in primary-key
chunks between two watermark writes and drops chunk rows that the log
changed inside the window, so dumps interleave with log events without
locks.

## Key claims

- Dual writes and distributed transactions have limitations; CDC reads changed rows from the transaction log. "An alternative approach that has recently emerged is to utilize Change-Data-Capture (CDC) in order to capture changed rows from a database’s transaction log and eventually deliver them downstream with low latency." (Abstract)
- Logs don't keep full history, so the full state has to be captured too. "In database systems, the transaction log typically has limited retention and it is not guaranteed to contain the full history of changes." (1 Introduction)
- Requirement: no time travel, an earlier version of a row must not be delivered after a later one. "This way an earlier version of a row (like the residential address of a member account) is not delivered after a later version." (1 Introduction)
- Requirement: avoid table locks, which block application writes. "we want to avoid primitives such as table locks which can block application write traffic." (1 Introduction)
- Existing tools (Databus, Maxwell) are prone to time travel; Debezium (at the time) used table locks for its consistent snapshot. "Debezium [10] captures a consistent snapshot for MySQL and PostgreSQL by using table locks and running selects across all tables within one transaction." (2 Related work)
- The database must emit each changed row in commit order, with an LSN. "The framework requires a database to emit an event for each changed row in commit order." (3.1)
- Chunks are selected in ascending primary key order after the last key of the previous chunk. (3.2)
- Watermarks: a single-row table whose UUID is updated; the update shows up in the change log. "A watermark is then generated by updating the UUID value of that row." (3.2)
- Algorithm: pause log processing, write low watermark, select chunk, write high watermark, resume; drop chunk rows whose keys appear in the log between the watermarks; emit the rest when the high watermark arrives. "As the exact position of the select is unknown, all selected chunk rows are removed, which collide with log events within that window." (3.2)
- Needs non-stale reads: the select must see changes committed before it runs. "We define this capability as ‘non-stale reads’." (3.2)
- Used at Netflix. "DBLog is currently used in production by tens of microservices at Netflix." (Abstract)
- Postgres support via replication slots and wal2json. (3.3)
