## Summary

The current HTTP/2 spec, obsoleting RFC 7540. Its introduction names
two kinds of head-of-line blocking: HTTP/1.1's at the application
layer, which HTTP/2 fixes, and TCP's, which it doesn't.

## Key claims

- HTTP/1.1 pipelining still has application-layer HOL blocking, so clients open several connections. "HTTP/1.1 [HTTP/1.1] added request pipelining, but this only partially addressed request concurrency and still suffers from application-layer head-of-line blocking." (1)
- HTTP/2 doesn't fix TCP's HOL blocking. "Note, however, that TCP head-of-line blocking is not addressed by this protocol." (1)

Added for `head-of-line-blocking` audit:

- HTTP/2 interleaves messages on one connection. "Specifically, it allows interleaving of messages on the same connection and uses an efficient coding for HTTP fields." (1)
- Because of pipelining's limits, HTTP/1.x clients open several connections. "Therefore, HTTP/1.0 and HTTP/1.1 clients use multiple connections to a server to make concurrent requests." (1)

Added for `http2`:

- HTTP/1.x headers are repetitive and fill the initial congestion window. "HTTP fields are often repetitive and verbose, causing unnecessary network traffic as well as causing the initial TCP congestion window to quickly fill." (1)
- HTTP/2 uses binary framing. "Finally, HTTP/2 also enables more efficient processing of messages through use of binary message framing." (1)
- One request/response exchange per stream; streams are largely independent. "Multiplexing of requests is achieved by having each HTTP request/response exchange associated with its own stream (Section 5)." (2)
- The RFC 7540 priority scheme is deprecated. "This revision of HTTP/2 deprecates the priority signaling scheme from [RFC7540]." (2)
- Over TLS, HTTP/2 is chosen with ALPN as "h2". "The string "h2" identifies the protocol where HTTP/2 uses Transport Layer Security (TLS); see Section 9.2." (3.1)
- Upgrading from HTTP/1.1 with "h2c" is deprecated. "This usage was never widely deployed and is deprecated by this document." (3.1)
- Without TLS, a client needs prior knowledge that the server speaks HTTP/2. "A client that knows that a server supports HTTP/2 can establish a TCP connection and send the connection preface (Section 3.4) followed by HTTP/2 frames." (3.3)
- The client preface is a fixed 24-octet string followed by SETTINGS. "That is, the connection preface starts with the string "PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n"." (3.4)
- Every frame has a 9-octet header: 24-bit length, 8-bit type, 8-bit flags, 1 reserved bit, 31-bit stream identifier. "All frames begin with a fixed 9-octet header followed by a variable-length frame payload." (4.1)
- Stream 0 is the connection itself. "The value 0x00 is reserved for frames that are associated with the connection as a whole as opposed to an individual stream." (4.1)
- Frames above 16,384 bytes need the receiver's permission. "Values greater than 2^14 (16,384) MUST NOT be sent unless the receiver has set a larger value for SETTINGS_MAX_FRAME_SIZE." (4.1)
- Big frames delay urgent ones. "Sending large frames can result in delays in sending time-sensitive frames (such as RST_STREAM, WINDOW_UPDATE, or PRIORITY), which, if blocked by the transmission of a large frame, could affect performance." (4.2)
- Header blocks (HEADERS + CONTINUATION) must be sent contiguously. "Field blocks MUST be transmitted as a contiguous sequence of frames, with no interleaved frames of any other type or from any other stream." (4.3)
- Header compression state is per connection and starts at 4,096 bytes. "When a connection is established, the dynamic table size for the HPACK decoder and encoder at both endpoints starts at 4,096 bytes" (4.3.1)
- Client-initiated streams are odd, server-initiated even. "Streams initiated by a client MUST use odd-numbered stream identifiers; those initiated by the server MUST use even-numbered stream identifiers." (5.1.1)
- Stream IDs can't be reused; a long-lived connection can run out. "Stream identifiers cannot be reused." (5.1.1)
- The concurrency limit counts open and half-closed streams. "Streams that are in the "open" state or in either of the "half-closed" states count toward the maximum number of streams that an endpoint is permitted to open." (5.1.2)
- Flow control applies per stream and per connection. "Flow control is used for both individual streams and the connection as a whole." (5.2)
- It works hop by hop. "HTTP/2 flow control operates between the endpoints of a single hop and not over the entire end-to-end path." (5.2.1)
- Initial window 65,535 octets. "The initial value for the flow-control window is 65,535 octets for both new streams and the overall connection." (5.2.1)
- Only DATA frames are flow controlled. "Of the frames specified in this document, only DATA frames are subject to flow control" (5.2.1)
- A window smaller than the bandwidth-delay product limits throughput. "If an endpoint cannot ensure that its peer always has available flow-control window space that is greater than the peer's bandwidth * delay product on this connection, its receive throughput will be limited by HTTP/2 flow control." (5.2.3)
- Bad prioritisation can make HTTP/2 slower than HTTP/1.1. "With no parallelism at the TCP layer, performance could be significantly worse than HTTP/1.1." (5.3)
- RFC 7540's priority signals failed. "In short, the prioritization signaling in RFC 7540 [RFC7540] was not successful." (5.3.1)
- MAX_CONCURRENT_STREAMS starts unlimited; at least 100 is recommended. "Initially, there is no limit to this value. It is recommended that this value be no smaller than 100, so as to not unnecessarily limit parallelism." (6.5.2)
- RST_STREAM cancels one stream. "RST_STREAM is sent to request cancellation of a stream or to indicate that an error condition has occurred." (6.4)
- PING measures RTT and checks an idle connection. "The PING frame (type=0x06) is a mechanism for measuring a minimal round-trip time from the sender, as well as determining whether an idle connection is still functional." (6.7)
- GOAWAY stops new streams while old ones finish. "GOAWAY allows an endpoint to gracefully stop accepting new streams while still finishing processing of previously established streams." (6.8)
- GOAWAY is meant for things like server maintenance. "This enables administrative actions, like server maintenance." (6.8)
- GOAWAY carries the last stream the sender might have processed. "the GOAWAY contains the stream identifier of the last peer-initiated stream that was or might be processed on the sending endpoint in this connection." (6.8)
- A message is HEADERS, then DATA, then optional trailing HEADERS. (8.1)
- Control data travels as pseudo-headers starting with ':'. "HTTP/2 uses special pseudo-header fields beginning with a ':' character (ASCII 0x3a) to convey message control data" (8.3)
- Push is hard to use well. "In practice, server push is difficult to use effectively, because it requires the server to correctly anticipate the additional requests the client will make" (8.4)
- GOAWAY and REFUSED_STREAM tell a client which requests are safe to retry. "Requests on streams with higher numbers are therefore guaranteed to be safe to retry." (8.7)
- PING lets a client test an idle connection that a NAT or load balancer may have dropped. "Connections that remain idle can become broken, because some middleboxes (for instance, network address translators or load balancers) silently discard connection bindings." (8.7)
- One connection per host and port. "Clients SHOULD NOT open more than one HTTP/2 connection to a given host and port pair" (9.1)
- A connection may be reused for other hosts the certificate covers; 421 undoes a wrong guess. "A single certificate can be used to establish authority for multiple origins." (9.1.1)
- HTTP/2 needs more state per connection than HTTP/1.1. "An HTTP/2 connection can demand a greater commitment of resources to operate than an HTTP/1.1 connection." (10.5)
- Several implementations were found open to denial of service through legitimate features. "A number of HTTP/2 implementations were found to be vulnerable to denial of service [NFLX-2019-002]." (10.5)
- Implementations should count feature use and set limits. "Implementations SHOULD track the use of these features and set limits on their use." (10.5)

- RFC 9113 (2022) replaces RFC 7540. "This document obsoletes RFCs 7540 and 8740." (1)
- Verbose headers slow down many requests on a new connection. "This can result in excessive latency when multiple requests are made on a new TCP connection." (1)
- Frame types: DATA 0x00, HEADERS 0x01, PRIORITY 0x02 (deprecated), RST_STREAM 0x03, SETTINGS 0x04, PUSH_PROMISE 0x05, PING 0x06, GOAWAY 0x07, WINDOW_UPDATE 0x08, CONTINUATION 0x09. (6.1 to 6.10)
- Unknown frame types are dropped. "Implementations MUST ignore and discard frames of unknown types." (4.1)
- SETTINGS, PING and GOAWAY belong to the connection (stream 0). "SETTINGS frames always apply to a connection, never a single stream." (6.5) and "PING frames are not associated with any individual stream." (6.7)
- The last frame of a message carries END_STREAM. "The last frame in the sequence bears an END_STREAM flag" (8.1)
- Pseudo-headers come before regular fields. "All pseudo-header fields MUST appear in a field block before all regular field lines." (8.3)
- Responses carry `:status`. "For HTTP/2 responses, a single ":status" pseudo-header field is" (8.3.2)
- New stream IDs must go up. "The identifier of a newly established stream MUST be numerically greater than all streams that the initiating endpoint has opened or reserved." (5.1.1)
- Long-lived connections can run out of IDs. "Long-lived connections can result in an endpoint exhausting the available range of stream identifiers." (5.1.1)
- Stream states: idle, open, half-closed (local or remote) after END_STREAM, closed after both END_STREAMs or RST_STREAM. (5.1, figure 2)
- Without TLS, reuse for another host needs the same IP address. "For TCP connections without TLS, this depends on the host having resolved to the same IP address." (9.1.1)
- With TLS, it also needs a certificate valid for the host. "For "https" resources, connection reuse additionally depends on having a certificate that is valid for the host in the URI." (9.1.1)
- 421 tells a client not to reuse the connection for that host. "A server that does not wish clients to reuse connections can indicate that it is not authoritative for a request by sending a 421 (Misdirected Request) status code" (9.1.1)
- The client preface is followed by SETTINGS. "This sequence MUST be followed by a SETTINGS frame (Section 6.5), which MAY be empty." (3.4)
- The preface is chosen so old servers stop. "The client connection preface is selected so that a large proportion of HTTP/1.1 or HTTP/1.0 servers and intermediaries do not attempt to process further frames." (3.4)
- The server's first frame is SETTINGS. "The server connection preface consists of a potentially empty SETTINGS frame (Section 6.5) that MUST be the first frame the server sends in the HTTP/2 connection." (3.4)
- Clients may send requests before the server's SETTINGS arrive. "clients are permitted to send additional frames to the server immediately after sending the client connection preface, without waiting to receive the server connection preface." (3.4)
- Control frames never wait on flow control. "This ensures that important control frames are not blocked by flow control." (5.2.1)
- Flow control is for receivers with limited resources, like a proxy. "For example, a proxy needs to share memory between many connections and also might have a slow upstream connection and a fast downstream one." (5.2.2)
- It lets a receiver stall one stream but not others. "Flow control addresses cases where the receiver is unable to process data on one stream yet wants to continue to process other streams in the same connection." (5.2.2)
- Advertising the maximum window effectively turns flow control off. "Deployments that do not require this capability can advertise a flow-control window of the maximum size (2^31-1) and can maintain this window by sending a WINDOW_UPDATE frame when any data is received." (5.2.2)
- Header block frames can change the compression state, hence they can't be interleaved. "because these frames carry data that can modify the compression context maintained by a receiver." (4.3)
- PING must be answered, with high priority. "PING responses SHOULD be given higher priority than any other frame." (6.7)
- Unprocessed requests may be retried, even non-idempotent ones. "Requests that have not been processed have not failed; clients MAY automatically retry them, even those with non-idempotent methods." (8.7)
- REFUSED_STREAM says a stream was never processed. "The REFUSED_STREAM error code can be included in a RST_STREAM frame to indicate that the stream is being closed prior to any processing having occurred." (8.7)
- Wrong push guesses cost more important responses. "In particular, pushing any significant amount of data can cause contention issues with responses that are more important." (8.4)
- Push was meant for things like stylesheets a page will ask for. "For example, a request for HTML is often followed by requests for stylesheets and scripts referenced by that page." (8.4)
- RFC 7540 priorities were uneven and often ignored. "Implementation of priorities was uneven in both clients and servers.  Many server deployments ignored client signals when prioritizing their handling of requests." (5.3.1)
- Features that can be abused include PING and SETTINGS replies and tiny WINDOW_UPDATEs. "Providing tiny increments to flow control in WINDOW_UPDATE frames can cause a sender to generate a large number of DATA frames." (10.5)

Added for `http2` audit:

- The client preface is 24 octets. "The client connection preface starts with a sequence of 24 octets" (3.4)
- A PING carries 8 bytes. "In addition to the frame header, PING frames MUST contain 8 octets of opaque data in the frame payload." (6.7)
- Push has to guess around caching, and wrong guesses cost bandwidth. "taking into account factors such as caching, content negotiation, and user behavior." (8.4)
- RFC 7540 priority was complex and unevenly implemented. "However, this system proved to be complex, and it was not uniformly implemented." (5.3.1)
- Floods of small frames are one abuse. "Large numbers of small or empty frames can be abused to cause a peer to expend time processing frame headers." (10.5)
