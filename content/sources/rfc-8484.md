## Summary

The 2018 spec for DNS over HTTPS: each DNS query and response becomes
one HTTP request and response over https, using the normal DNS wire
format as the body (`application/dns-message`). It covers GET vs POST,
how HTTP caching interacts with DNS TTLs, HTTP/2 as the minimum
recommended version, and the privacy trade-offs of putting DNS inside
the whole HTTP stack.

## Key claims

- One DNS query-response pair is one HTTP exchange. "Each DNS query-response pair is mapped into an HTTP exchange." (Abstract)
- Two use cases: stopping on-path interference, and letting web apps do DNS. "These use cases are preventing on-path devices from interfering with DNS operations, and also allowing web applications to access DNS information via existing browser APIs in a safe way" (1)
- Server identity is checked the HTTPS way. "[RFC2818] defines how HTTPS verifies the DoH server's identity." (3)
- A DoH client uses only its configured server. "A DoH client MUST NOT use a different URI simply because it was discovered outside of the client's configuration" (3)
- GET puts the query base64url-encoded in a `dns` parameter; POST sends it as the body. "When the HTTP method is GET, the single variable \"dns\" is defined as the content of the DNS request (as described in Section 6), encoded with base64url [RFC4648]." (4.1)
- POST sends the raw DNS message as the body. "When using the POST method, the data payload for this media type MUST NOT be encoded and is used directly as the HTTP message body." (6)
- The response type is the same DNS message format. "The only response type defined in this document is \"application/dns-message\"" (4.2)
- UDP DNS is unordered and cheap, which is why HTTP/2 is recommended. "The messages in classic UDP-based DNS [RFC1035] are inherently unordered and have low overhead." (5.2)
- The client's IP address is plain correlation data. "At the IP level, the client address provides obvious correlation information." (8.2)
- One connection for many queries groups them. "DNS implementations that use one TCP connection for multiple DNS requests directly group those requests." (8.2)
- Ways out of the bootstrap problem: configuration, IP-based URIs, or plain DNS with HTTPS still authenticated. "resolving the DNS API server's hostname via traditional DNS or another DoH server while still authenticating the resulting connection via HTTPS." (10)
- Servers must do both. "DoH servers MUST implement both the POST and GET methods." (4.1)
- Use DNS ID 0 so equal queries cache the same. "DoH clients using media formats that include the ID field from the DNS message header, such as \"application/dns-message\", SHOULD use a DNS ID of 0 in every DNS request." (4.1)
- A DNS failure still comes back as HTTP 2xx. "For example, a successful 2xx HTTP status code is used even with a DNS message whose DNS response code indicates failure, such as SERVFAIL or NXDOMAIN." (4.2.1)
- HTTP freshness must not outlive the smallest TTL. "The assigned freshness lifetime of a DoH HTTP response MUST be less than or equal to the smallest TTL in the Answer section of the DNS response." (5.1)
- Clients subtract the Age header from the TTL. "DoH clients MUST account for the Age response header field's value [RFC7234] when calculating the DNS TTL of a response." (5.1)
- HTTP/2 is the minimum recommended version. "HTTP/2 [RFC7540] is the minimum RECOMMENDED version of HTTP for use with DoH." (5.2)
- Why HTTP/2: UDP DNS is unordered and cheap, so HTTP needs reordering and parallelism to compete. "A competitive HTTP transport needs to support reordering, parallelism, priority, and header compression to achieve similar performance." (5.2)
- Encrypted and server-authenticated, like DoT. "DoH encrypts DNS traffic and requires authentication of the server." (8.1)
- Port 443 and mixing with other HTTPS traffic make it harder to single out. "the use of the HTTPS default port 443 and the ability to mix DoH traffic with other HTTPS traffic on the same connection can deter unprivileged on-path devices from interfering with DNS operations" (8.1)
- The server can still correlate: IP address, one connection for many queries, TLS resumption, cookies, headers. "Session resumption creates trivial mechanisms for a server to correlate TLS connections together." (8.2)
- Cookies should be refused unless needed. "HTTP cookies SHOULD NOT be accepted by DOH clients unless they are explicitly required by a use case." (8.2)
- DoH doesn't replace DNSSEC. "The HTTPS connection provides transport security for the interaction between the DoH server and client, but it does not provide the response integrity of DNS data provided by DNSSEC." (9)
- Without DNSSEC, the DoH server can hand out invalid data. "In the absence of DNSSEC information, a DoH server can give a client invalid data in response to a DNS query." (9)
- The server you pick affects the answers (split DNS). "Local policy considerations and similar factors mean different DNS servers may provide different results to the same query, for instance, in split DNS configurations [RFC6950]." (10)
- Scope: stub to recursive. "This document focuses on communication between DNS clients (such as operating system stub resolvers) and recursive resolvers." (1)
- Filtering built on plaintext DNS stops working. "Filtering or inspection systems that rely on unsecured transport of DNS will not function in a DNS over HTTPS environment" (10)
- Bootstrap problem: you can't resolve the DoH server's own name through it. "a DoH client cannot use its DoH server to initially resolve the server's host name into an address." (10)
