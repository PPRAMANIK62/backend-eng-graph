## Summary

A short informational RFC from 2010 that adds two Cache-Control
extensions: `stale-while-revalidate`, which lets a cache answer with a
stale response while it refreshes it in the background, and
`stale-if-error`, which lets a cache answer with a stale response when
the origin fails. Written by the person who built them at Yahoo!.

## Key claims

- It's informational, not a standard. "This document is not an Internet Standards Track specification; it is published for informational purposes." (Status of This Memo)
- stale-if-error returns a stale response instead of a hard error, for availability. "The stale-if-error HTTP Cache-Control extension allows a cache to return a stale response when an error -- e.g., a 500 Internal Server Error, a network segment, or DNS failure -- is encountered, rather than returning a \"hard\" error." (1)
- stale-while-revalidate hides revalidation latency from clients. "allows a cache to immediately return a stale response while it revalidates it in the background, thereby hiding latency (both in the network and on the server) from clients." (1)
- The cache should revalidate without blocking while it serves stale. "the cache SHOULD attempt to revalidate it while still serving stale responses (i.e., without blocking)." (3)
- Once the window passes without revalidation, stop serving stale. "If delta-seconds passes without the cached entity being revalidated, it SHOULD NOT continue to be served stale, absent other information." (3)
- Example: max-age=600, stale-while-revalidate=30 is fresh for 600 s, then may be served stale for up to 30 more seconds while an async validation runs. "indicates that it is fresh for 600 seconds, and it may continue to be served stale for up to an additional 30 seconds while an asynchronous validation is attempted." (3.1)
- Set max-age plus the window to the longest total staleness you can live with; with both at 600, up to 20 minutes. "with both set to 600, the server must be able to tolerate the response being served from cache for up to 20 minutes." (3.1)
- The background refresh only happens if a request arrives inside the window; sparse traffic means requests still block. "If the window is too small, or traffic is too sparse, some requests will fall outside of it, and block until the server can validate the cached response." (3.1)
- An error means a 500, 502, 503 or 504 would be returned. "In this context, an error is any situation that would result in a 500, 502, 503, or 504 HTTP response status code being returned." (4)
- stale-if-error works in requests and responses. "When used as a request Cache-Control extension, its scope of application is the request it appears in" (4)
- Example: max-age=600, stale-if-error=1200: a 500 at 900 s is replaced by the stored 200 with Age: 900; after an age of 1800 s the error goes through. "After the age is greater than 1800 seconds (i.e., it has been stale for 1200 seconds), the cache must write the error message through." (4.1)
- Background revalidation should be triggered by a real request, to avoid amplification. "It is suggested that such validation be predicated upon an incoming request, to avoid the possibility of an amplification attack" (5)

## My notes

- Written against RFC 2616; RFC 9111 4.2.4 names "extension directives
  such as those defined in [RFC5861]" as one way serving stale is allowed.
- The "warning header" it mentions was obsoleted by RFC 9111 (5.5).
