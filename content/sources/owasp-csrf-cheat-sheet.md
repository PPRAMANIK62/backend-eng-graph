## Summary

OWASP's long guide to CSRF defenses: use your framework's protection,
synchronizer tokens for stateful apps, signed double-submit cookies for
stateless ones, Fetch Metadata for modern browsers, custom headers for
API-driven sites, and SameSite and origin checks as defense in depth.

## Key claims

- Definition: another site tricks the user's browser into an unwanted action on a site where they're logged in. "A Cross-Site Request Forgery (CSRF) attack occurs when a malicious web site, email, blog, instant message, or program tricks an authenticated user's web browser into performing an unwanted action on a trusted site." (Introduction)
- It works because browsers attach cookies automatically. "Since browser requests automatically include all cookies including session cookies, this attack works unless proper authorization is used" (Introduction)
- The attacker gets the user's capabilities, not more. "successful CSRF attacks can only exploit the capabilities exposed by the vulnerable application and the user's privileges." (Introduction)
- XSS defeats CSRF protection. "Remember that Cross-Site Scripting (XSS) can defeat all CSRF mitigation techniques!" (Introduction)
- Tokens are still essential for cookie-authenticated apps, in OWASP's view. "While Cross-Site Scripting (XSS) vulnerabilities can bypass CSRF protections, CSRF tokens are still essential for web applications that rely on cookies for authentication." (Introduction)
- Fetch Metadata alone is an option only when you target modern browsers. "If your software targets only modern browsers, you may rely on Fetch Metadata headers together with the fallback options described below to block cross-site state-changing requests." (Introduction)
- Use the framework's protection first. "First, check if your framework has built-in CSRF protection and use it" (Introduction)
- Don't change state on GET. "Do not use GET requests for state changing operations." (Introduction)
- Go 1.25 ships a Fetch-Metadata-based defense. "Starting from 1.25, Go developers can rely on the built-in CrossOriginProtection type." (Built-In Or Existing CSRF Implementations)
- Tokens: unique per session, secret, unpredictable. "Unpredictable (large random value generated by a secure method)." (Synchronizer Token Pattern)
- Without the token an attacker can't build a valid request. "CSRF tokens prevent CSRF because without a CSRF token, an attacker cannot create valid requests to the backend server." (Synchronizer Token Pattern)
- Tokens must not go in URLs or logs. "A CSRF token must not be leaked in the server logs or in the URL." (Transmitting CSRF Tokens in Synchronized Patterns)
- Custom request headers are covered by the same-origin policy. "Since requests with custom headers are automatically subject to the same-origin policy, it is more secure to insert the CSRF token in a custom HTTP request header via JavaScript than adding a CSRF token in the hidden field form parameter." (Transmitting CSRF Tokens in Synchronized Patterns)
- The naive double-submit cookie falls to anyone who can write cookies on the domain. "The Naive Double-Submit Cookie pattern is bypassable by an attacker who can write cookies on the target domain" (Naive Double-Submit Cookie Pattern)
- Sec-Fetch-Site is the main Fetch Metadata signal. "Sec-Fetch-Site — the primary signal for CSRF protection." (Fetch Metadata headers)
- A fallback for browsers without the headers is mandatory. "Because some legacy browsers do not send Sec-Fetch-* headers, a fallback to standard origin verification headers is a mandatory requirement for any Fetch Metadata implementation." (Fetch Metadata headers)
- Sec-Fetch-Site values. "It indicates the relationship between the request initiator’s origin and its target's origin: same-origin, same-site, cross-site, or none." (Fetch Metadata headers)
- Signed double submit must be bound to the session. "Simply signing tokens without session binding provides minimal protection and remains vulnerable to cookie injection attacks. Always bind the CSRF token explicitly to session-specific data." (Signed Double-Submit Cookie)
- Lax blocks the cookie on unsafe cross-site methods, Strict on all cross-site contexts. "the session cookie would be allowed when following a regular link from an external website while blocking it in CSRF-prone request methods such as POST." (SameSite)
- The cheat sheet reports Lax as the default in Chrome since 2020, with Firefox and Edge following. "Chrome implemented SameSite=Lax as the default behavior in 2020, and Firefox and Edge have followed suit." (SameSite)
