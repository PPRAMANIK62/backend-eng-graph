## Summary

The 2012 RFC that added four status codes to HTTP: 428 Precondition
Required, 429 Too Many Requests, 431 Request Header Fields Too Large and
511 Network Authentication Required. For rate limiting, section 4 (429)
and section 7.2 are the parts that matter.

## Key claims

- 429 means the client sent too many requests in some amount of time. "The 429 status code indicates that the user has sent too many requests in a given amount of time (\"rate limiting\")." (4)
- A 429 should explain itself and may say when to come back. "The response representations SHOULD include details explaining the condition, and MAY include a Retry-After header indicating how long to wait before making a new request." (4)
- The RFC leaves how you identify and count clients up to you. "Note that this specification does not define how the origin server identifies the user, nor how it counts requests." (4)
- Counting can be per resource, per server or across servers; identity can be credentials or a cookie. "an origin server that is limiting request rates can do so based upon counts of requests on a per-resource basis, across the entire server, or even among a set of servers." (4)
- 429 must not be cached. "Responses with the 429 status code MUST NOT be stored by a cache." (4)
- Answering every request with 429 costs resources too; under attack, dropping connections can be better. "Therefore, servers are not required to use the 429 status code; when limiting resource usage, it may be more appropriate to just drop connections, or take other steps." (7.2)
- Unknown codes fall back to their class, so new codes are safe to deploy. "clients will treat unknown status codes as a generic error of the same class (e.g., 499 is treated as 400 if it is not recognized)" (1)
