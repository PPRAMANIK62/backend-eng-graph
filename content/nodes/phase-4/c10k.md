# The C10K problem

C10K is the problem of serving ten thousand clients at the same time
from one server. Dan Kegel named it in 1999, and the answers it
collected pushed servers from one
[[thread-per-connection|thread per connection]] to [[event-loop|event loops]].
The question underneath, what each open connection costs you in memory
and switching, still decides how servers are built.

## The hardware was never the problem

Kegel started with arithmetic. A machine with a 1000 MHz CPU, 2 GB of
RAM and a gigabit network card, serving 20,000 clients, gives each one
50 kHz of CPU, 100 KB of memory and 50 kbit/s of network. That's plenty
to send a few kilobytes a second to each client. In 1999 one busy FTP
site, cdrom.com, already handled 10,000 clients at once over gigabit
Ethernet.

So the limit wasn't the hardware. It was how operating systems and
servers handled each connection.

## Where a thread per connection ran out

The simple design is a [[thread-per-connection|thread per connection]]:
each client gets a thread that calls blocking `read` and `write`. Each
thread needs a stack, and in that era the stack was the problem:

- On 32-bit Linux, a [[process]] had 1 GB of user address space. With a
  common default of 2 MB per thread stack, that's room for 512 threads
  (2^30 / 2^21) before you run out of virtual addresses, whether or not
  the stacks are used.
- You could give threads smaller stacks, but most thread libraries
  couldn't grow a stack after creating it, so you had to keep every code
  path shallow.
- Kernels had their own caps. Linux 2.4 had a system-wide thread limit,
  and even with NPTL on Linux 2.6, going past about 32,000 threads meant
  raising `vm.max_map_count`.

On the right, an event loop: one thread calling epoll_wait on 10,000 sockets and running a handler for each ready one, with a small per-connection record holding each connection's state.](img/c10k-memory-per-connection.svg)

*What 10,000 connections cost in each design: a stack each, or a state record each.*

## The event-loop answer

The answer that won was to serve many clients from each thread. Put
every socket in [[non-blocking-io|non-blocking mode]], ask the kernel which ones are ready
([[io-multiplexing]]: `select` and `poll`, then Linux's epoll and BSD's
kqueue), and run a short handler for each ready one. That's the
[[event-loop]]. Instead of a stack per connection, you keep a small
record per connection with just its state: how much of the request has
arrived, what's left to send.

Kegel's list had other options too: asynchronous I/O with completion
notification, user-level threads, or putting the server in the kernel.

The event loop had one big hole, which Kegel pointed out: non-blocking
mode does nothing for disk files. The first time the server read a file
that wasn't in memory, the whole process blocked, and every client
waited. Servers worked around it with helper threads for disk I/O.

## What changed since

The numbers moved. On 64-bit machines, virtual address space is no
longer the limit, and a thread's stack only uses RAM for the pages it
touches. A 2018 test on Linux started 10,000 threads with the default
8 MiB stacks: about 80 GiB of virtual memory, but only about 80 MiB
resident. Its conclusion was that 10,000 threads in one process is
practical, and that a lot of early-2000s folklore about thread limits no
longer holds. Kegel had expected this: better threading and 64-bit CPUs
would make thread per connection workable at 10,000 clients.

What still matters is how much memory each connection really uses. In
the same test, when each of the 10,000 threads touched 400 KiB of stack,
resident memory went to about 2.6 GiB. That cost isn't about threads,
though. An event-loop handler that keeps 400 KiB per connection costs
the same.

## Where it gets tricky

**Threads vs events is an old argument.** In 2003, researchers who had
built event-driven servers argued that events were a mistake: the
problems blamed on threads came from particular thread libraries, not
from threads. Event code forces you to save and restore each
connection's state by hand between callbacks (they called it "stack
ripping"), and fixing that tends to reinvent threads. They showed a
user-level thread package running 100,000 threads, and a simple threaded
web server that beat an event-driven one on the same machine. The same
idea is behind [[green-threads]] today, and [[async-await]] is the
event-loop side's answer to stack ripping.

**Virtual is not resident.** A tool that shows 80 GiB for a process
with 10,000 threads isn't showing 80 GiB of RAM ([[virtual-memory]] explains the difference). Measure resident
memory when you count cost per connection.

**The page is history.** Kegel's page was last really updated in 2014,
and its OS details are from the Linux 2.4 and 2.6 days. Read it for the
design choices, not the limits.

## What this means when you build

- The phase 4 lab runs from 1,000 to 100,000 connections. Measure
  memory per connection as resident memory divided by connections, for
  each I/O model, not virtual size.
- Per-connection state is the real budget: buffers, parsed requests,
  stacks. Whatever design you pick, shrinking that is what lets you hold
  more connections.
- In an event loop, keep disk reads and other blocking calls off the
  loop thread.
