## Summary

The OAuth 2.0 spec (2012). It lets a third-party app get limited access
to an HTTP service on a user's behalf without the user's password: the
app sends the user to an authorization server, the user approves, and
the app gets an access token. Defines the four roles, client types, the
authorization code, implicit, password and client credentials grants,
and refresh tokens. Updated by RFC 8252, RFC 8996 and RFC 9700, not
obsoleted.

## Key claims

- The problem OAuth solves: sharing a password with a third party means it stores it, gets too much access, and can't be revoked alone. "Third-party applications gain overly broad access to the resource owner's protected resources" (1)
- Revoking one app meant changing the password. "Resource owners cannot revoke access to an individual third party without revoking access to all third parties, and must do so by changing the third party's password." (1)
- The client gets an access token instead of the user's credentials. "Instead of using the resource owner's credentials to access protected resources, the client obtains an access token -- a string denoting a specific scope, lifetime, and other access attributes." (1)
- The photo-printing example. "an end-user (resource owner) can grant a printing service (client) access to her protected photos stored at a photo-sharing service (resource server), without sharing her username and password with the printing service." (1)
- Four roles: resource owner, resource server, client, authorization server. "OAuth defines four roles" (1.1)
- The authorization server can be the same as the resource server, and one can serve many. "A single authorization server may issue access tokens accepted by multiple resource servers." (1.1)
- Access tokens are usually opaque to the client and can be a lookup id or a self-contained signed token. "The string is usually opaque to the client." and "may self-contain the authorization information in a verifiable manner (i.e., a token string consisting of some data and a signature)" (1.4)
- Refresh tokens get new access tokens and only go to the authorization server. "Unlike access tokens, refresh tokens are intended for use only with authorization servers and are never sent to resource servers." (1.5)
- Two client types, confidential and public, by whether they can keep a secret. "Clients incapable of maintaining the confidentiality of their credentials (e.g., clients executing on the device used by the resource owner, such as an installed native application or a web browser-based application)" (2.1)
- TLS is required at the authorization endpoint. "the authorization server MUST require the use of TLS as described in Section 1.6 when sending requests to the authorization endpoint." (3.1)
- TLS is required at the token endpoint. "the authorization server MUST require the use of TLS as described in Section 1.6 when sending requests to the token endpoint." (3.2)
- The code flow, steps A to E: redirect to authorization endpoint, user authenticates, redirect back with code, client exchanges code at the token endpoint. "The client requests an access token from the authorization server's token endpoint by including the authorization code received in the previous step." (4.1, step D)
- Codes are short-lived, single use, and bound to the client and redirect URI. "A maximum authorization code lifetime of 10 minutes is RECOMMENDED." and "The client MUST NOT use the authorization code more than once." (4.1.2)
- Reuse of a code should revoke tokens issued from it. "If an authorization code is used more than once, the authorization server MUST deny the request and SHOULD revoke (when possible) all tokens previously issued based on that authorization code." (4.1.2)
- CSRF against the redirect URI lets an attacker inject their own code. "A CSRF attack against the client's redirection URI allows an attacker to inject its own authorization code or access token" (10.12)
- Codes travel through the browser, so they leak through history and referrers. "they could potentially be disclosed through user-agent history and HTTP referrer headers." (10.5)
- Before OAuth, apps stored the user's password, often readable. "Third-party applications are required to store the resource owner's credentials for future use, typically a password in clear-text." (1)
- A breach of any such app leaks the password. "Compromise of any third-party application results in compromise of the end-user's password and all of the data protected by that password." (1)
- "Client" says nothing about where it runs. "The term \"client\" does not imply any particular implementation characteristics (e.g., whether the application executes on a server, a desktop, or other devices)." (1.1)
- The state parameter is there to stop CSRF. "The parameter SHOULD be used for preventing cross-site request forgery as described in Section 10.12." (4.1.1)
- How the authorization server and resource server talk is out of scope. "The interaction between the authorization server and resource server is beyond the scope of this specification." (1.1)
- Token attributes and how APIs check them are left to other specs. "Access token attributes and the methods used to access protected resources are beyond the scope of this specification" (1.4)
- Access tokens expire and refresh tokens replace them. "used to obtain a new access token when the current access token becomes invalid or expires" (1.5)
- The endpoints carry credentials in clear text, hence TLS. "Since requests to the token endpoint result in the transmission of clear-text credentials (in the HTTP request and response), the authorization server MUST require the use of TLS" (3.2)
- The implicit grant was for in-browser JavaScript clients. "These clients are typically implemented in a browser using a scripting language such as JavaScript." (4.2)
