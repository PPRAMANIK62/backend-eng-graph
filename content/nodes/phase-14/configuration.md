# Configuration

Configuration is everything about a service that you change without
changing its code: the database address, a timeout, a rate limit, which
features are on. Keeping it out of the build lets one artifact run in
every environment. But a config change reaches production faster than
a code change and gets less review, which is why it causes so many
outages.

## What counts as config

A useful test: config is whatever differs between deploys of the same
code. The database host in staging and production, the credentials
for an external API, the public hostname. The twelve-factor rule is to
keep all of that strictly out of the code, so the same build runs
anywhere, and to check it with one question: could you open-source the
repository right now without leaking a single credential?

Wiring that's the same in every deploy, like which URL maps to which
handler, isn't config. It belongs in the code.

Twelve-factor stores config in environment variables, set per deploy
and never grouped into named "environments" that multiply as the team
grows. That works well for the handful of values a process reads at
startup. Credentials are a special case with their own problems
(rotation, access control, not leaking into logs), covered in
[[secrets-management]].

## Config that changes while the service runs

Big services have a second kind of config: values changed live, many
times a day, without a restart. Rate limits, traffic weights between
regions, cache sizes, which users see a new feature. When its paper
was written (2015), Facebook changed this kind of config thousands of
times a day, far more often than it deployed code (twice a day). Google
reads config that changes while a binary runs from an external store.

This is where the danger is. A code change goes through review, tests,
a staged rollout and a watched canary. A config change is "just a
number", so it's tempting to push it straight to every server. And
it's fast: Facebook's system got a committed change onto production
servers in about 14.5 seconds.

Cloudflare's worst outage since 2019 is the example to remember. A
database permissions change made a query return duplicate rows. That
query builds a feature file for the bot-detection module every five
minutes, and the file is pushed to every machine on purpose, quickly,
so it can react to new attacks. The file doubled in size. The proxy
had a hard limit of 200 features (it used about 60) and panicked when
the limit was hit. Because the query sometimes ran on updated
database nodes and sometimes on old ones, good and bad files
alternated every five minutes, which made it look like an attack.
The trigger wasn't a code deploy. The config was generated by a
machine, and the proxy didn't treat it as input that could be wrong.

## Treat a config change like a deploy

Facebook and Google landed on the same answer: config goes
through the same path as code.

- **In source control, with review.** Every Google scheme keeps config
  in the main repository with mandatory review. Facebook went from
  optional to mandatory review and testing for config changes.
- **Validated before it ships.** Facebook's config compiler runs
  validators that check invariants for each config type. Cloudflare's
  first follow-up was to check config files its own systems generate
  as carefully as user input.
- **Canaried.** Facebook's canary pushes a new config to 20 servers,
  then to a full cluster, and compares their health with servers still
  on the old config. It rolls back on its own. See
  [[canary-analysis]].

## Where it gets tricky

**Valid config can still break things.** Facebook looked at three
months of high-impact incidents and found 16% involved config. Of
those, 42% were ordinary mistakes, 36% subtle ones, and 22% were
perfectly valid changes that sent traffic down a code path with a
bug. In one case the canary rejected a change for crashing servers;
the engineer decided it was a false positive, overrode it, and caused
more crashes.

**Old code, new config.** When code and config schema change together,
they don't reach every server at the same moment. New code can usually
read old config; old code often can't read new config. One Facebook
config using a new schema reached servers before the code that could
read it, and only the canary stopped an outage. It's the same problem
as [[schema-evolution]], with config as the message.

**Small canaries miss load problems.** A Facebook config sent mobile
requests down a rare path that overloaded a data store. Twenty servers
didn't generate enough load to notice; the whole site did. They added
a cluster-sized canary stage.

**The checked-in file isn't what's running.** If config is edited in
the repository but only picked up on restart, the two drift apart.
Always be able to ask a running process which config it has.

## What this means when you build

- Keep per-deploy values (addresses, credentials) out of the build.
  One artifact, many environments.
- Give live config a schema and validate it before it leaves your
  hands, including config your own systems generate.
- Roll config out in stages with automatic rollback, like code.
- Fail safe on bad config: keep running on the last good version
  instead of crashing on the new one.
- Have a kill switch for anything you push globally and quickly.
  [[feature-flags|Feature flags]] are live config too, and need the
  same care.
