## Summary

The 2022 spec (STD 97) for what HTTP means, apart from how any one
version puts it on the wire: resources and representations, messages,
fields, methods and their properties (safe, idempotent, cacheable),
status codes, intermediaries, and the Connection header. HTTP/1.1,
HTTP/2 and HTTP/3 all share it. It obsoletes RFCs 7231 to 7235 and the
non-syntax parts of RFC 7230.

## Key claims

- All three major versions share these semantics. "All three major versions of HTTP rely on the semantics defined by this document." (1.2)
- The split is new: semantics and caching are separate from HTTP/1.1 syntax so versions evolve independently. "This revision of HTTP separates the definition of semantics (this document) and caching ([CACHING]) from the current HTTP/1.1 messaging syntax ([HTTP/1.1])" (1.2)
- History: HTTP since 1990; HTTP/1.1 introduced in 1995, standards track 1997, revised 1999 and 2014. "HTTP/1.1 was introduced in 1995 and published on the Standards Track in 1997 [RFC2068], revised in 1999 [RFC2616], and revised again in 2014 ([RFC7230] through [RFC7235])." (1.2)
- HTTP/1.1 brought chunked and length framing, validators, cache controls, ranges and default persistent connections. "This included length-based data delimiters for both fixed and dynamic (chunked) content" (1.2)
- The method carries the request's meaning, not the URI. "One design goal of HTTP is to separate resource identification from request semantics, which is made possible by vesting the request semantics in the request method" (3.1)
- A representation reflects a resource's state; you never transfer the resource itself. "A \"representation\" is information that is intended to reflect a past, current, or desired state of a given resource" (3.2)
- Stateless: each request can be understood alone. "HTTP is defined as a stateless protocol, meaning that each request message's semantics can be understood in isolation" (3.3)
- Two requests on one connection aren't necessarily from the same user agent. "a server MUST NOT assume that two requests on the same connection are from the same user agent unless the connection is secured and specific to that agent." (3.3)
- Intermediaries: proxy, gateway (reverse proxy), tunnel; a message through three intermediaries crosses four connections. "There are three common forms of HTTP \"intermediary\": proxy, gateway, and tunnel." (3.7)
- A gateway is a reverse proxy. "A \"gateway\" (a.k.a. \"reverse proxy\") is an intermediary that acts as an origin server for the outbound connection" (3.7)
- Field names are case-insensitive. "Field names are case-insensitive" (5.1)
- Proxies forward header fields they don't recognize; this is how HTTP extends. "A proxy MUST forward unrecognized header fields unless the field name is listed in the Connection header field" (5.1)
- Repeated field lines combine into one comma-separated list, in order. "its combined field value consists of the list of corresponding field line values within that section, concatenated in order, with each field line value separated by a comma." (5.2)
- Set-Cookie is the exception that can't be combined. "recipients ought to handle \"Set-Cookie\" as a special case while processing fields." (5.3)
- A server must wait for the whole header section before acting. "A server MUST NOT apply a request to the target resource until it receives the entire request header section" (5.3)
- No predefined limit on field length; oversize fields get a 4xx, not silently ignored. "A server that receives a request header field line, field value, or set of fields larger than it wishes to process MUST respond with an appropriate 4xx (Client Error) status code." (5.4)
- A message is control data, headers, content, trailers. "A \"message\" consists of the following:" (6)
- Each version defines its own framing. "Each major version of HTTP defines its own framing mechanism." (6.1)
- Close-delimited framing can't tell a complete response from a cut-off one. "However, implicit framing can fail to distinguish an incomplete response if the connection closes early." (6.1)
- Host carries the authority so one server can host many names. "enabling the origin server to distinguish among resources while servicing requests for multiple host names." (7.2)
- Connection lists hop-by-hop options; intermediaries remove the named fields before forwarding. "Intermediaries MUST parse a received Connection header field before a message is forwarded" (7.6.1)
- Hop-by-hop fields to remove include Keep-Alive, TE, Transfer-Encoding and Upgrade. "This includes but is not limited to:" (7.6.1)
- The method is the primary source of request semantics. "The request method token is the primary source of request semantics" (9.1)
- Only GET and HEAD are required. "All general-purpose servers MUST support the methods GET and HEAD." (9.1)
- Unknown method: 501; known but not allowed here: 405. "SHOULD respond with the 501 (Not Implemented) status code." (9.1)
- Safe means read-only by intent. "Request methods are considered \"safe\" if their defined semantics are essentially read-only" (9.2.1)
- Safe is about what the client asked for, not what the server does (logging is fine). "What is important, however, is that the client did not request that additional behavior and cannot be held accountable for it." (9.2.1)
- The safe methods. "Of the request methods defined by this specification, the GET, HEAD, OPTIONS, and TRACE methods are defined to be safe." (9.2.1)
- Actions in GET query parameters must be disabled for safe methods, because crawlers and prefetchers GET every link. "then the resource owner MUST disable or disallow that action when it is accessed using a safe request method." (9.2.1)
- Idempotent: repeating has the same intended effect as doing it once. "A request method is considered \"idempotent\" if the intended effect on the server of multiple identical requests with that method is the same as the effect for a single such request." (9.2.2)
- The idempotent methods. "Of the request methods defined by this specification, PUT, DELETE, and safe request methods are idempotent." (9.2.2)
- Idempotence is what allows automatic retry after a connection failure. "Idempotent methods are distinguished because the request can be repeated automatically if a communication failure occurs before the client is able to read the server's response." (9.2.2)
- The response to a retry may differ even though the effect is the same. "It knows that repeating the request will have the same intended effect, even if the original request succeeded, though the response might differ." (9.2.2)
- Don't retry non-idempotent requests automatically. "A client SHOULD NOT automatically retry a request with a non-idempotent method unless it has some means to know that the request semantics are actually idempotent" (9.2.2)
- Some clients guess, e.g. retrying POST on an idle persistent connection that closed. "a client might automatically retry a POST request if the underlying transport connection closed before any part of a response is received, particularly if an idle persistent connection was used." (9.2.2)
- Proxies must never retry non-idempotent requests. "A proxy MUST NOT automatically retry non-idempotent requests." (9.2.2)
- Caching: GET, HEAD and POST have caching semantics but most caches only do GET and HEAD. "although the overwhelming majority of cache implementations only support GET and HEAD." (9.2.3)
- A body on GET has no meaning and can be rejected as a smuggling risk. "content received in a GET request has no generally defined semantics, cannot alter the meaning or target of the request, and might lead some implementations to reject the request and close the connection because of its potential as a request smuggling attack" (9.3.1)
- POST: resource-specific processing; created resources get 201 with Location. "the origin server SHOULD send a 201 (Created) response containing a Location header field" (9.3.3)
- PUT creates or replaces the target's state. "The PUT method requests that the state of the target resource be created or replaced with the state defined by the representation enclosed in the request message content." (9.3.4)
- Status codes run 100 to 599; the first digit is the class. "The first digit of the status code defines the class of response." (15)
- Clients must understand the class and treat unknown codes as x00. "a client MUST understand the class of any status code, as indicated by the first digit, and treat an unrecognized status code as being equivalent to the x00 status code of that class." (15)
- Example: unknown 471 is handled as 400. "if a client receives an unrecognized status code of 471, it can see from the first digit that there was something wrong with its request and treat the response as if it had received a 400 (Bad Request) status code." (15)
- Zero or more 1xx interim responses, then exactly one final one. "zero or more \"interim\" (non-final) responses with status codes in the \"informational\" (1xx) range, followed by exactly one \"final\" response" (15)
- Reason phrases are only recommendations. "The reason phrases listed here are only recommendations" (15.1)
- 301 and 302 may turn POST into GET for historical reasons; 307 and 308 preserve the method. "Prevailing practice eventually converged on changing the method to GET." (15.4)
- 307 must not change the method. "the user agent MUST NOT change the request method if it performs an automatic redirection to that URI." (15.4.8)
- 401 means missing or bad credentials and must carry WWW-Authenticate. "The server generating a 401 response MUST send a WWW-Authenticate header field" (15.5.2)
- 403 means understood but refused; a server can answer 404 to hide the resource. "An origin server that wishes to \"hide\" the current existence of a forbidden target resource MAY instead respond with a status code of 404 (Not Found)." (15.5.4)
- 502: a gateway got an invalid response from upstream. "received an invalid response from an inbound server it accessed while attempting to fulfill the request." (15.6.3)
- 503: temporary overload, may carry Retry-After. "The server MAY send a Retry-After header field (Section 10.2.3) to suggest an appropriate amount of time for the client to wait before retrying the request." (15.6.4)
- 504: a gateway didn't get a timely response from upstream. "did not receive a timely response from an upstream server it needed to access in order to complete the request." (15.6.5)
- Upstream/downstream follow the message; inbound/outbound follow the request route. "inbound means \"toward the origin server\", whereas outbound means \"toward the user agent\"." (3.7)
- A gateway talks to the servers behind it with any protocol it likes. "A gateway communicates with inbound servers using any protocol that it desires" (3.7)
- Gateways exist for legacy services, "accelerator" caching and load balancing. "Gateways are often used to encapsulate legacy or untrusted information services, to improve server performance through \"accelerator\" caching, and to enable partitioning or load balancing of HTTP services across multiple machines." (3.7)
- Intermediaries forward protocol elements they don't recognise. "Intermediaries are expected to forward messages even when protocol elements are not recognized (e.g., new methods, status codes, or field names) since that preserves extensibility for downstream recipients." (7.6)
- An intermediary must not forward to itself in a loop. "An intermediary MUST NOT forward a message to itself unless it is protected from an infinite request loop." (7.6)
- Intermediaries may buffer instead of streaming, so partial delivery isn't guaranteed. "senders and recipients cannot rely on incremental delivery of partial messages, since some implementations will buffer or delay message forwarding for the sake of network efficiency, security checks, or content transformations." (7.6)
- Via: each intermediary appends how it received the message. "Each intermediary appends its own information about how the message was received, such that the end result is ordered according to the sequence of forwarding recipients." (7.6.3)
- A gateway must add Via to requests it forwards inbound. "An HTTP-to-HTTP gateway MUST send an appropriate Via header field in each inbound request message and MAY send a Via header field in forwarded response messages." (7.6.3)
- Via can hide internal host names behind pseudonyms. "if the real host is considered to be sensitive information, a sender MAY replace it with a pseudonym." (7.6.3)

Added for `http-semantics`:

- A message can be relayed through another HTTP version without changing its meaning. "such that a message in one version can be relayed through other versions without changing its meaning." (6)
- HTTP runs over a reliable connection. "HTTP is a client/server protocol that operates over a reliable transport- or session-layer \"connection\"." (3.3)
- Statelessness is what lets proxies reuse connections and balancers spread requests. "Many implementations depend on HTTP's stateless design in order to reuse proxied connections or dynamically load balance requests across multiple servers." (3.3)
- Host is a target for cache poisoning and misrouting. "it is a frequent target for malware seeking to poison a shared cache or redirect a request to an unintended server." (7.2)
- 301 and 302 were changed to allow POST to become GET. "status codes 301 and 302 have been adjusted to allow a POST request to be redirected as GET." (15.4)
- HTTP doesn't care what a resource is. "HTTP does not limit the nature of a resource; it merely defines an interface that might be used to interact with resources." (3.1)
- The method table: GET, HEAD, OPTIONS, DELETE. "Transfer a current representation of the target resource." / "Same as GET, but do not transfer the response content." / "Describe the communication options for the target resource." / "Remove all current representations of the target resource." (9.1, Table 4)
- Known method not allowed on this resource gets 405. "SHOULD respond with the 405 (Method Not Allowed) status code." (9.1)
- POST examples include form fields and appending data. "Appending data to a resource's existing representation(s)." (9.3.3)
- Safe methods exist so spiders and prefetchers can work without harm. "allow automated retrieval processes (spiders) and cache performance optimization (pre-fetching) to work without fear of causing harm." (9.2.1)
- Link checkers and indexers GET every link. "when automated processes perform a GET on every URI reference for the sake of link maintenance, pre-fetching, building a search index, etc." (9.2.1)
- Status codes run from 100 to 599. "All valid status codes are within the range of 100 to 599, inclusive." (15)
- The five classes. "2xx (Successful): The request was successfully received, understood, and accepted" / "3xx (Redirection): Further action needs to be taken in order to complete the request" / "5xx (Server Error): The server failed to fulfill an apparently valid request" (15)
- 301 is permanent. "the target resource has been assigned a new permanent URI" (15.4.2); 302 is temporary: "the target resource resides temporarily under a different URI." (15.4.3)
- 307 and 308 were added to keep the method. "307 (Temporary Redirect) and 308 (Permanent Redirect) [RFC7538] were later added to unambiguously indicate method-preserving redirects" (15.4)
- 503 covers overload or maintenance. "the server is currently unable to handle the request due to a temporary overload or scheduled maintenance" (15.6.4)
- Intermediaries drop Connection itself after the listed fields. "and then remove the Connection header field itself" (7.6.1)
- No size limit on fields; ignoring oversize ones invites smuggling. "HTTP does not place a predefined limit on the length of each field line" / "Ignoring such header fields would increase the server's vulnerability to request smuggling attacks" (5.4)

Added for `http-1-1`:

- A response can't be parsed without knowing the request (HEAD). "For example, responses to the HEAD method look just like the beginning of a response to GET but cannot be parsed in the same manner." (6)
- Upgrade switches an HTTP/1.1 connection to another protocol. "The \"Upgrade\" header field is intended to provide a simple mechanism for transitioning from HTTP/1.1 to some other protocol on the same connection." (7.8)
- The switch is confirmed with 101 and an Upgrade header. "A server that sends a 101 (Switching Protocols) response MUST send an Upgrade header field to indicate the new protocol(s) to which the connection is being switched" (7.8)
- The spec's hypothetical example asks for websocket. "Upgrade: websocket, IRC/6.9, RTA/x11" (7.8)

Added for `http-caching`:

- A method must define caching to be cacheable. "a method definition that does not do so cannot be cached." (9.2.3)
- POST responses are cacheable only with explicit freshness and a matching Content-Location, and only for later GET/HEAD. "Responses to POST requests are only cacheable when they include explicit freshness information" (9.3.3)
- Heuristically cacheable status codes. "(e.g., 200, 203, 204, 206, 300, 301, 308, 404, 405, 410, 414, and 501 in this specification)" (15.1)
- A strong validator changes whenever the content would change. "A \"strong validator\" is representation metadata that changes value whenever a change occurs to the representation data that would be observable in the content of a 200 (OK) response to GET." (8.8.1)
- A hash of the content is a sufficient strong validator. "A collision-resistant hash function applied to the representation data is also sufficient" (8.8.1)
- Weak validators may not change for every change. "a \"weak validator\" is representation metadata that might not change for every change to the representation data." (8.8.1)
- A one-second modification time can be weak. "a representation's modification time, if defined with only one-second resolution, might be a weak validator if it is possible for the representation to be modified twice during a single second" (8.8.1)
- Same validator for gzip and uncompressed means it's weak. "if the origin server sends the same validator for a representation with a gzip content coding applied as it does for a representation with no content coding, then that validator is weak." (8.8.1)
- Weak validators are fine for cache validation. "Weak validators are only usable when the client does not require exact equality with previously obtained representation data, such as when validating a cache entry" (8.8.1)
- An ETag is an opaque quoted string, weak if prefixed W/. "An entity tag consists of an opaque quoted string, possibly prefixed by a weakness indicator." (8.8.3)
- ETags beat dates when one-second resolution isn't enough. "where the one-second resolution of HTTP-date values is not sufficient" (8.8.3)
- Servers should send an ETag when they can. "An origin server SHOULD send an ETag for any selected representation for which detection of changes can be reasonably and consistently determined" (8.8.3.1)
- If-None-Match uses weak comparison. "A recipient MUST use the weak comparison function when comparing entity tags for If-None-Match" (13.1.2)
- If-None-Match false on GET/HEAD gives 304. "the origin server MUST respond with either a) the 304 (Not Modified) status code if the request method is GET or HEAD" (13.1.2)
- If-Modified-Since is ignored when If-None-Match is present. "A recipient MUST ignore If-Modified-Since if the request contains an If-None-Match header field" (13.1.3)
- 304 means: use the copy you already have. "the server is therefore redirecting the client to make use of that stored representation as if it were the content of a 200 (OK) response." (15.4.5)
- A 304 must carry the headers a 200 would have had for caching. "Content-Location, Date, ETag, and Vary" (15.4.5)
- A 304 has no content. "A 304 response is terminated by the end of the header section; it cannot contain content or trailers." (15.4.5)
- Vary lists the request headers that selected the response. "The \"Vary\" header field in a response describes what parts of a request message, aside from the method and target URI, might have influenced the origin server's process for selecting the content of this response." (12.5.5)
- Vary expands the cache key. "In other words, Vary expands the cache key required to match a new request to the stored cache entry." (12.5.5)

Added for `conditional-requests`, `error-design` and `long-running-operations`:

- Conditionals on writes prevent lost updates. "Conditionals can also be applied to state-changing methods, such as PUT and DELETE, to prevent the \"lost update\" problem: one client accidentally overwriting the work of another client that has been acting in parallel." (13)
- If-Match uses strong comparison. "An origin server MUST use the strong comparison function when comparing entity tags for If-Match (Section 8.8.3.2), since the client intends this precondition to prevent the method from being applied if there have been any changes to the representation data." (13.1.1)
- If-Match takes `*`, one tag, or a list. "If-Match: \"xyzzy\", \"r2d2xxxx\", \"c3piozzzz\"" (13.1.1)
- A false If-Match stops the method. "An origin server that evaluates an If-Match condition MUST NOT perform the requested method if the condition evaluates to false." (13.1.1)
- The server may send 412, or 2xx if the change already seems applied (a lost response, or someone else made the same change). "Instead, the origin server MAY indicate that the conditional request failed by responding with a 412 (Precondition Failed) status code." (13.1.1)
- That 2xx shortcut is risky for resources used as a semaphore; strict 412 is better there. "For those kinds of resources, an origin server is better off being stringent in sending 412 for every failed precondition on an unsafe method." (13.1.1)
- Caches and intermediaries may ignore If-Match. "A cache or intermediary MAY ignore If-Match because its interoperability features are only necessary for an origin server." (13.1.1)
- `If-None-Match: *` stops a PUT from overwriting a resource the client thought didn't exist. "If-None-Match can also be used with a value of \"*\" to prevent an unsafe request method (e.g., PUT) from inadvertently modifying an existing representation of the target resource when the client believes that the resource does not have a current representation" (13.1.2)
- If-None-Match false on other methods gives 412. "b) the 412 (Precondition Failed) status code for all other request methods." (13.1.2)
- If-Unmodified-Since is the date-based version, ignored when If-Match is present. "This field accomplishes the same purpose as If-Match for cases where the user agent does not have an entity tag for the representation." (13.1.4)
- Preconditions are checked after normal request checks, just before the method runs. "a recipient cache or origin server MUST evaluate received request preconditions after it has successfully performed its normal request checks and just before it would process the request content (if any) or perform the action associated with the request method." (13.2.1)
- A server that isn't the origin must forward them, not evaluate them. "it MUST forward them if the request is forwarded, since the generating client intends that they be evaluated by a server that can provide a current representation." (13.2.1)
- Evaluation order: If-Match, then If-Unmodified-Since, then If-None-Match, then If-Modified-Since, then If-Range. (13.2.2)
- Strong comparison: both tags not weak and equal. "\"Strong comparison\": two entity tags are equivalent if both are not weak and their opaque-tags match character-by-character." (8.8.3.2)
- 412 lets the client refuse to act on an unexpected state. "This response status code allows the client to place preconditions on the current resource state (its current representations and metadata) and, thus, prevent the request method from being applied if the target resource is in an unexpected state." (15.5.13)
- 409 is for conflicts the user may be able to resolve and resubmit. "This code is used in situations where the user might be able to resolve the conflict and resubmit the request." (15.5.10)
- 422: syntax fine, content can't be processed. "the syntax of the request content is correct, but it was unable to process the contained instructions." (15.5.21)
- 4xx means the client seems to have erred, and the body should say if it's temporary or permanent. "the server SHOULD send a representation containing an explanation of the error situation, and whether it is a temporary or permanent condition." (15.5)
- 5xx: the server erred or can't do it; same advice about temporary or permanent. "The 5xx (Server Error) class of status code indicates that the server is aware that it has erred or is incapable of performing the requested method." (15.6)
- Retry-After says how long to wait, as a date or seconds. "Servers send the \"Retry-After\" header field to indicate how long the user agent ought to wait before making a follow-up request." (10.2.3)
- Retry-After value forms. "The Retry-After field value can be either an HTTP-date or a number of seconds to delay after receiving the response." (10.2.3)
- 202: accepted, not done, and might still fail. "The request might or might not eventually be acted upon, as it might be disallowed when processing actually takes place." (15.3.3)
- HTTP can't deliver the final status later. "There is no facility in HTTP for re-sending a status code from an asynchronous operation." (15.3.3)
- 202 is noncommittal on purpose, so the connection needn't stay open. "The 202 response is intentionally noncommittal." (15.3.3)
- The 202 body should point to a status monitor. "The representation sent with this response ought to describe the request's current status and point to (or embed) a status monitor that can provide the user with an estimate of when the request will be fulfilled." (15.3.3)
- `If-Match: *` is true only if the resource currently exists. "If the field value is \"*\", the condition is true if the origin server has a current representation for the target resource." (13.1.1)
- The 2xx-if-already-applied shortcut is risky when several clients make similar but uncoordinated changes. "comes with some risk if multiple user agents are making change requests that are very similar but not cooperative." (13.1.1)
