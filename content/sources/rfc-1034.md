## Summary

The 1987 spec that defines what DNS is: a tree of names, resource
records attached to the names, name servers that are authoritative for
zones, and resolvers that ask them. It explains recursive and
non-recursive (iterative) service, referrals, stub resolvers, the TTL,
CNAME aliases and optional negative caching. Still the base document;
many later RFCs update it (2181, 2308, 8767 among them).

## Key claims

- DNS has three parts: the name space and resource records, name servers, and resolvers. "The DNS has three major components:" (2.4)
- A name server has complete information for part of the tree, and pointers to other servers for the rest. "in general a particular name server has complete information about a subset of the domain space, and pointers to other name servers that can be used to lead to information from any part of the domain tree." (2.4)
- Authoritative data is organized into zones. "Authoritative information is organized into units called ZONEs" (2.4)
- A resolver is usually a system routine the program calls, with no protocol between them. "A resolver will typically be a system routine that is directly accessible to user programs; hence no protocol is necessary between the resolver and the user program." (2.4)
- The name space is a tree; each label is 0 to 63 octets; the root has the empty label. "Each node has a label, which is zero to 63 octets in length." (3.1)
- A domain name is the list of labels from a node up to the root, written most specific first. "The domain name of a node is the list of the labels on the path from the node to the root of the tree." (3.1)
- A complete (absolute) name ends in a dot, for the root; a name without it is relative and gets completed by local software, often from a search list. "Since a complete domain name ends with the root label, this leads to a printed form which ends in a dot." (3.1)
- The TTL is in seconds and says how long a cache may keep a record. "The TTL describes how long a RR can be cached before it should be discarded." (3.6)
- The zone's administrator sets the TTL; zero means don't cache; lower it before a planned change. "If a change can be anticipated, the TTL can be reduced prior to the change to minimize inconsistency during the change, and then increased back to its former value following the change." (3.6)
- In 1987 the advice was TTLs of days. "the realities of Internet performance suggest that these times should be on the order of days for the typical host." (3.6)
- A cached answer carries a smaller TTL than the authoritative one, because it has aged in the cache; cached answers also lack the AA bit. "The difference between the authoritative TTL and the TTL here is due to aging of the data in a cache." (6.2.1)
- A name with a CNAME holds no other data, so a cached CNAME can be trusted for every type. "If a CNAME RR is present at a node, no other data should be present" (3.6.2)
- In the Internet, queries go in UDP datagrams or over TCP. "In the Internet, queries are carried in UDP datagrams or over TCP connections." (4.3.1)
- A non-recursive answer is an error, the answer, or a referral to a closer server; every server must support this. "All name servers must implement non-recursive queries." (4.3.1)
- In recursive mode the server does the chasing and never returns referrals; this is optional and servers may restrict who gets it. "in this mode the name server acts in the role of a resolver and returns either an error or the answer, but never referrals." (4.3.1)
- One reason for recursive service is a shared cache. "a network where we want to concentrate the cache rather than having a separate cache for each client." (4.3.1)
- Recursion is asked for with the RD bit and offered with the RA bit. "The recursive mode occurs when a query with RD set arrives at a server which is willing to provide recursive service" (4.3.1)
- Negative results can be cached with a TTL (optional in 1987). "a resolver receiving such information is allowed to assume that the name does not exist during the TTL period without consulting authoritative data." (4.3.4)
- A stub resolver hands resolution to a recursive server and only needs a list of server addresses. "All that the remaining stub needs is a list of name server addresses that will perform the recursive requests." (5.3.1)
- A resolver with no idea where to start uses a configured list, usually including root servers, which lead to the whole tree. "The root servers will provide eventual access to all of the domain space." (5.3.3, SBELT)
- Glue: a name server named below the cut needs address records in the parent, or you'd need the server's address to learn the server's address. (4.2.1, quoted in RFC 9499 "Glue records")
