## Summary

How to open a WebSocket inside one HTTP/2 stream (2018). HTTP/2 has no
Upgrade header or 101 response, so the client sends an "extended
CONNECT" request with a `:protocol` pseudo-header after the server has
enabled it in SETTINGS. The stream then carries ordinary WebSocket
frames.

## Key claims

- HTTP/2 can't use the RFC 6455 handshake. "Due to its multiplexing nature, HTTP/2 does not allow connection-wide header fields or status codes, such as the Upgrade and Connection request-header fields or the 101 (Switching Protocols) response code." (1)
- One TCP connection can then carry both HTTP/2 and WebSockets. "Being able to bootstrap WebSockets from HTTP/2 allows one TCP connection to be shared by both protocols" (1)
- The result is a tunnel on a single stream. "The result is a tunnel on a single HTTP/2 stream that can carry data for WebSockets (or any other protocol)." (1)
- The stream behaves like the TCP connection in RFC 6455. "treating the stream as if it were the TCP connection in that specification." (1)
- The server opts in with a setting. "Upon receipt of SETTINGS_ENABLE_CONNECT_PROTOCOL with a value of 1, a client MAY use the Extended CONNECT as defined in this document when creating new streams." (3)
- The `:protocol` value is "websocket". "it MUST have a value of "websocket" to initiate a WebSocket connection on an HTTP/2 stream." (5)
