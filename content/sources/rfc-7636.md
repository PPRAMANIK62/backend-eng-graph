## Summary

PKCE (2015). Public clients like mobile apps can't keep a client
secret, so a stolen authorization code could be redeemed by an attacker.
PKCE has the client make a random secret per request, send a hash of it
with the authorization request, and send the secret itself when it
redeems the code. Only whoever started the flow can finish it.

## Key claims

- Public clients are exposed to code interception. "OAuth 2.0 public clients utilizing the Authorization Code Grant are susceptible to the authorization code interception attack." (Abstract)
- The attack: a malicious app registers the same custom URI scheme and receives the code. "it is possible for a malicious app to register itself as a handler for the custom scheme in addition to the legitimate OAuth 2.0 app." (1)
- With the code in hand the attacker gets an access token. "Once the attacker has gained access to the authorization code, it can use it to obtain the access token." (1)
- The code verifier: a high-entropy random string of 43 to 128 characters. "with a minimum length of 43 characters and a maximum length of 128 characters." (4.1)
- Recommended: 32 random bytes, base64url-encoded. "It is RECOMMENDED that the output of a suitable random number generator be used to create a 32-octet sequence." (4.1)
- S256 challenge is the base64url of the SHA-256 of the verifier. "code_challenge = BASE64URL-ENCODE(SHA256(ASCII(code_verifier)))" (4.2)
- Clients that can do S256 must use it. "If the client is capable of using \"S256\", it MUST use \"S256\", as \"S256\" is Mandatory To Implement (MTI) on the server." (4.2)
- The server recomputes the challenge from the verifier at the token endpoint. "BASE64URL-ENCODE(SHA256(ASCII(code_verifier))) == code_challenge" (4.6)
- Everything rests on the verifier staying secret and unguessable. "The security model relies on the fact that the code verifier is not learned or guessed by the attacker." (7.1)
- No downgrading to plain. "Clients MUST NOT downgrade to \"plain\" after trying the \"S256\" method." (7.2)
- Custom URI schemes are the typical redirect for native apps. "The Redirection Endpoint URI in this case typically uses a custom URI scheme." (1)
- The name is pronounced "pixy". "(PKCE, pronounced \"pixy\")" (Abstract)
- 32 random bytes, base64url-encoded, give 43 characters. "The octet sequence is then base64url-encoded to produce a 43-octet URL safe string to use as the code verifier." (4.1)
- plain only when S256 is impossible. "Clients are permitted to use \"plain\" only if they cannot support \"S256\" for some technical reason" (4.2)
