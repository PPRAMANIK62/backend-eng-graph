## Summary

The current TLS 1.3 specification, published in 2026. It obsoletes RFC
8446 (2018), which first defined TLS 1.3, and also obsoletes RFC 5246
(TLS 1.2). It keeps the same version number and wire format and tightens
some rules. Covers the full handshake, resumption with pre-shared keys,
0-RTT data and its replay risks, the record layer, client
authentication, and what implementations must support.

## Key claims

- TLS needs only a reliable, in-order stream underneath and gives a secure channel. "the only requirement from the underlying transport is a reliable, in-order data stream." (1)
- The promises hold against an attacker who controls the network. "These properties should be true even in the face of an attacker who has complete control of the network" (1)
- The server is always authenticated, the client optionally. "The server side of the channel is always authenticated; the client side is optionally authenticated." (1)
- TLS does not hide how much data is sent. "TLS does not hide the length of the data it transmits" (1)
- Two parts: a handshake protocol and a record protocol that protects traffic in records. "The record protocol divides traffic up into a series of records, each of which is independently protected using the traffic keys." (1)
- An attacker should not be able to push the two sides into weaker parameters. "an active attacker should not be able to force the peers to negotiate different parameters than they would if the connection were not under attack." (1)
- It is a minor, backward-compatible update of RFC 8446. "This document is a minor update to TLS 1.3 that retains the same version number and is backward compatible." (1.2)
- It forbids TLS 1.0 and 1.1 and reusing key shares between connections. "Forbid negotiating TLS 1.0 and 1.1 as they are now deprecated by [RFC8996]." and "Forbid the reuse of KeyShare values between connections." (1.2)
- The word "master" for secrets is replaced by "main". "it removes the use of the term \"master\" as applied to secrets in favor of the term \"main\"" (1.2)
- Key exchange text is now generic, to cover KEM-based (post-quantum) exchange. "to reflect the use of KEM-based key exchange." (1.2)
- Only AEAD ciphers remain in TLS 1.3. "Those that remain are all Authenticated Encryption with Associated Data (AEAD) algorithms." (1.3)
- Static RSA and DH are gone; all key exchange is forward secret. "all public-key based key exchange mechanisms now provide forward secrecy." (1.3)
- Everything after the ServerHello is encrypted. "All handshake messages after the ServerHello are now encrypted." (1.3)
- 0-RTT saves a round trip at a cost. "saving a round trip at connection setup for some application data, at the cost of certain security properties." (1.3)
- Session IDs and tickets from TLS 1.2 are replaced by one PSK mechanism. "Session resumption with and without server-side state as well as the PSK-based cipher suites of earlier TLS versions have been replaced by a single new PSK exchange." (1.3)
- The handshake has three phases; everything after key exchange is encrypted. "Key Exchange: Establish shared keying material and select the cryptographic parameters.  Everything after this phase is encrypted." (2)
- ClientHello carries a random nonce, versions, cipher/hash pairs and key shares or PSK labels. "which contains a random nonce (ClientHello.random); its offered protocol versions; a list of symmetric cipher/hash pairs" (2)
- CertificateVerify is a signature over the whole handshake. "A signature over the entire handshake using the private key corresponding to the public key in the Certificate message." (2)
- Finished is a MAC over the whole handshake and binds identity to keys. "This message provides key confirmation for the shared secrets established in the handshake, binds the endpoint's identity to the exchanged keys" (2)
- A server may send data before the client finishes, but to an unauthenticated peer. "any data sent at that point is, of course, being sent to an unauthenticated peer." (2)
- If the client guessed the wrong key share group, the server sends HelloRetryRequest and the client starts over. "the server corrects the mismatch with a HelloRetryRequest and the client needs to restart the handshake" (2.1)
- A server can give the client a PSK identity after the handshake for resuming later. "Once a handshake has completed, the server can send the client a PSK identity that corresponds to a unique key derived from the initial handshake" (2.2)
- TLS 1.2's session IDs and session tickets are obsolete in TLS 1.3. "In TLS 1.2 and below, this functionality was provided by \"session IDs\" and \"session tickets\" [RFC5077].  Both mechanisms are obsoleted in TLS 1.3." (2.2)
- PSK resumption can be combined with a fresh key exchange for forward secrecy, or used alone without it. "PSKs can be used with asymmetric key exchange to provide forward secrecy in combination with shared keys, or can be used alone, at the cost of losing forward secrecy for the application data." (2.2)
- On resumption the server authenticates by the PSK and sends no certificate. "As the server is authenticating via a PSK, it does not send a Certificate or a CertificateVerify message." (2.2)
- A PSK derived from a password is open to offline guessing. "Deriving a shared secret from a password or other low-entropy sources is not secure." (2.2)
- With a PSK the client can send data in its first flight (early data). "TLS 1.3 allows clients to send data on the first flight (\"early data\")." (2.3)
- 0-RTT data has weaker security. "The security properties for 0-RTT data are weaker than those for other kinds of TLS data." (2.3)
- 0-RTT data is not forward secret by default. "the client should assume that this data is not forward secret." (2.3)
- 0-RTT data can be replayed across connections. "There are no guarantees of non-replay between connections." (2.3)
- The server may ask the client for a certificate with CertificateRequest. "A server which is authenticating with a certificate MAY optionally request a certificate from the client." (4.4.2)
- CertificateRequest comes right after EncryptedExtensions. "This message, if sent, MUST follow EncryptedExtensions." (4.4.2)
- A server resuming with a PSK must not ask for a client certificate in the main handshake. "Servers which are authenticating with a resumption PSK MUST NOT send the CertificateRequest message in the main handshake" (4.4.2)
- Certificate validation details are left to RFC 5280. "In general, detailed certificate validation procedures are out of scope for TLS (see [RFC5280])." (4.5.1.3)
- If the client sends no certificate, the server can carry on or abort. "the server MAY at its discretion either continue the handshake without client authentication, or abort the handshake with a \"certificate_required\" alert." (4.5.1.3)
- The same choice applies to a client chain the server doesn't accept. "if some aspect of the certificate chain was unacceptable (e.g., it was not signed by a known, trusted CA), the server MAY at its discretion either continue the handshake (considering the client unauthenticated) or" (4.5.1.3)
- SHA-1 in certificate signatures is deprecated. "SHA-1 is deprecated and it is RECOMMENDED that any endpoint receiving any certificate which it would need to validate using any signature algorithm using a SHA-1 hash abort the handshake" (4.5.1.3)
- The signature covers a hash of the handshake transcript. "The content that is covered under the signature is the hash output as described in Section 4.1, namely:" (4.5.2)
- CertificateVerify proves possession of the private key. "This message is used to provide explicit proof that an endpoint possesses the private key corresponding to its certificate." (4.5.2)
- Tickets live at most 7 days. "Servers MUST NOT use any value greater than 604800 seconds (7 days)." (4.7.1)
- Clients only resume if the new SNI fits the original certificate. "Clients MUST only resume if the new SNI value is valid for the server certificate presented in the original session" (4.7.1)
- Servers may send several tickets, e.g. for parallel connections. "Servers MAY send multiple tickets on a single connection" (4.7.1)
- Post-handshake client authentication: the server can ask for a certificate later. "a server MAY request certificate-based client authentication at any time after the handshake has completed by sending a CertificateRequest message." (4.7.2)
- Each record's nonce is built from a 64-bit sequence number XORed with a per-direction IV. "The padded sequence number is XORed with either the static client_write_iv or server_write_iv (depending on the role)." (5.3)
- Records can be padded to hide their size. "This allows the sender to hide the size of the traffic from an observer." (5.4)
- AES-GCM keys must be rotated before about 24 million full-size records. "For AES-GCM, up to 2^24.5 full-size records (about 24 million) may be encrypted under a given set of keys" (5.5)
- TLS itself gives no replay protection for 0-RTT data. "TLS does not provide inherent replay protections for 0-RTT data." (8)
- Clients must only send replay-safe data as early data. "clients will not know which, if any, of these mechanisms servers actually implement and hence MUST only send early data which they deem safe to be replayed." (8)
- Each server instance must accept a given 0-RTT handshake at most once. "The server MUST ensure that any instance of it (be it a machine, a thread, or any other entity within the relevant serving infrastructure) would accept 0-RTT for the same 0-RTT handshake at most once" (8)
- Replays caused by client retries can't be stopped in TLS; the application must handle them. "The second class of attack cannot be prevented at the TLS layer and MUST be dealt with by any application" (8)
- Tickets can be database keys instead of self-contained. "If the tickets are not self-contained but rather are database keys, and the corresponding PSKs are deleted upon use" (8.1)
- Early data doesn't depend on the ServerHello, so it has weaker replay protection. "0-RTT data does not depend on the ServerHello and therefore has weaker guarantees." (2.3)
- Within one connection early data isn't processed twice and can't pass as 1-RTT data. "0-RTT data cannot be duplicated within a connection" and "an attacker will not be able to make 0-RTT data appear to be 1-RTT data" (2.3)
- One authoritative storage zone per ticket gives the best protection. "the best anti-replay protection is provided by having a single storage zone be authoritative for a given ticket and refusing 0-RTT for that ticket in any other zone." (8.2)
- Servers should hand out a new ticket on every connection. "Servers SHOULD issue new tickets with every connection." (C.4)
- Simplest anti-replay: single-use tickets. "The simplest form of anti-replay defense is for the server to only allow each session ticket to be used once." (8.1)
- Single-use tickets need a session database shared across servers. "this mechanism requires sharing the session database between server nodes in environments with multiple distributed servers" (8.1)
- Freshness windows on the internet are on the order of ten seconds. "For clients on the Internet, this implies windows on the order of ten seconds to account for errors in clocks and variations in measurements" (8.3)
- Mandatory cipher suite and key exchange. "A TLS-compliant application MUST implement the TLS_AES_128_GCM_SHA256 [GCM] cipher suite and SHOULD implement the TLS_AES_256_GCM_SHA384 [GCM] and TLS_CHACHA20_POLY1305_SHA256 [RFC8439] cipher suites" and "MUST support key exchange with secp256r1 (NIST P-256) and SHOULD support key exchange with X25519 [RFC7748]." (9.1)
- SNI is mandatory to implement. "Server Name Indication (\"server_name\"; Section 3 of [RFC6066])" (9.2)
- Weak keys are not appropriate. "certification paths containing keys or signatures weaker than 2048-bit RSA or 224-bit ECDSA are not appropriate for secure applications." (C.2)
- Using one certificate as both client and server hasn't been analyzed much. "This setting has not been extensively analyzed" (C.2)
- The client's certificate is sent encrypted. "unlike the client's Certificate, which is encrypted" (C.4)
- Clients shouldn't reuse a ticket, since it links connections. "Reuse of a ticket allows passive observers to correlate different connections." (C.4)
- EncryptedExtensions carries extensions that used to go in the clear in ServerHello. "The newly introduced EncryptedExtensions message allows various extensions previously sent in the clear in the ServerHello to also enjoy confidentiality protection." (1.3)
- EncryptedExtensions holds the server's extensions that don't set up keys, such as ALPN (the extension table lists application_layer_protocol_negotiation under "CH, EE"). "The EncryptedExtensions message contains extensions that can be protected, i.e., any which are not needed to establish the cryptographic context" (4.4.1, 4.2)
- Freshness: the client reports its view of the ticket's age (obfuscated) in the pre_shared_key extension, and the server compares the expected arrival time with its clock. "The server can determine the client's view of the age of the ticket by subtracting the ticket's \"ticket_age_add\" value from the \"obfuscated_ticket_age\" parameter in the client's \"pre_shared_key\" extension." (8.3)
- CertificateRequest names the signature algorithms and, optionally, the CAs the server accepts. "In TLS 1.3, the former is expressed by sending the \"signature_algorithms\" and optionally \"signature_algorithms_cert\" extensions.  The latter is expressed by sending the \"certificate_authorities\" extension" (4.4.2)
- A resumed connection is tied to the original one, whose keys were most likely tied to the peer's certificate. "the security context of the new connection is cryptographically tied to the original connection" (2.2) and "an initial non-PSK handshake (which was most likely tied to the peer's certificate)" (4.6.1)
- Using the same certificate as client and server is common and not well analyzed. "Note that it is common practice in some protocols to use the same certificate in both client and server modes." (C.2)
- Record sequence numbers start at zero and go up by one per record. "Each sequence number is set to zero at the beginning of a connection and whenever the key is changed" (5.3)
- The record layer rejects replayed and skipped records. "An attacker should not be able to cause the receiver to accept a record which it has already accepted or cause the receiver to accept record N+1 without having first processed record N." (F.2)
- Compatibility mode: a non-empty legacy session ID and dummy change_cipher_spec records. "The client always provides a non-empty session ID in the ClientHello" and "The server sends a dummy change_cipher_spec record immediately after its first handshake message." (E.4)
- Many middleboxes broke on TLS 1.3, so it can be made to look like TLS 1.2 resumption. "a significant number of middleboxes misbehave when a TLS client/server pair negotiates TLS 1.3." (E.4)
