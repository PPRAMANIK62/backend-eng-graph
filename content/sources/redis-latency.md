## Summary

Redis's guide to latency sources: slow commands, fork, transparent huge
pages, swapping, AOF and fsync, expires. The THP and fork sections show
how a memory setting turns into request latency for a database that
forks to persist. Living doc, undated.

## Key claims

- The checklist says THP must be disabled. "Transparent huge pages must be disabled from your kernel." (checklist, item 3)
- Fork copies the page table: on Linux/AMD64 with 4 kB pages a 24 GB instance has a 48 MB page table. "So a large 24 GB Redis instance requires a page table of 24 GB / 4 kB * 8 = 48 MB." (Latency generated by fork)
- Redis forks to write the RDB snapshot or rewrite the AOF in the background. "In order to generate the RDB file in background, or to rewrite the Append Only File if AOF persistence is enabled, Redis has to fork background processes." (Latency generated by fork)
- In a busy instance, a few event-loop runs after the fork write to a few thousand pages. "In a busy instance, a few event loops runs will cause commands to target a few thousand of pages" (Latency induced by transparent huge pages)
- The fix is setting THP to never. "echo never > /sys/kernel/mm/transparent_hugepage/enabled" (Latency induced by transparent huge pages)
- With THP on, after fork the parent and child share huge pages, and writes then copy almost the whole memory. "causing the copy on write of almost the whole process memory." (Latency induced by transparent huge pages)
- The result is high latency and high memory use. "This will result in big latency and big memory usage." (Latency induced by transparent huge pages)
- Swapped-out pages stop the process while the kernel reads them back. "the kernel will stop the Redis process in order to move the page back into the main memory." (Latency induced by swapping)
- One thread serves every request, one at a time, using multiplexing. "Redis can serve a single request in every given moment, so all the requests are served sequentially." (Single threaded nature of Redis)
- It stays fast because commands are short and it never blocks on socket system calls. "primarily because these products are designed to not block on system calls, such as reading data from or writing data to a socket." (Single threaded nature of Redis)
- Since 2.4 some slow disk I/O runs on background threads. "from Redis 2.4 we use threads in Redis in order to perform some slow I/O operations in the background, mainly related to disk I/O" (Single threaded nature of Redis)
- One slow command makes every other client wait. "when a request is slow to serve all the other clients will wait for this request to be served." (Latency generated by slow commands)
- KEYS in production is a very common cause; use SCAN (2.8+). "a VERY common source of latency generated by the execution of slow commands is the use of the KEYS command in production environments." (Latency generated by slow commands)
- The fork itself runs in the main thread. "The fork operation (running in the main thread) can induce latency by itself." (Latency generated by fork)
- Measured fork times from INFO latest_fork_usec, for example 6.9 GB RSS in 62 ms on a physical Xeon at 2.27 GHz, and 6.1 GB in 1460 ms on old Xen EC2 instances. "Linux running on physical machine (Xeon @ 2.27Ghz) 6.9GB RSS forked into 62 milliseconds (9 milliseconds per GB)." (Fork time in different systems)
- The AOF uses write(2) and fdatasync(2), and both can add latency. "Both the write(2) and fdatasync(2) calls can be source of latency." (Latency due to AOF and disk I/O)
- fdatasync can take milliseconds to seconds, so Redis runs it on another thread since 2.4. "it can take from a few milliseconds to a few seconds to complete, especially in the case of some other process doing I/O." (Latency due to AOF and disk I/O)
- With everysec, if fsync is still running, Redis delays the write up to two seconds, then writes anyway. "if the fsync is still in progress Redis uses a buffer to delay the write(2) call up to two seconds" (Latency due to AOF and disk I/O)
- With always, the fsync happens before the reply. "a fsync is performed at every write operation before replying back to the client with an OK code" (Latency due to AOF and disk I/O)
- Expiry is lazy (on access) plus active: 10 times a second it samples 20 keys and repeats while more than 25% were expired. "An expire cycle is started every 100 milliseconds (10 times per second)" (Latency generated by expires)
- Many keys expiring in the same second can block the server. "be aware that many keys expiring at the same moment can be a source of latency." (Latency generated by expires)
- Commands that touch many elements (SORT, LREM, SUNION) are the slow ones; complexity is documented for every command. "The algorithmic complexity of all commands is documented." (Latency generated by slow commands)
- Mass expiry in one second happens when EXPIREAT is used with one timestamp. "it is not impossible that the user used EXPIREAT extensively with the same Unix time." (Latency generated by expires)
