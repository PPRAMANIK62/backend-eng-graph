## Summary

BCP 126: best current practice for running a service over anycast, in an
IGP or across the Internet with BGP. What anycast is good for, which
services suit it, and the operational traps (health-driven
announcements, covering prefixes, monitoring).

## Key claims

- How it works: one stable set of addresses, announced from many independent nodes. "reachability to those addresses is advertised in a routing system from multiple, independent service nodes." (1)
- Popular for DNS, including root servers. "Several root DNS server operators have distributed their servers widely around the Internet" (1)
- The routing system picks the node, based on topology and where the request starts. "The routing system decides which node is used for each request, based on the topological design of the routing system and the point in the network at which the request originates." (3.1)
- Load between nodes is usually unbalanced. "Load-balancing between Anycast Nodes is typically difficult to achieve" (3.1)
- Goals include coarse load spreading, containing DoS attacks to one node or region, and shorter response time. (3.2, list items 1 to 5)
- Nearest in routing terms isn't the same as fastest. "Topological nearness within the routing system does not, in general, correlate to round-trip performance across a network" (3.2, item 5)
- Routing must stay stable for longer than one transaction. "the routing system's node selection decision ought to be stable for substantially longer than the expected transaction time" (4.1)
- DNS over UDP (one packet each way) suits anycast; long downloads are harder. (4.1)
- Long flows have odd failure modes. "especially for long running flows, there are potential failure modes using anycast that are more complex than a simple 'destination unreachable' failure using unicast." (4.1)
- Tie the route to health: announce while the service works, withdraw when it doesn't. "availability of the service triggers the route advertisement, and non-availability of the service triggers a route withdrawal." (4.4.1)
- Avoid fast announce/withdraw oscillation. "Rapid advertisement/withdrawal oscillations can cause operational problems" (4.4.1)
- On the Internet you announce a covering prefix, often a /24 for IPv4, because host routes get filtered. "For IPv4 Service Addresses, this is often a 24-bit prefix" (4.4.2)
- Monitor from many places, and record which node answered. "the identity of the node answering individual requests is recorded along with performance and availability statistics." (5.1)

Added 2026-09-28 (audit) for `anycast`:

- Damp flapping with a minimum delay after a withdrawal. "nodes should be configured such that rapid oscillations are avoided (e.g., by implementing a minimum delay following a withdrawal before the service can be re-advertised)." (4.4.1)
- Host routes don't propagate reliably on the Internet, by operator policy. "it is not possible, in general, to propagate a host route with confidence that the route will propagate throughout the network." (4.4.2)
- Goal 6: one address in place of a list of servers. "To reduce a list of servers to a single, distributed address." (3.2, item 6)
