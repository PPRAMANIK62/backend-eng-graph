## Summary

The IETF's best current practice (BCP 195, 2022) for deploying TLS:
which versions and cipher suites to allow, how to handle session
resumption, SNI, ALPN and host name validation. Updated in 2026 by RFC
9852, which requires TLS 1.3 for new protocols.

## Key claims

- TLS 1.0 and 1.1 must not be negotiated. "Implementations MUST NOT negotiate TLS version 1.0 [RFC2246]." and "Implementations MUST NOT negotiate TLS version 1.1 [RFC4346]." (3.1.1)
- Resumption is a major performance feature. "Session resumption drastically reduces the number of full TLS handshakes and thus is an essential performance feature for most deployments." (3.4)
- Stateless tickets are popular. "Stateless session resumption with session tickets is a popular strategy." (3.4)
- Resumption data must be authenticated and encrypted. "When it is used, the resumption information MUST be authenticated and encrypted to prevent modification or eavesdropping by an attacker." (3.4)
- Ticket-encryption keys must be rotated, e.g. weekly, to keep forward secrecy. "Ticket-encryption keys MUST be changed regularly, e.g., once every week, so as not to negate the benefits of forward secrecy" (3.4)
- Old ticket keys must be destroyed. "Old ticket-encryption keys MUST be destroyed at the end of the validity period." (3.4)
- Resumption must be as secure as the first handshake. "Session resumption is another kind of TLS handshake and therefore must be as secure as the initial handshake." (3.4, Rationale)
- SNI must be supported for HTTPS and similar. "TLS implementations MUST support the Server Name Indication (SNI) extension defined in Section 3 of [RFC6066] for those higher-level protocols that would benefit from it, including HTTPS." (3.7)
- SNI lets many sites share one address, each with its own certificate, but leaks the domain. "SNI supports deployment of multiple TLS-protected virtual servers on a single address" and "However, SNI also leaks the target domain for a given connection" (3.7, Rationale)
- Host name validation is what ties the connection to the right server. "Without it, TLS ensures that the certificate is valid and guarantees possession of the private key but does not ensure that the connection terminates at the desired endpoint." (6.1)
- Clients must also verify the whole chain. "application clients need to verify the entire certification path in accordance with [RFC5280]." (6.1)
