## Summary

How QUIC detects loss and controls congestion (2021). The algorithms
follow TCP's, but QUIC's packet numbers never repeat, so an ACK always
says exactly which transmission arrived. Section 4 lists the
differences from TCP.

## Key claims

- Packet numbers never repeat and always increase. "Packet numbers never repeat within a packet number space for the lifetime of a connection." (3)
- So there's no need to tell a retransmission from the original. "This design obviates the need for disambiguating between transmissions and retransmissions" (3)
- Transmission order and delivery order are separate: packet numbers for the first, stream offsets for the second. "QUIC separates transmission order from delivery order: packet numbers indicate transmission order, and delivery order is determined by the stream offsets in STREAM frames." (4.2)
- Lost data is resent in a new packet with a new number. "QUIC includes necessary frames in a new packet with a new packet number, removing ambiguity about which packet is acknowledged when an ACK is received." (4.2)
- TCP can report three SACK ranges; QUIC many. "QUIC supports many ACK ranges, as opposed to TCP's three SACK ranges." (4.5)
- The receiver reports how long it delayed the ACK. "QUIC endpoints measure the delay incurred between when a packet is received and when the corresponding acknowledgment is sent" (4.6)
- The default congestion controller is like NewReno. "This document specifies a sender-side congestion controller for QUIC similar to TCP NewReno [RFC6582]." (7)
- A sender can choose another algorithm on its own. "A sender can unilaterally choose a different algorithm to use, such as CUBIC [RFC8312]." (7)

- TCP mixes send order and delivery order, hence retransmission ambiguity. "TCP conflates transmission order at the sender with delivery order at the receiver, resulting in the retransmission ambiguity problem [RETRANSMISSION]." (4.2)
- Unique packet numbers give better RTT samples and easy spurious-retransmission detection. "Consequently, more accurate RTT measurements can be made, spurious retransmissions are trivially detected" (4.2)
