## Summary

The current TCP standard (STD 7), which obsoletes RFC 793 and folds in
the fixes from RFC 1122 and others. The parts noted here are the window
(flow control), zero-window probing, silly window syndrome, the Nagle
algorithm and delayed ACKs.

## Key claims

- The 16-bit Window field says how many bytes, starting at the ACK number, the sender of the segment will accept. "The number of data octets beginning with the one indicated in the acknowledgment field that the sender of this segment is willing to accept." (3.1, Window)
- The window is scaled when the window scale option is in use. "The value is shifted when the window scaling extension is used" (3.1, Window)
- The window is tied to the receiver's free buffer space. "There is an assumption that this is related to the data buffer space currently available for this connection." (3.8.6)
- Advertising more than you can hold leads to drops and retransmissions; advertising too little adds a round trip between segments. "Indicating a small window may restrict the transmission of data to the point of introducing a round-trip delay between each new segment transmitted." (3.8.6)
- Shrinking the window (moving its right edge left) is discouraged. "A TCP receiver SHOULD NOT shrink the window, i.e., move the right window edge to the left (SHLD-14)." (3.8.6)
- When the window is zero, the sender must keep probing it so a reopening isn't lost. "This retransmission is essential to guarantee that when either TCP peer has a zero window the reopening of the window will be reliably reported to the other." (3.8.6.1)
- A receiver may keep its window closed indefinitely, and the sender must keep the connection open while probes are ACKed. "A TCP implementation MAY keep its offered receive window closed indefinitely (MAY-8)." (3.8.6.1)
- First zero-window probe after one retransmission timeout, then exponentially longer gaps. "The transmitting host SHOULD send the first zero-window probe when a zero window has existed for the retransmission timeout period (SHLD-29)" (3.8.6.1)
- Silly window syndrome is a stable pattern of tiny window updates. "The \"Silly Window Syndrome\" (SWS) is a stable pattern of small incremental window movements resulting in extremely poor TCP performance." (3.8.6.2)
- The usable window is the offered window minus data in flight. "U = SND.UNA + SND.WND - SND.NXT" (3.8.6.2.1)

Added 2026-09-28 for `network-layers`:

- The TCP checksum covers a pseudo-header built from IP-layer fields (addresses, protocol, length), so TCP depends on the layer below. "The checksum also covers a pseudo-header (Figure 2) conceptually prefixed to the TCP header." (3.1)
- Pseudo-header size and purpose. "The pseudo-header is 96 bits for IPv4 and 320 bits for IPv6.  Including the pseudo-header in the checksum gives the TCP connection protection against misrouted segments." (3.1)
- The addresses are passed from IP to TCP across the layer interface. "This information is carried in IP headers and is transferred across the TCP/network interface in the arguments or results of calls by the TCP implementation on the IP layer." (3.1)
- The receiver avoids SWS by holding the right edge fixed until it can open by at least min(half the buffer, one MSS). (3.8.6.2.2, the RCV.BUFF diagram and inequality)
- Nagle: while data is unacknowledged, buffer new user data until it's ACKed or a full segment can go. "If there is unacknowledged data (i.e., SND.NXT > SND.UNA), then the sending TCP endpoint buffers all user data (regardless of the PSH bit) until the outstanding data has been acknowledged or until the TCP endpoint can send a full-sized segment (Eff.snd.MSS bytes)." (3.7.4)
- Nagle is a SHOULD, and there must be a way to turn it off per connection. "However, there MUST be a way for an application to disable the Nagle algorithm on an individual connection (MUST-17)." (3.7.4)
- Delayed ACK: SHOULD implement it, delay under 0.5 s, ACK at least every second full-sized segment. "the delay MUST be less than 0.5 seconds (MUST-40)" (3.8.6.3)
- Nagle plus delayed ACK hurts request-response applications. "the combination of the Nagle algorithm and delayed acknowledgments can result in poor application performance." (Appendix A.3)
- The standard wasn't updated with the Nagle fix, and many apps just turn Nagle off. "Additionally, many applications simply disable Nagle since this is generally supported by a socket option." (Appendix A.3)
- An endpoint MUST implement slow start, congestion avoidance and RTO backoff; RFC 5681 is the current description, and alternatives are allowed. "A TCP endpoint MUST implement the basic congestion control algorithms slow start, congestion avoidance, and exponential backoff of RTO to avoid creating congestion collapse conditions (MUST-19)." (3.8.2)

Added 2026-09-28 for the transport core nodes (tcp, tcp-handshake, time-wait):

- RFC 9293 replaces RFC 793. "This document obsoletes RFC 793, as well as RFCs 879, 2873, 6093, 6429, 6528, and 6691 that updated parts of RFC 793." (Abstract)
- RFC 793 dates from September 1981. "RFC 793, DOI 10.17487/RFC0793, September 1981" (8.2, reference [16])
- Options only exist when the data offset is above 5 words, so the fixed header is 20 bytes. "size(Options) == (DOffset-5)*32; present only when DOffset > 5." (3.1, Options)
- Once established, every segment carries an ACK. "Once a connection is established, this is always sent." (3.1, Acknowledgment Number)
- At low speeds wrapping takes hours. "At 2 megabits/sec., it takes 4.5 hours to use up 2^32 octets of sequence space." (3.4.3)
- Guessable ISNs are a security problem. "There are security issues that result if an off-path attacker is able to predict or guess ISN values" (3.4.1)
- TCP gives applications a reliable, in-order byte stream. "TCP provides a reliable, in-order, byte-stream service to applications." (2.2)
- Each segment rides in one IP datagram. "The application byte-stream is conveyed over the network via TCP segments, with each TCP segment sent as an Internet Protocol (IP) datagram." (2.2)
- Reliability is loss detection by sequence numbers, errors by checksum, and fixing both by retransmission. "TCP reliability consists of detecting packet losses (via sequence numbers) and errors (via per-segment checksums), as well as correction via retransmission." (2.2)
- TCP has no built-in way to tell a peer is alive. "TCP is connection oriented, though it does not inherently include a liveness detection capability." (2.2)
- Ports identify services and separate flows between two hosts. "TCP uses port numbers to identify application services and to multiplex distinct flows between hosts." (2.2)
- The header has 16-bit source and destination ports, 32-bit sequence and acknowledgment numbers, a 4-bit data offset, control bits, a 16-bit window, a 16-bit checksum, an urgent pointer, then options. (3.1, Figure 1)
- The control bits. "The currently assigned control bits are CWR, ECE, URG, ACK, PSH, RST, SYN, and FIN." (3.1)
- The checksum also covers a pseudo-header with the IP addresses, which guards against misrouted segments. "Including the pseudo-header in the checksum gives the TCP connection protection against misrouted segments." (3.1, Checksum)
- The states. "The states are: LISTEN, SYN-SENT, SYN-RECEIVED, ESTABLISHED, FIN-WAIT-1, FIN-WAIT-2, CLOSE-WAIT, CLOSING, LAST-ACK, TIME-WAIT, and the fictional state CLOSED." (3.3.2)
- What TIME-WAIT waits for. "TIME-WAIT - represents waiting for enough time to pass to be sure the remote TCP peer received the acknowledgment of its connection termination request and to avoid new connections being impacted by delayed segments from previous connections." (3.3.2)
- Every byte has a sequence number. "every octet of data sent over a TCP connection has a sequence number." (3.4)
- ACKs are cumulative. "an acknowledgment of sequence number X indicates that all octets up to but not including X have been received." (3.4)
- Sequence numbers are 32 bits and wrap, so all comparisons are modulo 2^32. "This space ranges from 0 to 2^32 - 1." (3.4)
- SYN and FIN each take one sequence number so they can be acknowledged. "The SYN and FIN are the only controls requiring this protection" (3.4)
- A plain ACK takes no sequence number. "the ACK does not occupy sequence number space (if it did, we would wind up ACKing ACKs!)." (3.5)
- A connection is identified by a pair of sockets. "A connection is defined by a pair of sockets." (3.4.1)
- A socket, in TCP's vocabulary, is an address plus a port. "the concatenation of an Internet Address with a TCP port." (4, Glossary, socket)
- TIME-WAIT and ISN choice together keep old segments out of new incarnations of a connection. "the TIME-WAIT state limits the rate of connection reuse, while the initial sequence number selection described below further protects against ambiguity" (3.4.1)
- ISNs come from a clock plus a secret keyed hash of the four addresses and ports. "ISN = M + F(localip, localport, remoteip, remoteport, secretkey)" (3.4.1)
- The ISN clock ticks roughly every 4 µs and wraps about every 4.55 hours. "it cycles approximately every 4.55 hours" (3.4.1)
- The clock part of the ISN is a 32-bit counter ticking about every 4 µs. "M is the 4 microsecond timer" (3.4.1, under the ISN formula) and "a 32-bit counter that typically increments at least once every roughly 4 microseconds" (3.4.1)
- Each side sends its ISN and gets it acknowledged; two of the four messages merge. "Because steps 2 and 3 can be combined in a single message this is called the three-way (or three message) handshake (3WHS)." (3.4.1)
- The receiver of a SYN can't tell an old duplicate from a new one, so it asks the sender to confirm. "The receiver of the first SYN has no way of knowing whether the segment was an old one or not" (3.4.1)
- The main reason for the three-way handshake. "The principal reason for the three-way handshake is to prevent old duplicate connection initiations from causing confusion." (3.5)
- Figure 6: A sends SEQ=100 SYN; B replies SEQ=300 ACK=101 SYN,ACK; A replies SEQ=101 ACK=301 ACK and then sends data with the same SEQ=101. (3.5, Figure 6)
- Data may ride on handshake segments if the receiver holds it until the connection is established. "this is perfectly legitimate, so long as the receiving TCP endpoint doesn't deliver the data to the user until it is clear the data is valid" (3.5)
- Simultaneous open must work. "A TCP implementation MUST support simultaneous open attempts" (3.5, MUST-10)
- An old duplicate SYN gets answered, the other side replies RST, and the listener goes back to LISTEN. (3.5, Figure 8)
- MSL is two minutes by definition. "For this specification the MSL is taken to be 2 minutes." (3.4.2)
- The 2-minute MSL is a choice, not a measurement. "This is an engineering choice, and may be changed if experience indicates it is desirable to do so." (3.4.2)
- At high speeds the sequence space wraps fast, and timestamps with PAWS handle it. "At 1 Gbps, the cycle time is 34 seconds, only 3 seconds at 10 Gbps, and around a third of a second at 100 Gbps." (3.4.3)
- CLOSE means "no more data to send"; the closer can still receive. "CLOSE is an operation meaning \"I have no more data to send.\"" (3.6)
- Figure 12, normal close: A sends FIN (FIN-WAIT-1); B ACKs (A to FIN-WAIT-2, B in CLOSE-WAIT); B sends FIN (LAST-ACK); A ACKs, sits in TIME-WAIT for 2 MSL, then CLOSED. (3.6, Figure 12)
- A connection can also end in an abort. "an \"abort\" in which one or more RST segments are sent and the connection state is immediately discarded." (3.6)
- The two directions close independently. "Since the two directions of a TCP connection are closed independently, it is possible for a connection to be \"half closed\"" (3.6.1)
- The active closer stays in TIME-WAIT for 2 MSL. "When a connection is closed actively, it MUST linger in the TIME-WAIT state for a time 2xMSL (Maximum Segment Lifetime) (MUST-13)." (3.6.1)
- A TIME-WAIT connection MAY accept a new SYN if the new ISN is larger than anything used before. (3.6.1, MAY-2)
- Timestamp-based TIME-WAIT reduction (RFC 6191) SHOULD be implemented. "This algorithm for reducing TIME-WAIT is a Best Current Practice that SHOULD be implemented" (3.6.1)
- Segment boundaries don't match write() boundaries. "TCP guarantees no correlation between the boundaries of TCP segments sent and received and the boundaries of the read or write buffers of user application data." (3.7)
- Retransmission is how delivery is ensured. "Because segments may be lost due to errors (checksum test failure) or network congestion, TCP uses retransmission to ensure delivery of every segment." (3.8)
- SND.UNA, SND.NXT and RCV.NXT: the oldest unacknowledged byte, the next byte to send, the next byte expected. (3.8)
- The RTO follows RFC 6298, including Karn's algorithm. "The RTO MUST be computed according to the algorithm in [10], including Karn's algorithm for taking RTT samples (MUST-18)." (3.8.1)
- Giving up on data: R2 at least 100 seconds. "The value of R2 SHOULD correspond to at least 100 seconds (SHLD-11)." (3.8.3)
- Giving up on a SYN: at least 3 minutes. "R2 for a SYN segment MUST be set large enough to provide retransmission of the segment for at least 3 minutes (MUST-23)." (3.8.3)
- Keep-alives are optional and off by default. "they MUST default to off (MUST-25)." (3.8.4)
- The keep-alive interval defaults to at least two hours. "This interval MUST be configurable (MUST-27) and MUST default to no less than two hours (MUST-28)." (3.8.4)
- TCP has no encryption or authentication of its own. "there are no built-in cryptographic capabilities to support any form of confidentiality, authentication, or other typical security functions." (7)
- SYN flooding is a known resource attack that OSes mitigate. "Examples include SYN flooding [32] or wasting resources on non-progressing connections [41]. Operating systems commonly implement mitigations for these attacks." (7)

Added 2026-09-28 for `tcp-flow-control` audit:

- A zero-window probe carries at least one byte of new data if there is any. "The sending TCP peer must regularly transmit at least one octet of new data (if available), or retransmit to the receiving TCP peer even if the send window is zero" (3.8.6.1)
- The receiver answers every segment, even at zero window, with its current window. "When the receiving TCP peer has a zero window and a segment arrives, it must still send an acknowledgment showing its next expected sequence number and current window (zero)." (3.8.6.1)
- Probe gaps grow exponentially. "SHOULD increase exponentially the interval between successive probes (SHLD-30)." (3.8.6.1)
- Sender SWS avoidance: send when a full segment fits, when pushed data all fits, when at least Fs (recommended 1/2) of the largest window seen can go, or when an override timer fires. "The override timeout should be in the range 0.1 - 1.0 seconds." (3.8.6.2.1)

Added 2026-09-28 (audit) for `icmp`:

- A segment for a connection that doesn't exist gets a reset. "If the connection does not exist (CLOSED), then a reset is sent in response to any incoming segment except another reset." (3.5.2)
