# The memory hierarchy

A computer keeps data in several layers of memory: registers, then two or
three levels of cache, then RAM, then the disk. Each layer is bigger and
slower than the one above it, and the hardware moves data between them for
you. Whether your code runs at cache speed or at RAM speed, which can be a
hundred times apart, depends mostly on how it touches memory.

## One loop, ten working-set sizes

The clearest way to see the hierarchy is to measure it. On the laptop this
lab runs on (an Intel i5-13500H, Linux 7.1.9), we ran a small C program
that follows a chain of pointers through a block of memory. Each step reads
the address of the next step, so the CPU can't start a load until the one
before it has finished, and the order is random, so the hardware can't
guess what's coming. That makes each step cost one full trip to wherever
the data lives. We did this for block sizes from 16 KiB up to 1 GiB. The
full setup is in [experiment 0001](../../experiments/0001-latency-numbers-on-my-laptop.md).

Here is the average time per load, median of 11 runs:

| Working set | ns per load |
|---|---|
| 16 KiB | 1.09 |
| 32 KiB | 1.26 |
| 256 KiB | 3.77 |
| 1 MiB | 6.08 |
| 2 MiB | 11.53 |
| 8 MiB | 18.82 |
| 16 MiB | 48.03 |
| 64 MiB | 104.17 |
| 256 MiB | 113.01 |
| 1 GiB | 125.19 |

The curve is a staircase. While the block fits in
the L1 cache, a load takes about 1 ns. Past that it jumps to 4 to 6 ns
(L2), then 12 to 19 ns (L3), then over 100 ns once the block is far bigger
than the 18 MiB L3 and almost every load goes to RAM. `lscpu` on this
machine reports 448 KiB of L1 data cache over 12 instances, 9 MiB of L2
over 6 instances, and one shared 18 MiB L3, and the steps land near those
sizes. A load from RAM costs about as much as 100 loads from L1.

The same shape shows up in measurements published in 2007, on a
processor with only two cache levels: three flat plateaus, one per level,
with the cost per element under 10 cycles in L1, around 28 from L2 and 480
or more from RAM.

## Why every level is a trade of size for speed

You might ask why the machine doesn't just have one big, fast memory. Two
reasons.

The first is cost. Memory as fast as a CPU core can be built, but it's
orders of magnitude more expensive per byte than the DRAM used for main
memory. A machine with a lot of reasonably fast RAM beats one with a little
very fast RAM, as soon as the program's data doesn't fit in the small one.
So the machine gets a lot of cheap, slower DRAM and a small amount of fast
SRAM next to the cores.

The second is physics. A fast cache has to be small. The bigger a memory
is, the farther its far end is from the core, and signal travel time
starts to matter. So a large cache is a slower one. That's why
there are several cache levels instead of one: each level is the biggest
that can still hit its speed target.

Below RAM there is one more level. When RAM is full, the operating system
can move pages of memory it isn't using out to disk and bring them back on
demand. Disk holds far more than RAM and is far slower. On this laptop's
NVMe SSD, a random 4 KiB read took 49.8 µs at the median, about 400 times
a RAM miss. If the OS picks the wrong pages to push out, a program can run
at disk speed instead of memory speed, which can mean 10,000 to 100,000
times slower. How the OS does this is the subject of
[[virtual-memory]] and [[page-faults]].

## Nobody has to manage it, and that's the point

The caches are not memory you can address. The CPU treats them as copies
of parts of RAM and decides on its own what to keep. The alternative,
mapping the fast memory into the address space and letting the OS or the
program decide what goes there, doesn't work in practice: every program
would need to manage its share, and the bookkeeping would eat the gain. So the
hardware does it, and your code can't tell the difference except by the
clock.

That's why the hierarchy is easy to ignore and expensive to ignore. The
program is correct either way. It just runs slower when it keeps asking
for data that isn't near the top.

## Locality is what makes the trick work

A cache only helps if the data you need next is data you used recently, or
data sitting right next to it. Programs usually behave like that, and the
two habits have names:

- **Temporal locality.** You'll probably touch the same thing again soon.
  Loop counters, the code of a loop, a hot map entry.
- **Spatial locality.** You'll probably touch something near it soon. The
  next element of an array, the next field of a struct.

The hardware bets on both. When you load one byte, the CPU fetches the
whole 64-byte block around it, called a cache line (the next article,
[[cpu-cache]], is about lines). Reading the other 63 bytes is then nearly
free. A 2010 experiment showed this in a simple way: a loop that touched
every int in a large array and a loop that touched every sixteenth int
took almost the same time (80 ms and 78 ms), because both loaded every
cache line in the array. The work was in the memory traffic, not the
arithmetic.

Our own laptop shows how much spatial locality buys. Adding up a 256 MiB
buffer front to back ran at 18.3 GB/s. That's about 0.44 ns per 8-byte
word, from RAM, compared with 104 to 125 ns for a random dependent load
from RAM. The data came from the same memory. The difference is that a
sequential read uses every byte of every line it fetches, and the CPU can
see the pattern and fetch the next line before you ask for it. This is
called prefetching, and it's why a sequential walk past the caches can
cost a few cycles per element instead of hundreds.

Locality is a rule of thumb about programs. Some code has a lot of it and
some has almost none: a hash table lookup, a tree walk, a linked list of
objects spread over the heap. That kind of code lives on the lower steps
of the staircase.

## The working set decides which step you're on

Put the two ideas together and you get the rule that explains the
staircase. What matters is the working set: the memory a piece of code
touches over a short stretch of time. If it fits in L1, loads cost about a
nanosecond. If it only fits in L3, they cost ten or twenty. If it doesn't
fit in any cache and the access pattern is random, every load pays the
full RAM price.

The total amount of memory your program uses matters much less. A server
with 10 GB of data that spends most of its time on 1 MB of hot entries
runs mostly at cache speed. A server that touches a fresh random slice of
those 10 GB for every request doesn't.

## Where it gets tricky

**Published numbers age fast.** Intel's figures for a Pentium M in 2007
put a RAM access at about 240 CPU cycles. On our laptop in 2026 a RAM miss
costs 104 to 125 ns. The ratios between levels have stayed in the same
range, but the absolute numbers belong to one machine in one year. Ours
were taken with the CPU governor set to `powersave`, on one pinned core.
Measure on the machine you care about. [[latency-numbers]]
has the rest of our measured table and why the famous lists disagree.

**The staircase mixes in a second cache.** Translating a virtual address
to a physical one has its own cache, the TLB, and it can overflow too. Our
test used 4 KiB pages, so at the largest sizes some of the cost is
probably TLB misses, not just RAM. The test didn't measure that part on
its own. The 2007 measurements show this directly: putting
each element on its own page produced a separate spike exactly where the
TLB ran out. RAM isn't always RAM: touching more pages than the TLB
covers is slow even when every byte is already in memory. See
[[virtual-memory]] and [[huge-pages]].

**Averages hide the steps between them.** Each number in the table is an
average per load. At 16 MiB the answer was 48 ns, between the L3 and RAM
values, most likely because some loads hit L3 and some didn't. Real programs sit on
these ramps all the time.

## What this means when you build

- Know your working set. The question to ask about a hot path is "how much
  memory does it touch per request?", not "how much memory does the
  process use?"
- Prefer layouts you can walk in order: arrays and slices of values over
  pointers to scattered objects. A sequential scan from RAM can be two
  orders of magnitude cheaper per item than chasing pointers.
- Keep hot data together and cold data out of the way, so each cache line
  fetched carries data you'll use.
- Treat RAM as the slow tier it is compared with cache, and disk as slower
  still: a single random SSD read costs as much as hundreds of RAM misses.
- Don't trust a latency table you didn't produce. Run a pointer-chase like
  ours on the target machine.
