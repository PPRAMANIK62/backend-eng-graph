## Summary

The Consul API docs page (v2.0.x, the latest when read) on blocking
queries: Consul's long polling. A response carries an index; the next
request passes it back and hangs until something newer exists or a
wait time runs out. The page lists the edge cases a client loop must
handle, and the streaming backend added in Consul 1.10 that replaces
long polling for some endpoints.

## Key claims

- Blocking queries are long polling. "A blocking query is used to wait for a potential change using long polling." (Blocking Queries)
- The response carries an index of the current state. "Endpoints that support blocking queries return an HTTP header named X-Consul-Index." (Blocking Queries)
- The request hangs until a change or the timeout. "When this is provided, the HTTP request will "hang" until a change in the system occurs, or the maximum timeout is reached." (Blocking Queries)
- A return doesn't mean something changed. "A critical note is that the return of a blocking request is no guarantee of a change." (Blocking Queries)
- The wait is capped at 10 minutes and defaults to 5. "This is limited to 10 minutes. If not set, the wait time defaults to 5 minutes." (Blocking Queries)
- Random extra wait spreads out wake-ups. "A small random amount of additional wait time is added to the supplied maximum wait time to spread out the wake up time of any concurrent requests. This adds up to wait / 16 additional time to the maximum duration." (Blocking Queries)
- If the index goes backwards, reset to 0. "Implementations must check to see if a returned index is lower than the previous value, and if it is, should reset index to 0 - effectively restarting their blocking loop." (Implementation Details)
- A zero index turns the loop into a busy loop. "It's especially bad because it causes blocking clients that are not aware to enter a busy loop, using excessive client CPU and causing high load on servers." (Implementation Details)
- Fast-changing data turns long polling into busy polling. "In cases where a result gets updated very fast however - possibly during an outage or incident with a badly behaved client - blocking query loops degrade into busy loops that consume excessive client CPU and cause high server load." (Implementation Details, Rate limit)
- Rate limit the loop instead of sleeping every time. "Clients should instead rate limit the loop so that in the happy case they proceed without waiting, but when values start to churn quickly they degrade into polling at a reasonable rate (say every 15 seconds)." (Implementation Details, Rate limit)
- Token bucket with burst 2. "a token bucket with burst of 2 is a simple way to achieve this." (Implementation Details, Rate limit)
- Streaming replaced long polling in Consul 1.10 for some endpoints. "The streaming backend, first introduced in Consul 1.10, is a replacement for the long polling backend." (Streaming backend)
- Streaming sends less data. "Streaming improves on the traditional long polling between clients and servers by significantly reducing the quantity of data sent between them, while still allowing clients to handle read requests." (Streaming backend)
- Hash-based blocking uses a content hash when there's no index. "each response instead contains a header X-Consul-ContentHash which is an opaque hash digest generated by hashing over all fields in the response that are relevant." (Hash-based Blocking Queries)
