## Summary

The IETF standard (2025) for telling API clients, in each response,
that a resource is or will be deprecated: the `Deprecation` header, a
`deprecation` link relation pointing to docs, and how it pairs with
the `Sunset` header from RFC 8594.

## Key claims

- What deprecating is for: move clients off, stop new dependencies. "It encourages client applications to migrate away from the resource, discourages applications from forming new dependencies on the resource, and informs applications about the risk of continued dependence upon the resource." (1. Introduction)
- Deprecating changes nothing about behavior. "The act of deprecation does not change any behavior of the resource." (1. Introduction; 5. Resource Behavior)
- The header value is a structured-field date, which may be in the past or future; the example is `Deprecation: @1688169599`. "Deprecation is an Item Structured Header Field; its value MUST be a Date as per Section 3.3.7 of [RFC9651]." (2.1 Syntax)
- A Link with rel="deprecation" points to docs and a migration guide. "The documentation MAY provide a guide and timeline for migrating away from the deprecated resource to a new resource(s) that replaces the deprecated resource, if applicable." (3.1 Documentation)
- Sunset (RFC 8594) says when the resource is expected to stop responding, and must not come before the deprecation. "The timestamp given in the Sunset HTTP header field MUST NOT be earlier than the one given in the Deprecation header field." (4. Sunset)
- Deprecation info is only a hint; clients must work without it. "It is optional information that cannot be depended on, and client applications should always be implemented in ways that allow them to function without deprecation-related information." (2.2 Scope)
- After the deprecation date, clients can't assume behavior stays the same. "In cases where the Deprecation header field value is in the past, the client application developers MUST no longer assume that the behavior of the resource will remain the same as before the deprecation date." (7. Security Considerations)

## My notes

- Deprecation, then Sunset, then removal is the lifecycle. Neither
  header says how long the gap should be; that's the provider's
  policy.
