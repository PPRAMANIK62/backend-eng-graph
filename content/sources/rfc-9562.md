## Summary

The UUID standard (2024, Proposed Standard), which obsoletes RFC 4122. It
defines the 128-bit UUID layout and versions 1 to 8, adds the
time-ordered UUIDv6 and UUIDv7, and gives best practices, including a
section on using UUIDs as database keys.

## Key claims

- It replaces RFC 4122. "This document obsoletes RFC 4122." (Abstract)
- The first reason for the update: random UUIDs are bad for B-tree indexes. "UUID versions that are not time ordered, such as UUIDv4 (described in Section 5.4), have poor database-index locality." (2.1, item 1)
- Random keys mean inserts at random places in the index. "new values created in succession are not close to each other in the index; thus, they require inserts to be performed at random locations." (2.1, item 1)
- The effect on B-trees can be large. "The resulting negative performance effects on the common structures used for this (B-tree and its variants) can be dramatic." (2.1, item 1)
- Many ad hoc sortable id schemes existed before (ULID, Snowflake, KSUID and others). "This has led to numerous implementations over the past 10+ years solving the same problem in slightly different ways." (2.1)
- UUIDv4 is random except for the version and variant bits: 122 random bits. "randomly generate the exact required number of bits for random_a, random_b, and random_c (122 bits total)" (5.4)
- UUIDv7 puts a 48-bit Unix millisecond timestamp first, then random bits. "allocating a Unix timestamp in milliseconds in the most significant 48 bits and filling the remaining 74 bits, excluding the required version and variant bits, with random bits" (5.7)
- UUIDv7 may add a sub-millisecond fraction or a counter for extra monotonicity. "An OPTIONAL carefully seeded counter as per Section 6.2 (Method 1 or 2)." (5.7)
- Prefer v7 over v1 and v6. "Implementations SHOULD utilize UUIDv7 instead of UUIDv1 and UUIDv6 if possible." (5.7)
- v6 and v7 sort correctly as raw bytes. "UUIDv6 and UUIDv7 are designed so that implementations that require sorting (e.g., database indexes) sort as opaque raw bytes without the need for parsing or introspection." (6.11)
- Time-ordered keys land near each other in the index; the difference can be ten times or more. "The real-world differences in this approach of index locality versus random data inserts can be one order of magnitude or more." (6.11)
- Store UUIDs as 128-bit binary, not text (text takes 288 bits). "storing UUIDs as text is unnecessarily verbose, requiring 288 bits to represent 128-bit UUID values." (6.13)
- In a single database, database-generated UUIDs give the best ordering. "Applications using a monolithic database may find using database-generated UUIDs (as opposed to client-generated UUIDs) provides the best UUID monotonicity." (6.13)
- Values that look unique and permanent often turn out not to be. "A common issue observed in database schema design is the assumption that a particular value will never change, which later turns out to be an incorrect assumption." (6.13)
- Examples: postal codes, licence and ID numbers. "Postal codes, license or other identification numbers, and numerous other such identifiers seem unique and unchanging at a given point time -- only later to have edge cases where they need to change." (6.13)
- The advice: time-based surrogate keys over natural keys. "The general advice is to avoid name-based UUID natural keys and, instead, to utilize time-based UUID surrogate keys" (6.13)
- UUIDs are not secrets. "they MUST NOT be used as security capabilities (identifiers whose mere possession grants access)." (8)
- The timestamp in a v7 reveals creation order; use v4 where that matters. "If UUIDs are required for use with any security operation within an application context in any shape or form, then UUIDv4 (Section 5.4) SHOULD be utilized." (8)
- A UUID is 128 bits and meant to be unique without coordination. "A UUID is 128 bits long and is intended to guarantee uniqueness across space and time." (Abstract)
- UUIDv7 field layout: 48-bit unix_ts_ms, 4-bit ver, 12-bit rand_a, 2-bit var, 62-bit rand_b. "rand_a: 12 bits of pseudorandom data to provide uniqueness as per Section 6.9" and "rand_b: The final 62 bits of pseudorandom data to provide uniqueness as per Section 6.9" (5.7)
- Clocks can move backwards, and the implementation has to decide what to do. "if it is possible for the system clock to move backward due to either manual adjustment or corrections from a time synchronization protocol, implementations need to determine how to handle such cases." (6.1, Reliability)
- Monotonicity is the point of time-ordered UUIDs. "Monotonicity (each subsequent value being greater than the last) is the backbone of time-based sortable UUIDs." (6.2)
- Many UUIDs in the same millisecond need a counter to stay in order. "Batch UUID creation implementations MAY utilize a monotonic counter that increments for each UUID created during a given timestamp." (6.2)
- With many generating nodes, collision chances grow; the RFC mentions node IDs and central registries but doesn't require either. "as the total number of UUID generating nodes increases, so does the likelihood of a collision." (6.4)
- A central registry can become a bottleneck and is not recommended. "Shared knowledge schemes with central/global registries are outside the scope of this specification and are NOT RECOMMENDED." (6.4, Centralized Registry)
- Distributed generation depends on every host's randomness. "Distributed applications generating UUIDs at a variety of hosts MUST be willing to rely on the random number source at all hosts." (6.4)

## My notes

- The "one order of magnitude or more" is the RFC's claim with no benchmark setup given. Use it as the RFC's statement only.
