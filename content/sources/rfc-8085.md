## Summary

Best Current Practice 145 (2017, replaces RFC 5405). What an
application built on UDP has to do for itself because UDP won't:
congestion control, message sizing, reliability, duplicate handling,
checksums, and surviving NATs and firewalls.

## Key claims

- UDP is minimal and unreliable. "The User Datagram Protocol (UDP) [RFC768] provides a minimal, unreliable, best-effort, message-passing transport" (1)
- No connection setup or teardown, little state. "UDP communication consequently does not incur connection establishment and teardown overheads, and there is minimal associated end-system state." (1)
- No congestion control, and apps can send at line rate. "A second unique characteristic of UDP is that it provides no inherent congestion control mechanisms." (1)
- An application can send at the speed of its network card, which is often more than the path can carry. "On many platforms, applications can send UDP datagrams at the line rate of the platform's link interface, which is often much greater than the available end-to-end path capacity" (1)
- So the application must add it. "Because UDP itself provides no congestion control mechanisms, it is up to the applications that use UDP for Internet communication to employ suitable mechanisms to prevent congestion collapse and establish a degree of fairness." (1)
- Largest payload: 65,507 bytes over IPv4, 65,527 over IPv6. "A UDP datagram is carried in a single IP packet and is hence limited to a maximum payload of 65,507 bytes for IPv4 and 65,527 bytes for IPv6." (1)
- Fragmentation should be avoided. "Fragmentation decreases communication reliability and efficiency and should be avoided." (1)
- Losing one fragment loses the whole datagram. "The loss of a single fragment results in the loss of an entire fragmented packet" (3.2)
- Don't send datagrams bigger than the path MTU. "an application SHOULD NOT send UDP datagrams that result in IP packets that exceed the Maximum Transmission Unit (MTU) along the path to the destination." (3.2)
- If you don't know the path MTU, stay under 576 bytes (IPv4) or 1280 bytes (IPv6). "For IPv4, EMTU_S is the smaller of 576 bytes and the first-hop MTU [RFC1122]. For IPv6, EMTU_S is 1280 bytes [RFC2460]." (3.2)
- The UDP header is 8 bytes. "the length of the UDP header (8 bytes)" (3.2)
- No retransmission; apps that need reliability build it. "Applications that do require reliable message delivery MUST implement an appropriate mechanism themselves." (3.3)
- Datagrams can be duplicated. "an application may receive multiple copies of the same UDP datagram, with some duplicates arriving potentially much later than the first." (3.3)
- No ordering. "Applications that require ordered delivery MUST reestablish datagram ordering themselves." (3.3)
- Be ready for delayed duplicates for 2 minutes (TCP's MSL). "applications SHOULD be robust to the reception of delayed or duplicate packets that are received within this 2-minute interval." (3.3)
- Retransmissions also need congestion control. "Any application that uses retransmission is responsible for congestion control of its retransmissions" (3.3)
- If you need reliable, ordered delivery, use a standard transport instead. "an application that requires reliable and ordered message delivery SHOULD whenever possible choose an IETF standard transport protocol that provides these features." (3.3)
- The checksum is weak. "These checks are not strong from a coding or cryptographic perspective" (3.4)
- Over IPv4 the checksum can be switched off (zero); over IPv6 it must be used, since IPv6 has no header checksum. "When UDP is used over IPv6, the UDP checksum is relied upon to protect both the IPv6 and UDP headers from corruption (because IPv6 lacks a checksum)" (3.4; 3.4.1 allows a zero checksum for some tunnels)
- NATs and firewalls guess UDP flow state and time it out. "middleboxes can create per-flow state when they see a packet that -- according to some local criteria -- indicates a new flow, and destroy the state after some time during which no packets belonging to the same flow have arrived." (3.5)
- DNS works fine through middleboxes because it is a quick request and reply. "One example is the Domain Name System (DNS)" with its request and response pattern that "typically completes within seconds." (3.5)
- Keep-alives, if needed, no more often than every 15 seconds. "SHOULD NOT transmit them more frequently than once every 15 seconds" (3.5)
- NATs should keep UDP state at least 2 minutes, but many don't. "NATs require a state timeout of 2 minutes or longer [RFC4787]. However, empirical evidence suggests that a significant fraction of currently deployed middleboxes unfortunately use shorter timeouts." (3.5)
