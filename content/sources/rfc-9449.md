## Summary

DPoP (2023) binds OAuth access and refresh tokens to a key pair the
client holds, at the application layer: every request carries a fresh
signed JWT proving possession of the private key, so a stolen token is
useless without the key.

## Key claims

- What it is. "Demonstrating Proof of Possession (DPoP) is an application-level mechanism for sender-constraining OAuth [RFC6749] access and refresh tokens." (1)
- How: a DPoP header with a JWT. "It enables a client to prove the possession of a public/ private key pair by including a DPoP header in an HTTP request." (1)
- Contrast with bearer tokens. "Access tokens that are sender-constrained via DPoP thus stand in contrast to the typical bearer token, which can be used by any party in possession of such a token." (1)
- Bearer tokens have leaked in practice. "unforeseen vectors for leakage have occurred due to vulnerabilities and implementation issues in other layers in the protocol or software stack" (1)
- The proof covers the method. "htm: The value of the HTTP method (Section 9.1 of [RFC9110]) of the request to which the JWT is attached." (4.2)
- And the URI, without query. "htu: The HTTP target URI (Section 7.1 of [RFC9110]) of the request to which the JWT is attached, without query and fragment parts." (4.2)
- A unique id per proof. "jti: Unique identifier for the DPoP proof JWT." (4.2)
- With an access token, a hash of it. "ath: Hash of the access token." (4.2)
- The token names the key by thumbprint. "jkt: JWK SHA-256 Thumbprint confirmation method." (6.1)
- The resource server checks the key matches. "confirm that the public key to which the access token is bound matches the public key from the DPoP proof." (4.3)
- It doesn't protect the body. "The DPoP proof only contains claims for the HTTP URI and method, but not the message body or general request headers, for example." (11.7)
- XSS defeats it. "At this application layer, there is most likely no feasible defense against this threat except generally preventing XSS; therefore, it is considered out of scope for DPoP." (2)
- The creation time. "iat: Creation timestamp of the JWT (Section 4.1.6 of [RFC7519])." (4.2)
- Servers can require a nonce they issued. "When the authentication server or resource server provides a DPoP- Nonce HTTP header in a response (see Sections 8 and 9), the DPoP proof MUST also contain the following claim:" nonce (4.2)
