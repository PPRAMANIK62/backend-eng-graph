## Summary

The 2022 HTTP caching standard (STD 98), obsoleting RFC 7234: shared
and private caches, the cache key, when a response may be stored, how
freshness is worked out, validation, invalidation, and the
Cache-Control directives.

## Key claims

- A shared cache serves many users and usually sits in an intermediary. "A \"shared cache\" is a cache that stores responses for reuse by more than one user; shared caches are usually (but not always) deployed as a part of an intermediary." (1)
- Fresh means reusable without asking the origin. "A cache considers a stored response \"fresh\", as defined in Section 4.2, if it can be reused without \"validation\" (checking with the origin server to see if the cached response remains valid for this request)." (1)
- Reuse is the default unless something forbids it. "it can be assumed that reusing a cached response is desirable and that such reuse is the default behavior when no requirement or local configuration prevents it." (2)
- The cache key is at least method and URI; many caches use only the URI. "However, many HTTP caches in common use today only cache GET responses and therefore only use the URI as the cache key." (2)
- Vary adds request headers to the key. "Caches differentiate these responses by incorporating some of the original request's header fields into the cache key as well, using information in the Vary response header field" (2)
- A shared cache must not store responses to requests with Authorization unless explicitly allowed. "if the cache is shared: the Authorization header field is not present in the request (see Section 11.6.2 of [HTTP]) or a response directive is present that explicitly allows shared caching" (3)
- `no-store` forbids any cache from storing the response. "The no-store response directive indicates that a cache MUST NOT store any part of either the immediate request or the response" (5.2.2.5)
- `private` forbids shared caches from storing a response. "The unqualified private response directive indicates that a shared cache MUST NOT store the response (i.e., the response is intended for a single user)." (5.2.2.7)
- `s-maxage` overrides max-age for shared caches. "The s-maxage response directive indicates that, for a shared cache, the maximum age specified by this directive overrides the maximum age specified by either the max-age directive or the Expires header field." (5.2.2.10)
- Without explicit freshness, caches may guess, typically 10% of the time since Last-Modified. "A typical setting of this fraction might be 10%." (4.2.2)
- A stale response can still be used after validation or if the origin is down. "When a cached response is not fresh, it might still be reusable if validation can freshen it (Section 4.3) or if the origin is unavailable (Section 4.2.4)." (1)
- Unsafe methods invalidate the cached target URI. "A cache MUST invalidate the target URI (Section 7.1 of [HTTP]) when it receives a non-error status code in response to an unsafe request method (including methods whose safety is unknown)." (4.4)
- Cache poisoning spreads an attacker's content to many users, often via parser differences. "Storing malicious content in a cache can extend the reach of an attacker to affect multiple users." (7.1)
- A common way in is parsing differences between proxies and user agents. "One common attack vector for cache poisoning is to exploit differences in message parsing on proxies and in user agents" (7.1)

Added for `http-caching`:

- Caching is optional, and caches can store more than 200s to GET: redirects, 404s, 206s. "However, it is also possible to store redirects, negative results (e.g., 404 (Not Found)), incomplete results (e.g., 206 (Partial Content)), and responses to methods other than GET" (2)
- The cache key is built from at least the method and target URI. "The \"cache key\" is the information a cache uses to choose a response and is composed from, at a minimum, the request method and target URI used to retrieve the stored response" (2)
- The rules focus on stopping bad storage and reuse, not on forcing caching. "HTTP cache requirements are focused on preventing a cache from either storing a non-reusable response or reusing a stored response inappropriately" (2)
- A response is storable only if it has one of: public, private (private cache), Expires, max-age, s-maxage (shared), a cache extension, or a heuristically cacheable status code. "the response contains at least one of the following:" (3)
- Caches may store responses with neither validator nor lifetime, but some don't. "some caches will not store a response that has neither a cache validator nor an explicit expiration time, as such responses are not usually useful to store." (3)
- must-revalidate, public and s-maxage allow a shared cache to reuse a response to a request with Authorization. "In this specification, the following response directives have such an effect: must-revalidate (Section 5.2.2.2), public (Section 5.2.2.9), and s-maxage (Section 5.2.2.10)." (3.5)
- A stored response is reused only if URI, method and Vary headers match, no-cache doesn't forbid it, and it's fresh, allowed stale, or validated. "When presented with a request, a cache MUST NOT reuse a stored response unless:" (4)
- A cache must add an Age header when it serves a stored response. "When a stored response is used to satisfy a request without validation, a cache MUST generate an Age header field" (4)
- Unsafe methods are always written through to the origin. "A cache MUST write through requests with methods that are unsafe (Section 9.2.1 of [HTTP]) to the origin server" (4)
- Request collapsing is allowed. "This enables a cache to \"collapse requests\" -- or combine multiple incoming requests into a single forward request upon a cache miss" (4)
- Vary: all nominated request headers must match the original request. "the cache MUST NOT use that stored response without revalidation unless all the presented request header fields nominated by that Vary field value match those fields in the original request" (4.1)
- Vary: * never matches. "A stored response with a Vary header field value containing a member \"*\" always fails to match." (4.1)
- Fresh means age below freshness lifetime. "A \"fresh\" response is one whose age has not yet exceeded its freshness lifetime." (4.2)
- The freshness test. "response_is_fresh = (freshness_lifetime > current_age)" (4.2)
- An Expires in the past forces validation on every request. "If an origin server wishes to force a cache to validate every request, it can assign an explicit expiration time in the past to indicate that the response is already stale." (4.2)
- Order of precedence for the lifetime: s-maxage (shared), max-age, Expires minus Date, then heuristic. "If the cache is shared and the s-maxage response directive (Section 5.2.2.10) is present, use its value" (4.2.1)
- When directives conflict, honour the most restrictive. "If directives conflict (e.g., both max-age and no-cache are present), the most restrictive directive should be honored." (4.2.1)
- No heuristics when an explicit lifetime exists. "A cache MUST NOT use heuristics to determine freshness when an explicit expiration time is present in the stored response." (4.2.2)
- Heuristics apply only to heuristically cacheable status codes or responses marked cacheable (e.g., public). "heuristics can only be used on responses without explicit freshness whose status codes are defined as \"heuristically cacheable\"" (4.2.2)
- The old ban on heuristic freshness for URLs with a query string wasn't widely implemented. "In practice, this has not been widely implemented." (4.2.2)
- Age is the time spent in all caches on the path plus transit. "The Age value is therefore the sum of the time that the response has been resident in each of the caches along the path from the origin server, plus the time it has been in transit along network paths." (4.2.3)
- Stale may be served only when disconnected or explicitly permitted. "A cache MUST NOT generate a stale response unless it is disconnected or doing so is explicitly permitted by the client or origin server" (4.2.4)
- RFC 5861 extensions are one explicit permission. "extension directives such as those defined in [RFC5861]" (4.2.4)
- Validation uses conditional requests. "This process is known as \"validating\" or \"revalidating\" the stored response." (4.3)
- A cache must send the entity tags it has. "MUST send the relevant entity tags (using If-Match, If-None-Match, or If-Range) if the entity tags were provided in the stored response(s) being validated." (4.3.1)
- Caches usually send both validators for old intermediaries. "In most cases, both validators are generated in cache validation requests, even when entity tags are clearly superior" (4.3.1)
- If-None-Match takes precedence over If-Modified-Since. "If-None-Match takes precedence over If-Modified-Since." (4.3.2)
- A 304 means update the stored response and reuse it. "A 304 (Not Modified) response status code indicates that the stored response can be updated and reused" (4.3.3)
- On a 5xx during validation, a cache may forward it or act as if the server didn't answer. "if a cache receives a 5xx (Server Error) response while attempting to validate a response, it can either forward this response to the requesting client or act as if the server failed to respond." (4.3.3)
- A 304 updates the stored headers. "the cache MUST update its header fields with the header fields provided in the 304 (Not Modified) response" (4.3.4)
- Invalidation happens only in caches the request passes through. "a state-changing request would only invalidate responses in the caches it travels through." (4.4)
- Invalidation of Location/Content-Location URIs is optional, same origin only. "A cache MAY invalidate other URIs when it receives a non-error status code in response to an unsafe request method" (4.4)
- A proxy can't aim a directive at one cache. "It is not possible to target a directive to a specific cache." (5.2)
- Request directives are advisory. "They are advisory; caches MAY implement them, but are not required to." (5.2.1)
- max-age response: stale after that many seconds of age. "The max-age response directive indicates that the response is to be considered stale after its age is greater than the specified number of seconds." (5.2.2.1)
- must-revalidate: no stale reuse once stale, even if disconnected. "if a cache is disconnected, the cache MUST generate an error response rather than reuse the stale response." (5.2.2.2)
- must-revalidate is meant for cases where stale use would be incorrect. "such as a silently unexecuted financial transaction." (5.2.2.2)
- no-cache: may store, must validate before each reuse. "indicates that the response MUST NOT be used to satisfy any other request without forwarding it for validation and receiving a successful response" (5.2.2.4)
- no-cache holds even against caches configured to serve stale. "even by caches that have been configured to send stale responses." (5.2.2.4)
- The qualified forms of no-cache and private are often treated as unqualified. "the special handling for the qualified form is not widely implemented." (5.2.2.4)
- no-store is not a privacy mechanism. "This directive is not a reliable or sufficient mechanism for ensuring privacy." (5.2.2.5)
- private controls where it's stored, not privacy. "This usage of the word \"private\" only controls where the response can be stored; it cannot ensure the privacy of the message content." (5.2.2.7)
- public is unnecessary on responses that are already cacheable. "Note that it is unnecessary to add the public directive to a response that is already cacheable according to Section 3." (5.2.2.9)
- s-maxage also implies proxy-revalidate for shared caches. "The s-maxage directive incorporates the semantics of the proxy-revalidate response directive (Section 5.2.2.8) for a shared cache." (5.2.2.10)
- Unknown directives are ignored, which is how extensions deploy. "A cache MUST ignore unrecognized cache directives." (5.2.3)
- max-age overrides Expires. "If a response includes a Cache-Control header field with the max-age directive (Section 5.2.2.1), a recipient MUST ignore the Expires header field." (5.3)
- An invalid Expires such as "0" means already expired. "A cache recipient MUST interpret invalid date formats, especially the value \"0\", as representing a time in the past" (5.3)
- Very long lifetimes are allowed now, but caches evict far sooner. "many caches will evict a response far sooner than that." (5.3)
- Pragma is deprecated. "As a result, this specification deprecates Pragma." (5.4)
- Set-Cookie doesn't stop caching. "Note that the Set-Cookie response header field [COOKIE] does not inhibit caching" (7.3)
- Caching sensitive data by mistake usually comes from misunderstanding caches. "Implementation and deployment flaws (often led to by the misunderstanding of cache operation) might lead to the caching of sensitive information" (7.3)
- Timing attacks and double keying. "Such \"timing attacks\" can be mitigated by adding more information to the cache key, such as the identity of the referring site" (7.2)
