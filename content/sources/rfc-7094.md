## Summary

The IAB's look at anycast as architecture, not just operations. Main
worry: stateful transports like TCP assume one endpoint, and a routing
change mid-connection can send packets to a different anycast node.

## Key claims

- Apps should expect the routing system might send each anycast packet to a different instance. "it would perhaps be safe to assume that the routing system may deliver each anycast packet to a different service instance" (3.1)
- Unmodified TCP can fail with anycast under normal routing changes. "they will fail probabilistically, but possibly catastrophically, when using anycast addresses in the presence of \"normal\" routing dynamics." (3.1)
- UDP is the usual anycast transport. "UDP is the \"lingua franca\" for anycast today." (4.2)
- Observed failure: a TCP connection to an anycast DNS node gets split across instances when a route changes. "the TCP connection will likely elicit a connection reset but will certainly result in the disruption of the connection." (4.2)
- Aggregation can make some anycast sites unreachable because of longest match. "longest-match routing might result in some anycast locations being unreachable." (4.1)
- Despite the architecture concerns, TCP anycast is widely deployed, e.g. for CDNs. "there is expanding deployment (e.g., for content distribution networks)" (4.5)
- Evidence suggests TCP anycast isn't "safe" in the architectural sense. "Evidence exists to suggest that such practice is not \"safe\" in the traditional and architectural sense" (4.5)
- Summarizes RFC 4786's core rule: routing must "be stable" for longer than a transaction. (2.4)
