## Summary

The 2023 standards-track RFC that defines "problem details": a small
JSON (or XML) object, served as `application/problem+json`, that an
HTTP API puts in the body of an error response so clients get
machine-readable detail beyond the status code. It obsoletes RFC 7807,
adds a registry of common problem types, and says what to do when a
request has several problems.

## Key claims

- The goal is one common error format so APIs don't invent their own. "to avoid the need to define new error response formats for HTTP APIs." (Abstract)
- Status codes alone often aren't enough. "HTTP status codes (Section 15 of [HTTP]) cannot always convey enough information about errors to be helpful." (1)
- The status code is for generic software; the body is for the client's own logic. The out-of-credit example uses 403 "to inform generic HTTP software (such as client libraries, caches, and proxies) of the response's general semantics." (1)
- An occurrence URI helps support and forensics. "which can be useful for support or forensic purposes." (1)
- The format has a media type. "it uses the \"application/problem+json\" media type." (1)
- Worked example: `type` https://example.com/probs/out-of-credit, `title` "You do not have enough credit.", `detail` "Your current balance is 30, but that costs 50.", `instance`, plus extensions `balance` and `accounts`, returned with 403. (3)
- Validation example: 422 with an `errors` extension, each entry a `detail` and a JSON Pointer `pointer` such as `#/age`. "Each member is an object containing \"detail\" to describe the issue and \"pointer\" to locate the problem within the request's content using a JSON Pointer [JSON-POINTER]." (3)
- Several different problems: report the most important one. "it is RECOMMENDED that the most relevant or urgent problem be represented in the response." (3)
- `type` is the identifier clients should switch on. "Consumers MUST use the \"type\" URI (after resolution, if necessary) as the problem type's primary identifier." (3.1.1)
- Without a type, it's `about:blank`. "When this member is not present, its value is assumed to be \"about:blank\"." (3.1.1)
- `status` must repeat the real status code. "Generators MUST use the same status code in the actual HTTP response, to assure that generic HTTP software that does not understand this format still behaves correctly." (3.1.2)
- `title` is the same for every occurrence of a type. "It SHOULD NOT change from occurrence to occurrence of the problem, except for localization" (3.1.3)
- `detail` is for fixing the problem, not debugging. "The \"detail\" string, if present, ought to focus on helping the client correct the problem, rather than giving debugging information." (3.1.4)
- Don't parse `detail`. "Consumers SHOULD NOT parse the \"detail\" member for information; extensions are more suitable and less error-prone ways to obtain such information." (3.1.4)
- `instance` identifies this one occurrence. "The \"instance\" member is a JSON string containing a URI reference that identifies the specific occurrence of the problem." (3.1.5)
- Clients ignore extensions they don't know, so types can grow. "Clients consuming problem details MUST ignore any such extensions that they don't recognize; this allows problem types to evolve and include additional information in the future." (3.2)
- Problem details aren't for dumping internals. "Problem details are not a debugging tool for the underlying implementation; rather, they are a way to expose greater detail about the HTTP interface itself." (4)
- Generic problems don't need a type. "truly generic problems -- i.e., conditions that might apply to any resource on the Web -- are usually better expressed as plain status codes." (4)
- A new type must document a type URI, a short title and the status code. (4)
- Problem types can say to use Retry-After. "Problem type definitions MAY specify the use of the Retry-After response header ([HTTP], Section 10.2.3) in appropriate circumstances." (4)
- Avoid exposing stack dumps. "Generators providing links to occurrence information are encouraged to avoid making implementation details such as a stack dump available through the HTTP interface" (5)
- The `status` member and the real status can disagree if something in between changed it. "a disagreement might indicate that (for example) an intermediary has changed the HTTP status code in transit (e.g., by a proxy or cache)." (5)
- Changes from RFC 7807: a registry of common problem types, guidance on multiple problems, and on type URIs that can't be dereferenced. (Appendix D)
- It replaces RFC 7807. "Obsoletes: 7807" (header)
- A generic problem needs no type: a 403 to a PUT already explains itself. "a 403 Forbidden status code in response to a PUT request is self-explanatory." (4)
- Batch types that bundle several different problems fit HTTP badly. "While it is possible to create generic \"batch\" problem types that convey multiple, disparate types, they do not map well into HTTP semantics." (3)
