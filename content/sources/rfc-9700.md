## Summary

The OAuth security BCP (2025). Updates RFC 6749, 6750 and 6819 with a
decade of attacks: exact redirect URI matching, PKCE for everyone,
the implicit grant and password grant deprecated, sender-constrained
and audience-restricted tokens, refresh token rotation for public
clients.

## Key claims

- It updates the older specs and deprecates insecure modes. "it deprecates some modes of operation that are deemed less secure or even insecure." (Abstract)
- Redirect URIs must match exactly. "authorization servers MUST utilize exact string matching except for port numbers in localhost redirection URIs of native apps" (2.1)
- No open redirectors. "Open redirectors can enable exfiltration of authorization codes and access tokens." (2.1)
- Clients must prevent CSRF; PKCE counts if the server supports it. "Clients that have ensured that the authorization server supports Proof Key for Code Exchange (PKCE) [RFC7636] MAY rely on the CSRF protection provided by PKCE." (2.1)
- Public clients must use PKCE. "Public clients MUST use PKCE [RFC7636] to this end" (2.1.1)
- Confidential clients should too. "For confidential clients, the use of PKCE [RFC7636] is RECOMMENDED" (2.1.1)
- PKCE applies to web apps as well. "Although PKCE was designed as a mechanism to protect native apps, this advice applies to all kinds of OAuth clients, including web applications." (2.1.1)
- S256 is the only method that doesn't expose the verifier. "Currently, S256 is the only such method." (2.1.1)
- Servers must support PKCE. "Authorization servers MUST support PKCE [RFC7636]." (2.1.1)
- Implicit grant: don't use it. "clients SHOULD NOT use the implicit grant (response type token) or other response types issuing access tokens in the authorization response" (2.1.2)
- Sender-constrained tokens (mTLS or DPoP) prevent use of stolen tokens. "Authorization and resource servers SHOULD use mechanisms for sender-constraining access tokens, such as mutual TLS for OAuth 2.0 [RFC8705] or OAuth 2.0 Demonstrating Proof of Possession (DPoP) [RFC9449]" (2.2.1)
- Public client refresh tokens must be sender-constrained or rotated. "Refresh tokens for public clients MUST be sender-constrained or use refresh token rotation as described in Section 4.14." (2.2.2)
- Least privilege and audience restriction for access tokens. "access tokens SHOULD be audience-restricted to a specific resource server or, if that is not feasible, to a small set of resource servers." (2.3)
- The password grant must not be used. "The resource owner password credentials grant [RFC6749] MUST NOT be used." (2.4)
- It trains users to type passwords in the wrong place. "training users to enter their credentials in places other than the authorization server." (2.4)
- Asymmetric client authentication is recommended. "It is RECOMMENDED to use asymmetric cryptography for client authentication, such as mutual TLS for OAuth 2.0 [RFC8705] or signed JWTs" (2.5)
- Authorization responses never over plain HTTP. "Authorization responses MUST NOT be transmitted over unencrypted network connections." (2.6)
- Rotation: a replayed old refresh token reveals the breach and gets the active one revoked. "If a refresh token is compromised and subsequently used by both the attacker and the legitimate client, one of them will present an invalidated refresh token, which will inform the authorization server of the breach." (4.14.2)
- Otherwise, CSRF tokens in state. "Otherwise, one-time use CSRF tokens carried in the state parameter that are securely bound to the user agent MUST be used for CSRF protection" (2.1)
- The password grant doesn't fit two-factor or WebAuthn. "the resource owner password credentials grant is not designed to work with two-factor authentication and authentication processes that require multiple user interaction steps." and "Authentication with cryptographic credentials (cf. WebCrypto [W3C.WebCrypto], WebAuthn [W3C.WebAuthn]) may be impossible to implement with this grant type" (2.4)
- Servers should publish metadata so libraries can configure themselves. "It is therefore RECOMMENDED that authorization servers publish OAuth Authorization Server Metadata according to [RFC8414] and that clients make use of this Authorization Server Metadata (when available) to configure themselves." (2.6)
- On a replayed rotated refresh token the server revokes the active one, and the real client must get a new grant. "The authorization server cannot determine which party submitted the invalid refresh token, but it will revoke the active refresh token." (4.14.2)
