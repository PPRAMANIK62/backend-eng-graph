## Summary

A 2020 standards-track change that lets recursive resolvers keep
answering with expired records when the authoritative servers can't be
reached. It rewrites the TTL definition from RFC 1035, recommends a TTL
cap of 7 days, and says stale answers go out with a TTL of about 30
seconds.

## Key claims

- The goal: survive outages and DoS of authoritative servers. "This document defines a method (serve-stale) for recursive resolvers to use stale DNS data to avoid outages when authoritative nameservers cannot be reached to refresh expired data." (Abstract)
- Several resolvers already did this. "A number of recursive resolver packages, including BIND, Knot Resolver, OpenDNS, and Unbound, provide options to use stale data." (3)
- The new TTL definition: how long a record MAY be cached before the source MUST be asked again; zero means use for this transaction only. "Zero values are interpreted to mean that the RR can only be used for the transaction in progress, and should not be cached." (4)
- Recommended cap on TTLs: 7 days. "Values SHOULD be capped on the order of days to weeks, with a recommended cap of 604,800 seconds (7 days)." (4)
- If a refresh fails when the TTL runs out, the old record may still be used. "If the data is unable to be authoritatively refreshed when the TTL expires, the record MAY be used as though it is unexpired." (4)
- Stale records are sent with a small positive TTL, 30 seconds recommended. "a recursive resolver MUST set the TTL of each expired record in the message to a value greater than 0, with a RECOMMENDED value of 30 seconds." (4)
- Only NOERROR or NXDOMAIN answers with AA set count as a refresh. "Answers from authoritative servers that have a DNS response code of either 0 (NoError) or 3 (NXDomain) and the Authoritative Answer (AA) bit set MUST be considered to have refreshed the data at the resolver." (4)
- A client response timer of 1.8 s is suggested, just under a common 2 s client timeout. "a recommended value of 1.8 seconds as being just under a common timeout value of 2 seconds" (5)

## My notes

- This changes what "TTL" means in practice: the TTL is when a resolver
  must try to refresh, not a hard deadline after which old data is gone.
