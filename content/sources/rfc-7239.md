## Summary

The 2014 standard for the `Forwarded` request header, which replaces the
non-standard X-Forwarded-For/-By/-Proto family with one header that
carries, per proxy, the client (`for`), the proxy's own interface (`by`),
the original Host (`host`) and the scheme (`proto`). Also says plainly
that the header can't be trusted on its own.

## Key claims

- Proxies make requests look like they come from the proxy. "However, these proxies make the requests appear as if they originated from the proxy's IP address, and they may change other information in the original request." (1)
- Uses of the client address: diagnostics, access control, abuse handling. "The main uses of this information are for diagnostics, access control, and abuse management." (1)
- X-Forwarded-* are the common non-standard way. "A common way to disclose this information is by using the non-standard header fields such as X-Forwarded-For, X-Forwarded-By, and X-Forwarded-Proto." (1)
- Forwarded keeps each proxy's information together, which the X- headers can't. "Such conclusions are not possible to make with the X-Forwarded class of header fields." (1)
- Each proxy adds an element; the first element comes from the first proxy. "The first element in this list holds information added by the first proxy that implements and uses this header field, and each subsequent element holds information added by each subsequent proxy." (4)
- Example value with several parameters. "Forwarded: for=192.0.2.60;proto=http;by=203.0.113.43" (4)
- IPv6 addresses must be quoted. "Note that as \":\" and \"[]\" are not valid characters in \"token\", IPv6 addresses are written as \"quoted-string\"." (4)
- The last proxy isn't in the `for` list; the server sees it as the TCP peer. "The last proxy in the chain is not part of the list of \"for\" parameters." (5.2)
- `proto` lets a backend behind a TLS-terminating proxy know the client used https. "in an environment where a reverse proxy is also used as a crypto offloader, this allows the origin server to rewrite URLs in a document to match the type of connection as the user agent requested" (5.4)
- Converting X-Forwarded-For: prefix each element with `for=`. "this can be translated to \"Forwarded\", by prepending each element with \"for=\"." (7.4)
- The header can be changed by anyone on the way, including the client. "The \"Forwarded\" HTTP header field cannot be relied upon to be correct, as it may be modified, whether mistakenly or for malicious reasons, by every node on the way to the server, including the client making the request." (8.1)
- Trusting known proxies still leaves the earlier part of the chain untrusted. "First, the chain of IP addresses listed before the request came to the proxy cannot be trusted." (8.1)
- Worked example of two proxies (7.5): client 192.0.2.43, proxies 198.51.100.17 and 203.0.113.60; the origin sees `Forwarded: for=192.0.2.43, for=198.51.100.17;by=203.0.113.60;proto=http;host=example.com`.
- `by` is the interface where the request reached the proxy. "The \"by\" parameter is used to disclose the interface where the request came in to the proxy server." (5.1)
- `host` carries the original Host header. "The \"host\" parameter is used to forward the original value of the \"Host\" header field." (5.3)
