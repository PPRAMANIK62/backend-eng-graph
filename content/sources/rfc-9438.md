## Summary

The Standards Track spec for CUBIC, obsoleting RFC 8312. CUBIC grows
the congestion window as a cubic function of time since the last
congestion event, flattening out near the window where loss last
happened. Written by the algorithm's designers.

## Key claims

- CUBIC is the default in Linux, Windows and Apple stacks. "CUBIC has been adopted as the default TCP congestion control algorithm by the Linux, Windows, and Apple stacks." (Abstract)
- It's the most widely deployed standard for TCP congestion control. "It is therefore to be regarded as the currently most widely deployed standard for TCP congestion control." (1)
- It fixes Reno's slow growth after a loss on large-BDP paths. "This problem arises from a slow increase of the congestion window (cwnd) following a congestion event in a network with a large bandwidth-delay product (BDP)." (1)
- The Reno problem shows up even at windows of a few hundred packets. "[HLRX07] indicates that this problem is frequently observed even in the range of congestion window sizes over several hundreds of packets." (1)
- K is how long the function takes to get back to W_max. "_K_ is the time period that the above function takes to increase the congestion window size at the beginning of the current congestion avoidance stage to _W_max_ if there are no further congestion events." (4.2)
- BIC-TCP, its predecessor, became Linux's default in 2005. "Binary Increase Congestion Control (BIC-TCP) [XHR04], a predecessor of CUBIC, was selected as the default TCP congestion control algorithm by Linux in the year 2005" (1)
- Growth is concave up to the last loss point, then convex. "The cubic function is set to have its plateau at the remembered congestion window size, so that the concave window increase continues until then. After that, the cubic function turns into a convex profile and the convex window increase begins." (3.1)
- The window function is W_cubic(t) = C * (t - K)^3 + W_max, with t the time since the congestion avoidance stage began. (4.2, Figure 1)
- Growth depends on time, not RTT, so flows with different RTTs get closer to equal windows. "CUBIC maintains a window increase rate that is independent of RTTs outside the Reno-friendly region" (3.3)
- Multiplicative decrease factor is 0.7, Reno's is 0.5. "CUBIC sets the multiplicative window decrease factor to 0.7, whereas Reno uses 0.5." (3.4)
- C should be 0.4. "Therefore, _C_ SHOULD be set to 0.4." (5.1)
- Where the cubic curve would be slower than Reno, CUBIC follows Reno. "The region where CUBIC behaves like Reno is called the \"Reno-friendly region\"." (3.2)
- CUBIC SHOULD use HyStart++ for slow start. "In general, CUBIC SHOULD use the HyStart++ slow start algorithm [RFC9406]" (4.10)
- Still loss (or ECN) driven: it reacts to congestion events found by duplicate ACKs, ECN-Echo, RACK-TLP or QUIC loss detection. (3.1)
