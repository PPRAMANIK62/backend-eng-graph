## Summary

OWASP's guide to web sessions: what a session ID must look like (random,
meaningless, at least 64 bits of entropy), how to carry it (cookies, over
TLS, with Secure, HttpOnly, SameSite and `__Host-`), when to replace it
(login and any privilege change), and how to end it (idle, absolute and
renewal timeouts, and logout that kills the session on the server).

## Key claims

- After login the session ID is as good as the password. "Once an authenticated session has been established, the session ID (or token) is temporarily equivalent to the strongest authentication method used by the application" (Introduction)
- Stolen, guessed or fixed IDs mean full impersonation. "The disclosure, capture, prediction, brute force, or fixation of the session ID will lead to session hijacking (or sidejacking) attacks, where an attacker is able to fully impersonate a victim user in the web application." (Introduction)
- Entropy. "Session identifiers must have at least 64 bits of entropy to prevent brute-force session guessing attacks." (Session ID Entropy)
- From a CSPRNG. "A strong CSPRNG (Cryptographically Secure Pseudorandom Number Generator) must be used to generate session IDs." (Session ID Entropy)
- Their example: 64 bits, 10,000 guesses a second and 100,000 live sessions gives about 585 years. "an attacker can expect to spend approximately 585 years to successfully guess a valid session ID, assuming the attacker can try 10,000 guesses per second with 100,000 valid simultaneous sessions available in the application." (Session ID Entropy, note)
- The ID must mean nothing. "The session ID content (or value) must be meaningless to prevent information disclosure attacks" (Session ID Content)
- The data lives on the server. "The meaning and business or application logic associated with the session ID must be stored on the server side, and specifically, in session objects or in a session management database or repository." (Session ID Content)
- Making your own: 128 bits. "If you need to create your own sessionID, use a cryptographically secure pseudorandom number generator (CSPRNG) with a size of at least 128 bits and ensure that each sessionID is unique." (Session ID Content)
- IDs in URLs leak. "might disclose the session ID (in web links and logs, web browser history and bookmarks, the Referer header or search engines)" (Session Management Implementation)
- Prefer the framework's session code. "It is recommended to use these built-in frameworks versus building a home made one from scratch" (Built-in Session Management Implementations)
- TLS for the whole session. "it is essential to use an encrypted HTTPS (TLS) connection for the entire web session, not only for the authentication process where the user credentials are exchanged." (Transport Layer Security)
- HttpOnly protects confidentiality, not use. "The HttpOnly cookie only protects the confidentiality of the cookie; the attacker cannot use it offline, outside of the context of an XSS" (HttpOnly Attribute)
- SameSite is defense in depth, and the browser default varies. "Never use SameSite=None without Secure, and do not rely on the browser-default value, which varies across browsers and versions." (SameSite Attribute)
- Recommended cookie. "Set-Cookie: __Host-SessionID=<value>; Secure; HttpOnly; SameSite=Strict; Path=/" (Cookie Name Prefixes)
- Strict handling: never accept an ID you didn't issue. "Web applications should never accept a session ID they have never generated, and in case of receiving one, they should generate and offer the user a new valid session ID." (Session ID Generation and Verification)
- Renew the ID on privilege change, especially login. "The session ID must be renewed or regenerated by the web application after any privilege level change within the associated user session." (Renew the Session ID After Any Privilege Level Change)
- That's what stops fixation. "The session ID regeneration is mandatory to prevent session fixation attacks, where an attacker sets the session ID on the victim user's web browser instead of gathering the victim's session ID" (Renew the Session ID After Any Privilege Level Change)
- Typical timeouts. "Common idle timeouts ranges are 2-5 minutes for high-value applications and 15-30 minutes for low risk applications." (Session Expiration)
- Invalidate on the server. "When a session expires, the web application must take active actions to invalidate the session on both sides, client and server. The latter is the most relevant and mandatory from a security perspective." (Session Expiration)
- Idle timeout doesn't stop an attacker who keeps the session busy. "if the attacker is able to hijack a given session, the idle timeout does not limit the attacker's actions, as they can generate activity on the session periodically to keep the session active for longer periods of time." (Idle Timeout)
- Enforce timeouts server side. "Session timeout management and expiration must be enforced server-side." (Idle Timeout)
- Absolute timeout caps a hijack. "The absolute session limits the amount of time an attacker can use a hijacked session and impersonate the victim user." (Absolute Timeout)
- Session IDs must not be cached. "it is highly recommended to include the Cache-Control: no-store directive in responses containing session IDs." (Web Content Caching and Clear-Site-Data)
- Renewal timeout: rotate the ID mid-session. "Alternatively, the web application can implement an additional renewal timeout after which the session ID is automatically renewed, in the middle of the user session, and independently of the session activity and, therefore, of the idle timeout." (Renewal Timeout)
- Reauthenticate after risky events (password or email change, new device or IP, account recovery). "Web applications should require reauthentication after high-risk events such as" (Reauthentication After Risk Events)
- Why not web storage. "These APIs are accessible to any JavaScript executing in the origin, so a single XSS vulnerability discloses every token." (The localStorage API)
- No tokens in web storage. "Do not store authentication tokens, session IDs, JWTs, refresh tokens, or any credential in localStorage or sessionStorage." (The localStorage API)
