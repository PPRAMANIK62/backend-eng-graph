## Summary

Best Current Practice 230. Defines link MTU and path MTU, explains how
IPv4 and IPv6 fragment packets and how path MTU discovery works, then
lists every way fragments and discovery break on the real internet
(NAT, firewalls, load balancers, ICMP loss, anycast). Its advice: new
protocols should not rely on IP fragmentation.

## Key claims

- Link MTU, and the minimums. "IPv4 [RFC0791] requires every link to support an MTU of 68 octets or greater (see NOTE 1). IPv6 [RFC8200] similarly requires every link to support an MTU of 1280 octets or greater." (2.1)
- Path MTU is the smallest link MTU on the path, and changes when the path does. "For any given path, the PMTU is equal to the smallest of its link MTUs. Because Internet paths are dynamic, PMTU is also dynamic." (2.1)
- PMTUD: send non-fragmentable packets; a router that can't forward one drops it and returns ICMP Packet Too Big with the next link's MTU. "The ICMP PTB message indicates the MTU of the link through which the packet could not be forwarded." (2.1)
- PMTUD fails if Packet Too Big can't reach the sender, and ICMP is easy to forge. "If the network cannot deliver ICMP PTB messages to the source node, PMTUD fails." (2.1)
- 576 is a reassembly minimum, not the minimum MTU. "In IPv4, every host must be able to reassemble a packet whose length is less than or equal to 576 octets." (2.1, NOTE 1)
- DF=1 means routers may not fragment; all IPv6 packets are like that. "An IPv4 packet whose DF bit is set to 1 is non-fragmentable. All IPv6 packets are also non-fragmentable." (2.1, NOTE 2)
- ICMPv4 PTB is Destination Unreachable code 4; ICMPv6 PTB is its own message type. "In ICMPv4 [RFC0792], the ICMP PTB message is a Destination Unreachable message with Code equal to 4 (fragmentation needed and DF set)." (2.1, NOTE 3)
- IPv6 fragments only at the source. "An IPv6 packet may be fragmented only at the source node." (2.2)
- PLPMTUD probes with real packets and uses acknowledgements instead of ICMP. "Therefore, PLPMTUD does not rely on the network's ability to deliver ICMP PTB messages to the source." (2.3)
- NAT devices must virtually reassemble fragments to translate them. "the NAT device must virtually reassemble fragmented packets in order to translate and forward each fragment." (3.3)
- Stateless firewalls see ports only in the first fragment. "Because port information is only available in the first fragment and not available in the subsequent fragments, the firewall is limited to the following options" (3.4)
- ECMP/load balancers hash later fragments on 3 fields instead of 5, so one flow can be split across links. (3.5)
- IPv4's 16-bit ID wraps at high rates and fragments get misassembled. "At high data rates, the 16-bit IP identification field is not large enough to prevent duplicate IDs, resulting in frequent incorrectly assembled IP fragments" (3.6)
- Packet Too Big delivery is unreliable (congestion, rate limiting, broken firewalls on consumer routers, anycast, one-way routing). "However, ICMP PTB delivery is not reliable." (3.8)
- Many consumer routers drop valid Packet Too Big messages. "The security policy described above has been implemented incorrectly on many consumer CPE routers." (3.8.2)
- Anycast: the PTB goes to the nearest instance of the anycast address, which may not be the sender. (3.8.3)
- Fragments are often dropped outright. "The study revealed that at least 28% of the sampled paths did not convey packets containing the IPv6 Fragment extension header." (3.9)
- TCP avoids fragmentation by keeping segments under the MSS. "If the TCP MSS is sufficiently small, then the underlying IP module never produces a packet whose length is greater than the actual PMTU." (4.1)
- DNS over UDP still relies on fragmentation for large responses; truncation then retry over TCP is the workaround. (5.1)
- Recommendation. "Developers SHOULD NOT develop new protocols or applications that rely on IP fragmentation." (6.1)
- It does not deprecate fragmentation. "While this document identifies issues associated with IP fragmentation, it does not recommend deprecation." (1)

Added (audit) for `mtu-and-fragmentation`:

- It's a Best Current Practice. "BCP: 230" and "Category: Best Current Practice" (header)
- A stateless firewall can only accept or block all later fragments. "Accept all subsequent fragments, possibly admitting certain classes of attack." (3.4)
- Fragments of a flow can be split across links. "fragmented packets belonging to the same flow can be divided between that link and another." (3.5)
- Checksums don't catch misassembled fragments. "the TCP and UDP checksums are insufficient to prevent the resulting corrupted datagrams from being delivered to upper-layer protocols." (3.6)
- Lost Packet Too Big messages cause PMTU black holes. "Transient loss of ICMP PTB messages can cause transient PMTU black holes." (3.8)
- DNSSEC makes some DNS responses too big to prune. "One scenario where such pruning is ineffective is in the use of DNSSEC, where large key sizes act to increase the response size to certain DNS queries." (5.1)
