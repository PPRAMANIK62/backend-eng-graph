## Summary

The IPv4 path MTU discovery method: send everything with Don't Fragment
set, and shrink your packet size when a router sends back "fragmentation
needed". Adds the Next-Hop MTU field to that ICMP message so the sender
knows how far to shrink. IPv6's version is RFC 8201.

## Key claims

- Path MTU is the smallest MTU on the path. "This datagram size is referred to as the Path MTU (PMTU), and it is equal to the minimum of the MTUs of each hop in the path." (1. Introduction)
- Before this, hosts used 576 or the first hop's MTU for remote destinations. "The current practice [1] is to use the lesser of 576 and the first-hop MTU as the PMTU for any destination that is not connected to the same network or subnet as the source." (1. Introduction)
- The method. "The basic idea is that a source host initially assumes that the PMTU of a path is the (known) MTU of its first hop, and sends all datagrams on that path with the DF bit set." (2. Protocol overview)
- The router drops the packet and sends Destination Unreachable, fragmentation needed; the source shrinks its estimate. "Upon receipt of such a message (henceforth called a "Datagram Too Big" message), the source host reduces its assumed PMTU for the path." (2. Protocol overview)
- New field: the router reports the MTU of the hop that was too small. "we propose that a currently unused header field in the Datagram Too Big message be used to report the MTU of the constricting hop." (2. Protocol overview)
- Probing for a bigger PMTU must be rare. "An attempt to detect an increase (by sending a datagram larger than the current estimate) MUST NOT be done less than 5 minutes after a Datagram Too Big message has been received for the given destination" (3. Host specification)
- Recommended timers are double the minimums: 10 minutes and 2 minutes. (3. Host specification)
