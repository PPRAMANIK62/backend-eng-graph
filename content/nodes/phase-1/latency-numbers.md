# Latency numbers every design sits on

A cache hit takes about a nanosecond. A round trip to another continent
takes a few hundred milliseconds. That's a factor of a hundred million, and
almost every backend design decision is about where in that range your
work lands. As a [[backend-engineer]], you need a feel for these numbers
before you build anything, and you should know which ones you measured and
which ones you copied.

## The table everyone quotes

In 2009 Jeff Dean put a slide called "Numbers Everyone Should Know" in a
talk on building large distributed systems at Google. It's the version
most people have seen:

| Operation | Dean, 2009 |
|---|---|
| L1 cache reference | 0.5 ns |
| L2 cache reference | 7 ns |
| Main memory reference | 100 ns |
| Read 1 MB sequentially from memory | 250 µs |
| Round trip within the same datacenter | 500 µs |
| Disk seek | 10 ms |
| Read 1 MB sequentially from disk | 20 ms |
| Packet California to Netherlands and back | 150 ms |

The point of the slide was the next one: use these numbers to estimate a
design before you build it. Dean's example was a page of 30 image
thumbnails. Read them one after another from disk, with a seek each, and
you pay about 30 × 10 ms for seeks plus the transfer time, around 560 ms.
The table tells you that design is slow before you write a line of code.

A popular interactive version lets you slide the year and watch the
numbers change. Its base numbers come from Peter Norvig's list from 2002,
and its source code shows that most values after 2002 are **projections**:
exponential curves fitted to old data. Memory latency is held flat at
100 ns for every year after 2000. SSD random reads are held at 16 µs after
2014. The datacenter round trip is fixed at 500 µs with a comment
asking whether it changes much. Those are estimates, not measurements, and
the table has no row at all for the machine you're running on.

## The same numbers, measured on this laptop

So we measured our own. The lab machine is a laptop with an Intel
i5-13500H, Linux 7.1.9, an NVMe SSD under btrfs and dm-crypt, on home
Wi-Fi in India. The full setup and raw data are in
[experiment 0001](../../experiments/0001-latency-numbers-on-my-laptop.md).
All CPU tests were pinned to one core; values are medians.

| Operation | This laptop (2026-09-28) |
|---|---|
| Load from L1 (16 KiB working set) | 1.1 ns |
| Load from L2 (256 KiB – 1 MiB) | 3.8 – 6.1 ns |
| Load from L3 (2 – 8 MiB) | 11.5 – 18.8 ns |
| Load from RAM (64 MiB – 1 GiB) | 104 – 125 ns |
| Read 256 MiB sequentially from RAM | 14.7 ms (18.3 GB/s) |
| Empty [[system-call]] (`getppid`) | 64 ns |
| Pipe round trip, two [[context-switch\|context switches]] | 1.7 µs |
| Random 4 KiB SSD read, `O_DIRECT` | 49.8 µs (p99.9: 249 µs) |
| Ping to the home router | 1.7 ms best, 4.0 ms average |
| TCP handshake to AWS Mumbai | 76.5 ms |
| … AWS Singapore | 107.7 ms |
| … AWS Ireland | 212.3 ms |
| … AWS Oregon | 295.0 ms |
| … AWS Virginia | 318.9 ms |
| … AWS São Paulo | 395.2 ms |

Read it as ratios. A RAM access that misses every cache costs about 100
L1 hits. A random SSD read costs about 400 RAM misses. The home router
costs as much as dozens of SSD reads. One round trip to Virginia from here
costs about as much time as 300 million L1 hits.

## Measuring a latency, not a throughput

The memory rows are the easiest to get wrong. A modern CPU can have many
loads in flight at once. If your test reads addresses it could have
guessed, or loads that don't depend on each other, the CPU overlaps them
and you measure how many loads per second it can finish, not how long one
takes.

The fix is old. The lmbench paper from 1996 laid out four meanings of
"memory latency" and picked the one software can measure: **back-to-back
dependent loads**. Build a linked list and walk it, `p = p->next`, so each
load needs the result of the one before. Nothing overlaps, and the time per
step is the latency. Walk lists of different sizes, and the result is a
staircase: a flat step while the list fits in one level of the
[[memory-hierarchy]], then a rise where it spills into the next.

Our chase test is that method with two changes. The list is a random cycle,
one node per 64-byte cache line, so the prefetcher can't guess the next
address. And it runs 50 million loads per size, 11 times. The staircase
shows up clearly: about 1 ns in L1, 4 to 6 ns in L2, 12 to 19 ns in L3, and
104 to 125 ns once the working set is far past the 18 MiB L3. The slow
climb from 104 ns at 64 MiB to 125 ns at 1 GiB is probably partly the
TLB: with 4 KiB pages, big working sets also miss on address translations
(see [[virtual-memory]]). The test didn't measure that separately.

![Line chart of nanoseconds per load against working-set size, both on log scales. It rises from 1.1 ns at 16 KiB, through 3.8 ns at 256 KiB and 18.8 ns at 8 MiB, climbs steeply past the 18 MiB L3 size, and flattens between 104 ns at 64 MiB and 125 ns at 1 GiB.](img/memory-hierarchy-staircase.svg)

*Average time per dependent load, median of 11 runs, from [experiment 0001](../../experiments/0001-latency-numbers-on-my-laptop.md), generated by `visuals/charts.py`. Only the L3 size is marked: `lscpu` reports L1 and L2 as totals across mixed core types.*

The same care applies to the kernel rows. Popular calls like `getpid`
get heavily optimized, so our test used `getppid` through the raw
`syscall()` function. And a pipe round trip includes pipe work, so it's an upper bound
on what the context switches cost.

## The network is mostly distance

Everything on a single machine is under a millisecond. The network is where
the milliseconds come from, and most of it is the distance the signal has
to travel.

Our numbers are from a home connection: Wi-Fi, the ISP, then the internet
to each AWS region's public endpoint. We assumed each endpoint answers from
inside the region it's named for, and didn't verify it. For comparison, Microsoft publishes median round trips between Azure regions, measured by
probes on its own network over 30 days (the set read here ends on
2026-07-30):

| Azure regions | Median round trip |
|---|---|
| West Europe to UK South | 11 ms |
| Southeast Asia to Central India | 53 ms |
| East US to West US | 69 ms |
| West Europe to Central India | 140 ms |
| East US to Central India | 198 ms |

Two things stand out. Within a continent, a region-to-region hop is tens
of milliseconds. Across the world it's 150 to 200 ms, close to Dean's 2009
figure, because the speed of light hasn't changed. And our home-to-cloud
numbers are higher than the backbone ones: Singapore from our Wi-Fi was
108 ms, while Azure's Southeast Asia to Central India is 53 ms. Different
clouds and paths, so it's not a clean comparison, but the last mile and the
public internet add real time.

## Where it gets tricky

**Tables disagree, and each is right for its machine.** Main memory is
100 ns in Dean's table, "just over 70 ns" on a 2024 AMD desktop with DDR5,
104 to 125 ns on our laptop, and 20 ns for random reads in a 2026 table of
rounded numbers measured on a Google Cloud server. That last one probably
lets loads overlap, which our test deliberately prevents; its README
doesn't say, so treat it with care. The same 2026 table puts a context
switch at 10 µs and a system call at 300 ns, several times our numbers.
Different hardware, different tests.

**Memory latency has barely moved.** The 2024 desktop's 70 ns about
matches a Haswell-era i7-4770 with DDR3. New memory brings bandwidth, not
lower latency. That's why the projections hold memory flat after 2000, and
why CPUs keep adding cache instead (Zen 5 grew its L1 data cache by half).

**Medians hide the tail.** Our SSD read's median was 49.8 µs, its p99.9
was 249 µs and its worst was 1.8 ms. The router ping ranged from 1.7 ms to
33 ms. A request that makes many such calls will hit the slow ones. What
happens inside the drive is [[ssd-internals]].

**Our SSD number isn't the drive's.** The read went through btrfs checksums
and dm-crypt decryption, and used `O_DIRECT` to skip the
[[page-cache]], so it includes the cost of both layers. How much they add
hasn't been measured yet. How [[direct-io]] bypasses the cache is its own
article.

**Direction matters.** In Azure's data, East US to East US 2 is 8 ms and
the reverse is 9 ms. Round trips aren't always symmetric.

## What this means when you build

- Estimate before you build. Count the RAM misses, disk reads and round
  trips a request makes and multiply. The design that needs five
  cross-region round trips per request is slow no matter how fast the code
  is.
- Keep hot data close: in cache, then RAM, then local SSD, then the
  network. Each step down costs tens to thousands of times more.
- Batch across the network. One round trip that carries 100 items beats
  100 round trips of one item, because the distance cost is paid once.
- Plan for the tail, not the median.
- Measure on your own hardware, pin to a core, and write down the setup.
  A number without its machine and method is only a rough guess.

- [Designs, Lessons and Advice from Building Large Distributed Systems](https://www.cs.cornell.edu/projects/ladis2009/talks/dean-keynote-ladis2009.pdf), Jeff Dean, 2009. The original "Numbers Everyone Should Know" slide and the back-of-the-envelope example.

- [napkin-math](https://github.com/sirupsen/napkin-math), Simon Eskildsen, 2026. A modern, measured, rounded table with throughput alongside latency.
- [AMD's Ryzen 9950X: Zen 5 on Desktop](https://chipsandcheese.com/p/amds-ryzen-9950x-zen-5-on-desktop), Chester Lam, 2024. A current desktop's memory latency, and why it hasn't improved.
- [Azure network round-trip latency statistics](https://learn.microsoft.com/en-us/azure/networking/azure-network-latency), Microsoft, 2026. Measured median round trips between cloud regions, with the method.
