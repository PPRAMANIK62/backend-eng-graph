## Summary

A 2017 standards-track RFC adding the `immutable` Cache-Control
extension: the server promises the response won't change while it's
fresh, so clients can skip revalidating it, even when the user presses
reload. Aimed at versioned URLs.

## Key claims

- Fresh responses can still change on the origin during their lifetime; that's allowed. "However, it is still possible that the resource will be modified during that period." (1)
- A reload makes conditional requests, and a page can issue hundreds of them. "A user agent that understands HTML and fetches its dependent sub-resources might issue hundreds of conditional requests to refresh all portions of a common page [REQPERPAGE]." (1)
- Versioned URLs: a change is published under a new URL. "When these resources need an update, they are simply published under a new URL, typically embedding an identifier unique to that version of the resource in the path" (1)
- Versioned URLs allow very long lifetimes. "This design pattern allows a very large freshness lifetime to be used for the sub-resource without guessing when it will be updated in the future." (1)
- The client can't tell versioned URLs apart, so reloads waste 304s. "As a result, user-driven refreshes still translate into wasted conditional requests for each sub-resource as each will return 304 responses." (1)
- Meaning of immutable. "the immutable Cache-Control extension indicates that the origin server will not update the representation of that resource during the freshness lifetime of the response." (2)
- Clients skip conditional requests while fresh, except on force reload. "Clients SHOULD NOT issue a conditional request during the response's freshness lifetime (e.g., upon a reload) unless explicitly overridden by the user (e.g., a force reload)." (2)
- It only applies while fresh. "Stale responses SHOULD be revalidated as they normally would be in the absence of the immutable extension." (2)
- Proxies should skip revalidating fresh immutable responses too. "proxies SHOULD skip conditionally revalidating fresh responses containing the immutable extension unless there is a signal from the client that a validation is necessary" (2.1)
- Example. "Cache-Control: max-age=31536000, immutable" (2.2)
- It pins content, so it amplifies cache poisoning; clients should ignore it outside HTTPS. "Clients SHOULD ignore the immutable extension from resources that are not part of an authenticated context such as HTTPS." (3)

## My notes

- 31536000 s is 365 days.
- MDN says Chrome didn't implement immutable and instead stopped
  revalidating subresources on reload (see `mdn-http-caching`).
