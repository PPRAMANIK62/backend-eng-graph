## Summary

A 2022 best current practice (BCP 56) for people who define protocols
and APIs on top of HTTP. Its core rule is that HTTP's methods, status
codes and existing headers have generic meanings that apply to every
resource, so an application must not redefine them. It gives advice on
GET, OPTIONS, status codes, caching and multiple requests.

## Key claims

- HTTP's value is its generic semantics. "Much of the value of HTTP is in its generic semantics -- that is, the protocol elements defined by HTTP are potentially applicable to every resource and are not specific to a particular context." (3.1)
- Applications must not redefine methods, status codes or existing headers. "Therefore, applications that use HTTP MUST NOT redefine, refine, or overlay the semantics of generic protocol elements such as methods, status codes, or existing header fields." (3.1)
- Promising one exact status code makes clients brittle. "A POST request MUST result in a 201 (Created) response." (3.1, given as the bad example)
- Stick to registered methods. "Applications that use HTTP MUST confine themselves to using registered HTTP methods such as GET, POST, PUT, DELETE, and PATCH." (4.5)
- GET must not have significant side effects because software retries it. "since implementations can and do retry HTTP GET requests that fail." (4.5.1)
- Content in a GET has no meaning. "content in a GET is not recommended, has no meaning, and will be either ignored or rejected by generic HTTP software" (4.5.1)
- Status codes come from components other than your app. "First, status codes are often generated by components other than the application itself." (4.6)
- Who else generates codes: network errors, captive portals, proxies, CDNs, overloaded servers. "when a captive portal, proxy, or content delivery network is present; or when a server is overloaded or thinks it is under attack." (4.6)
- A standard format exists for error details. "[PROBLEM-DETAILS] provides one way to do so." (4.6)
- Use the general codes when unsure, and put detail in the body. "making generous use of the general status codes (200, 400, and 500) when in doubt." (4.6)
- Clients must handle unknown codes by class. "e.g., 499 can be safely handled as 400 (Bad Request) by clients that don't recognise it" (4.6)
- The reason phrase has no function and HTTP/2 doesn't carry it. "the reason phrase has no function in HTTP, is not guaranteed to be preserved by implementations, and is not carried at all in the HTTP/2 [HTTP/2] message format." (4.6)
- In HTTP/1, parallel requests usually mean several connections. "In HTTP/1 [HTTP/1.1], parallel requests are most often supported by opening multiple connections." (4.11)
- Order between separate requests isn't guaranteed. "If two requests need strict ordering, the only reliable way to ensure the outcome is to issue the second request when the final response to the first has begun." (4.11)
- Don't tie meaning to the connection. "Applications MUST NOT make assumptions about the relationship between separate requests on a single transport connection" (4.11)
- Standards shouldn't squat on fixed URL paths; links are recommended instead. "Instead of statically defining URI components like paths, it is RECOMMENDED that applications using HTTP define and use links [WEB-LINKING] to allow flexibility in deployment." (3.2)
- Links give a natural way to extend and version. "The use of links also offers a natural mechanism for extensibility, versioning, and capability management because the document containing the links can also contain information about their targets." (3.2)
- A fixed "/app/v1" prefix is common for a single-deployment API but wrong for an IETF standard. "while it is common practice for a specification of a single-deployment API to specify the path prefix \"/app/v1\" (for example), doing so in an IETF specification is inappropriate." (4.4)
- Clients usually start from one discovery document with links. "a client will begin interacting with a given application server by requesting an initial document that contains information about that particular deployment, potentially including links to other relevant resources." (4.4.1)
