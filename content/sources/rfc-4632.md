## Summary

The current CIDR document (BCP 122), obsoleting RFC 1519. Explains why
the class A/B/C system was dropped, how prefix ("slash") notation works,
how addresses are handed out (IANA to RIRs to ISPs), and the rules for
longest-match forwarding and aggregation.

## Key claims

- It replaced the original CIDR spec after more than twelve years. "This document obsoletes the original CIDR spec [RFC1519], with changes made both to clarify the concepts it introduced and, after more than twelve years, to update the Internet community on the results of deploying the technology described." (1)
- In the class system, the all-zeros and all-ones host values were reserved for network and broadcast addresses, so a class C held 254 hosts. "(minus special bit values reserved for network/broadcast addresses)" and "254 end systems (256 bit combinations minus the reserved all-zeros and all-ones patterns)" (2)
- By 1992 three problems were clear: class B exhaustion, routing table growth, and eventual IPv4 exhaustion. "Exhaustion of the Class B network address space." (2, problem 1)
- Class C (254 hosts) was too small, class B (65,534 hosts) too big for most. "Class C, with a maximum of 254 host addresses, is too small, whereas Class B, which allows up to 65534 host addresses, is too large for most organizations" (2)
- CIDR didn't try to solve IPv4 exhaustion, only to buy time. "It did not and does not attempt to solve the third problem" (2)
- Classes were replaced with prefixes of any length. "The solution that the community created was to deprecate the Class A/B/C network address assignment system in favor of using \"classless\", hierarchical blocks of IP addresses (referred to as prefixes)." (3)
- CIDR was meant to last three to five years and is still here. "CIDR has far outlasted its anticipated lifespan and has become the mid-term solution" (3)
- Slash notation: the number after "/" is how many leading bits are the network. "followed by the \"/\" (slash) character, followed by a decimal value between 0 and 32 that describes the number of significant bits." (3.1)
- Example: 172.16.0.0 with mask 255.255.0.0 is 172.16.0.0/16. "the legacy \"Class B\" network 172.16.0.0, with an implied network mask of 255.255.0.0, is defined as the prefix 172.16.0.0/16" (3.1)
- A prefix is any power-of-two block from 1 to 2^32 addresses. "prefixes may be defined to describe any power of two-sized block of between one and 2^32 end system addresses." (3.1)
- IANA hands /8 blocks (2^24 addresses) to the Regional Internet Registries, which hand smaller blocks to ISPs. "These allocations are made in contiguous bit-aligned blocks of 2^24 addresses (a.k.a. /8 prefixes)." (3.1)
- Table: /32 is 1 address ("host route"), /24 is 256, /16 is 65,536, /8 is 16,777,216, /0 is all 4,294,967,296 ("default route"). (3.1, table)
- The mask can't be inferred from the address any more, so routing protocols must carry it. "it is not possible to infer the network mask from the initial bit pattern of an IPv4 address." (5)
- Equipment that works in classes can't be trusted on the Internet. "Equipment that organizes its routing/forwarding information according to legacy Class A/B/C network/subnet conventions cannot be expected to work correctly on networks connected to the global Internet" (5)
- Forwarding uses the longest match. "Forwarding in the Internet is done on a longest-match basis." (5.1, rule 1)
- A router announcing an aggregate must drop packets for parts of it it can't reach (a "null" route), or loops form. "the \"next hop\" for the aggregate route should be the null destination." (5.1, rule 2)
- 0.0.0.0/0 is the default route and must be accepted. "the degenerate route to prefix 0.0.0.0/0 is used as a default route and MUST be accepted by all implementations." (5.1)
- The mask must be contiguous. "The only outstanding constraint is that the mask must be left contiguous." (5.1)

Added (audit) for `ip-addressing`:

- The prefix table labels /31 as a point-to-point link: "n.n.n.x/31 2 2147483648 \"p2p link\"" (3.1, table)
- CIDR was meant to be short-term. "this addressing plan was intended to be a relatively short-term response, lasting approximately three to five years" (3)
- The ROAD group met in 1992 and named the three problems. "… and identified three major problems" (2)
- Routing table growth was the second problem. "Growth of routing tables in Internet routers beyond the ability of current software, hardware, and people to effectively manage." (2, problem 2)
- Prefixes follow the topology so they can be aggregated, along provider-subscriber lines. "The assignment of prefixes is intended to roughly follow the underlying Internet topology so that aggregation can be used to facilitate scaling of the global routing system." (3)
