## Summary

The 2016 spec for DNS over TLS (DoT): ordinary DNS messages, with their
TCP length prefix, sent inside a TLS session on TCP port 853. It covers
connection reuse, two privacy profiles (opportunistic and key-pinned),
the extra latency and state, and what TLS still leaks. Scoped to the hop
from a stub resolver to its recursive resolver.

## Key claims

- DNS queries are almost all sent in the clear. "Today, nearly all DNS queries [RFC1034] [RFC1035] are sent unencrypted, which makes them vulnerable to eavesdropping by an attacker that has access to the network channel" (1)
- DNSSEC gives integrity, not privacy. "By intention, DNSSEC does not protect request and response privacy." (1)
- Scope: stub to recursive. "This document focuses on securing stub-to-recursive traffic, as per the charter of the DPRIVE Working Group." (Abstract)
- Port 853 by default. "By default, a DNS server that supports DNS over TLS MUST listen for and accept TCP connections on port 853" (3.1)
- Never DoT on port 53, to avoid downgrade confusion. "Such another port MUST NOT be port 53" (3.1)
- The reason for not using port 53: avoid mixing and downgrades. "This recommendation against use of port 53 for DNS over TLS is to avoid complication in selecting use or non-use of TLS and to reduce risk of downgrade attacks." (3.1)
- Remember servers that don't support DoT, for about an hour. "not request DNS over TLS from them for a reasonable period (such as one hour per server)." (3.1)
- No cleartext DNS on port 853. "DNS clients and servers MUST NOT use port 853 to transport cleartext DNS messages." (3.1)
- The TLS handshake starts as soon as the TCP connection is up. "Once the DNS client succeeds in connecting via TCP on the well-known port for DNS over TLS, it proceeds with the TLS handshake" (3.2)
- Padding helps against size analysis but isn't enough alone. "simple padding schemes alone might not be sufficient to mitigate such an attack." (8)
- Messages keep the two-byte length prefix of DNS over TCP. "All messages (requests and responses) in the established TLS session MUST use the two-octet length field described in Section 4.2.2 of [RFC1035]." (3.3)
- Clients should pipeline queries and match responses by ID, since they can come back out of order. "Since pipelined responses can arrive out of order, clients MUST match responses to outstanding queries on the same TLS connection using the Message ID." (3.3)
- Reuse connections instead of one per query. "clients and servers SHOULD NOT immediately close a connection after each response." (3.4)
- Opportunistic privacy only protects against passive listeners. "Opportunistic privacy can be used by any current client, but it only provides privacy when there are no on-path active attackers." (4.1)
- Key-pinned profile: client only talks to servers whose SPKI fingerprint it has. "In this profile, clients authenticate servers by matching a set of SPKI Fingerprints in an analogous manner to that described in [RFC7469]." (4.2)
- Setup cost: one extra RTT for TCP, and TLS (1.2 at the time) adds two. "The TLS handshake adds another two RTTs of latency." (5)
- TCP costs one extra RTT over UDP. "Compared to UDP, DNS over TCP requires an additional round-trip time (RTT) of latency to establish a TCP connection." (5)
- Encryption doesn't hide sizes and timing; padding helps a little. "Even with encrypted messages, a well-positioned party may be able to glean certain details from an analysis of message timings and sizes." (8)
- DNSSEC and DoT are independent. "As noted earlier, DNSSEC and DNS over TLS are independent and fully compatible protocols, each solving different problems." (8)
