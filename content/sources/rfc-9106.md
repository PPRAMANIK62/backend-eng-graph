## Summary

The IRTF (CFRG) description of Argon2 version 1.3 (2021), by its
designers. Explains the three variants, the inputs (password, salt,
memory, passes, lanes), parameter choices, and the known trade-off
attacks.

## Key claims

- Argon2 is memory-hard. "Argon2 is a memory-hard function [HARD]." (1. Introduction)
- Argon2i uses data-independent memory access, preferred for passwords. "Argon2i uses data-independent memory access, which is preferred for password hashing and password-based key derivation." (1. Introduction)
- Argon2id is half Argon2i, half Argon2d. "Argon2id works as Argon2i for the first half of the first pass over the memory and as Argon2d for the rest" (1. Introduction)
- Argon2id is the one that must be implemented. "Argon2id MUST be supported by any implementation of this document, whereas Argon2d and Argon2i MAY be supported." (1. Introduction)
- Salt: 16 bytes, unique per password. "16 bytes is RECOMMENDED for password hashing." (3.1 Argon2 Inputs and Outputs)
- The salt should be unique. "The salt SHOULD be unique for each password." (3.1)
- First recommended option: t=1, p=4, 2 GiB. "select Argon2id with t=1 iteration, p=4 lanes, m=2^(21) (2 GiB of RAM), 128-bit salt, and 256-bit tag size." (4. Parameter Choice)
- Second: t=3, p=4, 64 MiB when memory is short. "If much less memory is available, a uniformly safe option is Argon2id with t=3 iterations, p=4 lanes, m=2^(16) (64 MiB of RAM), 128-bit salt, and 256-bit tag size." (4. Parameter Choice)
- Example setting for backend authentication: 0.5 s on a 2 GHz CPU using 4 cores, Argon2id, 8 lanes, 4 GiB of RAM. "Backend server authentication, which takes 0.5 seconds on a 2 GHz CPU using 4 cores" (4. Parameter Choice)
- Argon2id is meant for settings where attackers may share the machine. "Argon2id is optimized for more realistic settings, where the adversary can possibly access the same machine, use its CPU, or mount cold-boot attacks." (4. Parameter Choice)
- Defenders are usually bound by latency. "A bottleneck in a system employing the password hashing function is often the function latency rather than memory costs." (7.3 Security for Time-Bounded Defenders)
- Argon2d suits settings without side-channel threats. "Argon2d uses data-dependent memory access, which makes it suitable for cryptocurrencies and proof-of-work applications with no threats from side-channel timing attacks." (1. Introduction)
- Argon2id gets both. "thus providing both side-channel attack protection and brute-force cost savings due to time-memory trade-offs." (1. Introduction)
- Recommended options are uniformly safe starting points. "If a uniformly safe option that is not tailored to your application or hardware is acceptable, select Argon2id with t=1 iteration, p=4 lanes, m=2^(21) (2 GiB of RAM), 128-bit salt, and 256-bit tag size." (4. Parameter Choice)
- Parameter t is the number of passes. "Number of passes t (used to tune the running time independently of the memory size)" (3.1 Argon2 Inputs and Outputs)
- Parameter p is the number of lanes. "Degree of parallelism p determines how many independent (but synchronizing) computational chains (lanes) can be run." (3.1)
- Parameter m is memory in KiB. "Memory size m MUST be an integer number of kibibytes from 8*p to 2^(32)-1." (3.1)

## My notes

- Status: Informational, CFRG consensus, not an IETF standard.
- The recommended options are per hash; a server doing many logins at
  once has to multiply the memory. OWASP's minimums are far lower
  (owasp-password-storage).
