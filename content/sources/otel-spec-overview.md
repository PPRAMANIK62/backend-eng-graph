## Summary

The overview chapter of the OpenTelemetry specification (version 1.61.0
when read). Defines the client architecture (signals, each split into
API, SDK, semantic conventions and contrib packages), the tracing,
metrics, logs and baggage signals, resources, context propagation, and
the Collector.

## Key claims

- Clients are organised by signal; signals share context propagation. "Signals share a common subsystem – context propagation – but they function independently from each other." (OpenTelemetry Client Architecture)
- OpenTelemetry is a cross-cutting concern. "This makes OpenTelemetry a cross-cutting concern - a piece of software which is mixed into many other pieces of software in order to provide value." (OpenTelemetry Client Architecture)
- Four package types per signal. "each signal consists of four types of packages: API, SDK, Semantic Conventions, and Contrib." (OpenTelemetry Client Architecture)
- The SDK belongs to the application owner. "Within an application, the SDK is installed and managed by the application owner." (SDK)
- Instrumentation depends only on the API. "Instrumentation authors MUST NOT directly reference any SDK package of any kind, only the API." (SDK)
- Semantic conventions name common things. "The Semantic Conventions define the keys and values which describe commonly observed concepts, protocols, and operations used by applications." (Semantic Conventions)
- A trace is a DAG of spans. "a Trace can be thought of as a directed acyclic graph (DAG) of Spans" (Traces)
- TraceId is 16 random bytes; SpanId is 8 random bytes. "It is worldwide unique with practically sufficient probability by being made as 16 randomly generated bytes." (SpanContext)
- Metrics: instruments include counters, gauges and histograms; the aggregation can be chosen by the user. "There are several types of metric instruments for specific use cases, such as counters for incrementing values, gauges for capturing current values, and histograms for capturing distributions of measurements." (Instruments)
- Views customise aggregation and filtering. "A View allows the customization of metric data beyond the default collection behavior, enabling specific aggregations, transformations, and filtering of metrics." (Views)
- Resource describes the entity producing telemetry, e.g. a Kubernetes cluster, namespace, pod and container. "Resource captures information about the entity for which telemetry is recorded." (Resources)
- Baggage carries name/value pairs along a transaction. (Baggage Signal)
- Propagators serialize SpanContext and baggage into carriers as text. "TextMapPropagator injects values into and extracts values from carriers as text." (Propagators)
- The Collector receives, aggregates, samples, transforms and exports. "The collector will allow to enrich and transform collected telemetry (e.g. add additional attributes or scrub personal information)." (Collector)
- Two Collector modes. "The OpenTelemetry Collector has two primary modes of operation: Agent (a daemon running locally with the application) and Collector (a standalone running service)." (Collector)
- SpanId is 8 random bytes. "It is globally unique with practically sufficient probability by being made as 8 randomly generated bytes." (SpanContext)
