## Summary

The HTTP/3 spec: HTTP semantics mapped onto QUIC. Its introduction
explains why HTTP/2 over TCP still stalls on loss, which is what
motivated moving to QUIC.

## Key claims

- HTTP/1.1 opens many TCP connections for parallelism, which hurts congestion control. "since TCP does not share congestion control across multiple connections." (1.1)
- HTTP/2 multiplexes over one TCP connection, and one lost packet stalls every request. "because the parallel nature of HTTP/2's multiplexing is not visible to TCP's loss recovery mechanisms, a lost or reordered packet causes all active transactions to experience a stall regardless of whether that transaction was directly impacted by the lost packet." (1.1)
- QUIC gives per-stream reliability and connection-wide congestion control. "By providing reliability at the stream level and congestion control across the entire connection, QUIC has the capability to improve the performance of HTTP compared to a TCP mapping." (1.2)
- QPACK lets the encoder limit how much head-of-line blocking header compression causes. "[QPACK] describes a variation of HPACK that gives an encoder some control over how much head-of-line blocking can be caused by compression." (4.2.1)

Added for `http3`:

- QUIC already does multiplexing and per-stream flow control. "The QUIC transport protocol incorporates stream multiplexing and per-stream flow control, similar to that provided by the HTTP/2 framing layer." (1.2)
- HTTP/3 keeps an HTTP/2-like framing on each stream. "While delegating stream lifetime and flow-control issues to QUIC, a binary framing similar to the HTTP/2 framing is used on each stream." (1.2)
- One request/response per QUIC stream. "Each request-response pair consumes a single QUIC stream." (2)
- Connection-wide frames go on a dedicated control stream. "Frames that apply to the entire connection are conveyed on a dedicated control stream." (2)
- HPACK is replaced by QPACK because QUIC doesn't order across streams. "Because HPACK ([HPACK]) relies on in-order transmission of compressed field sections (a guarantee not provided by QUIC), HTTP/3 replaces HPACK with QPACK ([QPACK])." (2)
- ALPN token "h3". "Unless some other mechanism is used to select HTTP/3, the token "h3" is used in the Application-Layer Protocol Negotiation (ALPN; see [RFC7301]) extension during the TLS handshake." (3.1)
- Clients should fall back to TCP when QUIC fails. "Connectivity problems (e.g., blocking UDP) can result in a failure to establish a QUIC connection; clients SHOULD attempt to use TCP-based versions of HTTP in this case." (3.1)
- Servers advertise HTTP/3 with Alt-Svc. "An HTTP origin can advertise the availability of an equivalent HTTP/3 endpoint via the Alt-Svc HTTP response header field or the HTTP/2 ALTSVC frame ([ALTSVC]) using the "h3" ALPN token." (3.1.1)
- Each side opens one control stream and sends SETTINGS first. "Each side MUST initiate a single control stream at the beginning of the connection and send its SETTINGS frame as the first frame on this stream." (6.2.1)
- A request stream carries one request. "A client MUST send only a single request on a given stream." (4.1)
- Stream concurrency is managed by QUIC, and streams stay "active" longer than in HTTP/2. "In contrast to HTTP/2, stream concurrency in HTTP/3 is managed by QUIC." (A.1)
- All HTTP/3 frames are flow controlled, not only DATA. "All HTTP/3 frames are sent on QUIC streams, so all frames on all streams are flow controlled in HTTP/3." (A.1)
- Frames lose the stream number and flags. "Because frames are already on a stream, they can omit the stream number." (A.2)
- HTTP/2 frames that assume cross-stream order would break. "if a frame type makes assumptions that frames from different streams will still be received in the order sent, HTTP/3 will break them." (A.2)
- No priority signaling in the base spec. "HTTP/3 does not provide a means of signaling priority." (A.2.1)
- RST_STREAM, PING, WINDOW_UPDATE and CONTINUATION don't exist in HTTP/3. "PING frames do not exist in HTTP/3, as QUIC provides equivalent functionality." and "WINDOW_UPDATE frames do not exist in HTTP/3, since QUIC provides flow control." (A.2.5)
- Settings are sent once and can't change. "An important difference from HTTP/2 is that settings are sent once, as the first frame of the control stream, and thereafter cannot change." (A.3)

- No RST_STREAM. "RST_STREAM frames do not exist in HTTP/3, since QUIC provides stream lifecycle management." (A.2.5)
- No CONTINUATION; HEADERS can be bigger. "CONTINUATION frames do not exist in HTTP/3; instead, larger HEADERS/PUSH_PROMISE frames than HTTP/2 are permitted." (A.2.5)
- Stream 0's role goes to the control stream. "frame type HTTP/2 extensions are typically portable to QUIC simply by replacing stream 0 in HTTP/2 with a control stream in HTTP/3." (A.2.4)
- No END_STREAM flag, so no flags field. "Because stream termination is handled by QUIC, an END_STREAM flag is not required.  This permits the removal of the Flags field from the generic frame layout." (A.2)
- HTTP/2 transport settings become QUIC transport parameters. "Some transport-level options that HTTP/2 specifies via the SETTINGS frame are superseded by QUIC transport parameters in HTTP/3." (A.3)
- Sending the old concurrent-streams setting is an error. "Specifying a setting with the identifier 0x03 (corresponding to the SETTINGS_MAX_CONCURRENT_STREAMS parameter) in the HTTP/3 SETTINGS frame is an error." (A.3)
- HTTP/2 closes a stream earlier than QUIC does. "HTTP/2 considers a stream closed when the frame containing the END_STREAM bit has been committed to the transport." (A.1)
- So servers may allow more streams. "HTTP/3 servers might choose to permit a larger number of concurrent client-initiated bidirectional streams to achieve equivalent concurrency to HTTP/2" (A.1)
- HTTP/3 can use any UDP port. "Servers MAY serve HTTP/3 on any UDP port" (3.1)

Added for `http3` audit:

- QUIC includes TLS 1.3. "QUIC also incorporates TLS 1.3 ([TLS]) at the transport layer" (1.2)
- A client may try QUIC directly for an https URI. "A client MAY attempt access to a resource with an "https" URI by resolving the host identifier to an IP address, establishing a QUIC connection to that address on the indicated port" (3.1)
- The spec's Alt-Svc example uses UDP port 50781. "Alt-Svc: h3=":50781"" (3.1.1)
