## Summary

The OpenJDK proposal that made virtual threads final in JDK 21 (2023),
by the Project Loom leads. Explains why Java wanted cheap threads (keep
the thread-per-request style instead of asynchronous pipelines), how
virtual threads are mounted on carrier platform threads by a
work-stealing ForkJoinPool, what blocks the carrier (pinning), and how
their stacks live on the heap.

## Key claims

- Goal: thread-per-request code that uses the hardware well. "Enable server applications written in the simple thread-per-request style to scale with near-optimal hardware utilization." (Goals)
- OS threads are costly, so their number caps a thread-per-request server's throughput. "the number of threads often becomes the limiting factor long before other resources, such as CPU or network connections, are exhausted." (Motivation)
- The asynchronous style gives up loops and try/catch, stack traces and debugger stepping. "They thus forsake the language's basic sequential composition operators, such as loops and try/catch blocks." (Motivation)
- In the asynchronous style, stack traces and debuggers stop helping. "Stack traces provide no usable context, debuggers cannot step through request-handling logic, and profilers cannot associate an operation's cost with its caller." (Motivation)
- A virtual thread uses an OS thread only while it computes; blocking I/O in java.* becomes a non-blocking OS call plus a suspend. "When code running in a virtual thread calls a blocking I/O operation in the java.* API, the runtime performs a non-blocking OS call and automatically suspends the virtual thread until it can be resumed later." (Motivation)
- Early Java green threads were M:1 and lost to 1:1 threads; virtual threads are M:N. "Java's green threads all shared one OS thread (M:1 scheduling) and were eventually outperformed by platform threads" (Description)
- Virtual threads use M:N scheduling. "Virtual threads employ M:N scheduling, where a large number (M) of virtual threads is scheduled to run on a smaller number (N) of OS threads." (Description)
- They are not faster threads. "Virtual threads are not faster threads — they do not run code any faster than platform threads." (Using virtual threads vs. platform threads)
- They help when there are many concurrent tasks (more than a few thousand) and the work isn't CPU-bound. "The workload is not CPU-bound, since having many more threads than processor cores cannot improve throughput in that case." (Using virtual threads vs. platform threads)
- Don't pool them; use a semaphore to limit concurrency. "virtual threads are not expensive so there is never a need to pool them." (Do not pool virtual threads)
- The scheduler is a work-stealing ForkJoinPool in FIFO mode, sized to the number of processors by default. "The JDK's virtual thread scheduler is a work-stealing ForkJoinPool that operates in FIFO mode." (Scheduling virtual threads)
- No time slicing in JDK 21. "The scheduler does not currently implement time sharing for virtual threads." (Scheduling virtual threads)
- Virtual threads are not cooperative: code doesn't yield explicitly. "virtual threads are not cooperative." (Executing virtual threads)
- Some blocking calls capture the carrier (many filesystem operations, Object.wait()); the scheduler compensates by adding threads for a while. "The implementations of these blocking operations compensate for the capture of the OS thread by temporarily expanding the parallelism of the scheduler." (Executing virtual threads)
- In JDK 21, a virtual thread is pinned inside synchronized blocks or native calls. "When it executes code inside a synchronized block or method, or" (Executing virtual threads, list of pinning cases)
- Pinning isn't compensated. "The scheduler does not compensate for pinning by expanding its parallelism." (Executing virtual threads)
- Their stacks are heap objects that grow and shrink. "The stacks of virtual threads are stored in Java's garbage-collected heap as stack chunk objects." (Memory use and interaction with garbage collection)
- Heap use overall should be close to asynchronous code. "Overall, the heap consumption and garbage collector activity of thread-per-request versus asynchronous code should be roughly similar." (Memory use)
- Scalability is governed by Little's Law: concurrency must grow with throughput for a given latency. "The scalability of server applications is governed by Little's Law, which relates latency, concurrency, and throughput" (Motivation)
- The old flat thread dump doesn't work for huge numbers of virtual threads, so there's a new format. "This is suitable for dozens or hundreds of platform threads, but is unsuitable for thousands or millions of virtual threads." (Observing virtual threads)
- The OS doesn't see them. "they are invisible to the OS, which is unaware of their existence." (Observing virtual threads)

## My notes

- Previews: JEP 425 (JDK 19), JEP 436 (JDK 20). Final in JDK 21.
- The synchronized pinning limitation is removed by JEP 491 (JDK 24).
- The 10,000 and 1,000,000 tasks-per-second figures are for a toy
  program that sleeps one second per task, not a benchmark.
