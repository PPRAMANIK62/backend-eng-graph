## Summary

The WebSocket protocol (2011): an HTTP/1.1 Upgrade handshake that turns
one TCP connection into a two-way channel of framed messages. Covers
the handshake and its key/accept check, the frame format, client
masking and why it exists, ping/pong and closing.

## Key claims

- Before WebSockets, two-way web apps polled over HTTP. "has required an abuse of HTTP to poll the server for updates while sending upstream notifications as distinct HTTP calls" (1.1)
- The fix is one TCP connection used both ways. "A simpler solution would be to use a single TCP connection for traffic in both directions." (1.1)
- It is designed to work on ports 80 and 443 through HTTP proxies. "it is designed to work over HTTP ports 80 and 443 as well as to support HTTP proxies and intermediaries" (1.1)
- The protocol has two parts. "The protocol has two parts: a handshake and the data transfer." (1.2)
- The client's handshake is an HTTP Upgrade request (`Upgrade: websocket`, `Connection: Upgrade`, `Sec-WebSocket-Key`, `Sec-WebSocket-Version: 13`), and the server answers `101 Switching Protocols`. (1.2, example)
- After the handshake either side sends whenever it likes. "This is a two-way communication channel where each side can, independently from the other, send data at will." (1.2)
- Data moves as messages made of one or more frames, and intermediaries may re-split them. "a fragmented message may be coalesced or split by an intermediary." (1.2)
- The server proves it understood the handshake by hashing the key with a fixed GUID. "concatenate this with the Globally Unique Identifier (GUID, [RFC4122]) "258EAFA5-E914-47DA-95CA-C5AB0DC85B11" in string form" (1.3)
- The hash is SHA-1, base64 encoded; the spec's key `dGhlIHNhbXBsZSBub25jZQ==` gives `s3pPLMBiTxaQ9kYGzzhZRbK+xOo=` (checked with `openssl sha1 -binary | base64`). (1.3)
- Any status other than 101 means the handshake failed. "Any status code other than 101 indicates that the WebSocket handshake has not completed" (1.3)
- Clients must mask every frame; servers must not. "a client MUST mask all frames that it sends to the server" and "A server MUST NOT mask any frames that it sends to the client." (5.1)
- Masking happens even over TLS. "(Note that masking is done whether or not the WebSocket Protocol is running over TLS.)" (5.1)
- Frame header: FIN bit, opcode, mask bit, 7-bit length extended to 16 or 64 bits, optional 4-byte masking key. (5.2, figure)
- Opcodes: continuation, text, binary, close, ping, pong. "%x9 denotes a ping" (5.2)
- Ping can be used as a keepalive. "A Ping frame may serve either as a keepalive or as a means to verify that the remote endpoint is still responsive." (5.5.2)
- Masking exists because an experiment poisoned caching proxies with fake requests over an upgraded connection. "an experiment was conducted to demonstrate a class of attacks on proxies that led to the poisoning of caching proxies deployed in the wild" (10.3)

- Typical uses. "games, stock tickers, multiuser applications with simultaneous editing, user interfaces exposing server-side services in real time" (1.1)
- The accept check stops a WebSocket server accepting connections that aren't WebSockets, e.g. crafted form posts. "This prevents an attacker from tricking a WebSocket server by sending it carefully crafted packets using XMLHttpRequest [XMLHttpRequest] or a form submission." (1.3)
- Origin lets the server refuse scripts from other sites. "The |Origin| header field [RFC6454] is used to protect against unauthorized cross-origin use of a WebSocket server by scripts using the WebSocket API in a web browser." (1.3)
- The server picks one offered subprotocol. "The server selects one or none of the acceptable protocols and echoes that value in its handshake to indicate that it has selected that protocol." (1.3)
- Pong echoes the ping's data. "A Pong frame sent in response to a Ping frame must have identical "Application data" as found in the message body of the Ping frame being replied to." (5.5.3)
- Servers close on unmasked frames. "The server MUST close the connection upon receiving a frame that is not masked." (5.1)
- The masking key is a fresh random 32-bit value per frame. "The masking key is a 32-bit value chosen at random by the client." (5.3)
- Unpredictable keys stop scripts choosing the bytes on the wire. "The unpredictability of the masking key is essential to prevent authors of malicious applications from selecting the bytes that appear on the wire." (5.3)
- Text frames are UTF-8. "there are types for textual data (which is interpreted as UTF-8 [RFC3629] text), binary data" (1.2)
- Masking is a byte-wise XOR with the key. "transformed-octet-i = original-octet-i XOR masking-key-octet-j" (5.3)

- The attack: upgrade a connection to the attacker's server, then send bytes that look like a GET. "and subsequently send data over that UPGRADEd connection that looked like a GET request for a specific known resource" (10.3)
- The fake response got cached for other users. "this response would be cached by a nonzero percentage of deployed intermediaries, thus poisoning the cache." (10.3)
