## Summary

Textbook chapter that builds vsfs, a very simple Unix-like file system, on
a tiny disk of 4 KB blocks: superblock, inode and data bitmaps, an inode
table and a data region. Then walks through what a read, a write and a file
creation cost in disk I/Os. PDF footer says © 2008–26.

## Key claims

- The example disk is a row of 4 KB blocks numbered 0 to N−1. "a series of blocks, each of size 4 KB. The blocks are addressed from 0 to N − 1" (§40.2)
- Inodes are commonly 128 or 256 bytes; at 256 bytes, 16 fit in a 4 KB block. "Assuming 256 bytes per inode, a 4-KB block can hold 16" (§40.2)
- Free space is tracked with bitmaps, one for inodes and one for data blocks. "one for the data region (the data bitmap), and one for the inode table (the inode bitmap)" (§40.2)
- The superblock describes the file system: counts, where the inode table starts, a magic number. "The superblock contains information about this particular file system" (§40.2)
- Inode means index node. "The name inode is short for index node" (§40.3)
- Each inode has a number (i-number), and the file system can compute where it lives on disk from that number. "given an i-number, you should directly be able to calculate where on the disk the corresponding inode is located." (§40.3)
- Inodes point at data blocks with direct pointers, plus indirect blocks for bigger files. "an indirect block is allocated (from the data-block region of the disk), and the inode's slot for an indirect pointer is set to point to it." (§40.3)
- 12 direct pointers, a single and a double indirect block, 4 KB blocks and 4-byte pointers give just over 4 GB. "this structure can accommodate a file of just over 4 GB in size" (§40.3)
- An extent is a pointer plus a length. "An extent is simply a disk pointer plus a length (in blocks)" (§40.3, Tip)
- Extents are more compact but less flexible than per-block pointers. "Extent-based approaches are less flexible but more compact" (§40.3, Tip)
- XFS and ext4 use extents; ext2 and ext3 use pointers. "Other file systems, including SGI XFS and Linux ext4, use extents instead of simple pointers" (§40.3)
- A directory is a list of (name, inode number) pairs. "a directory basically just contains a list of (entry name, inode number) pairs." (§40.4)
- A directory is a special file with its own inode. "file systems treat directories as a special type of file." (§40.4)
- Opening a path walks it from the root, whose inode number is well known (2 in most Unix file systems). "In most UNIX file systems, the root inode number is 2." (§40.6)
- The inode holds basic file info such as permissions and size. "to obtain some basic information about the file (permissions information, file size, etc.)" (§40.6)
- The I/O for open grows with path length. "the amount of I/O generated by the open is proportional to the length of the pathname." (§40.6)
- Each allocating write costs five I/Os: read and write the data bitmap, read and write the inode, write the data. "each write to a file logically generates five I/Os" (§40.6)
- Creating a file in the example takes 10 I/Os. "10 I/Os in this case, to walk the pathname and then finally create the file" (§40.6)
- Most file systems buffer writes in memory for 5 to 30 seconds. "most modern file systems buffer writes in memory for anywhere between five and thirty seconds" (§40.7)
- (added in review) Extents work well when there is free space to lay files out contiguously. "they work well when there is enough free space on the disk and files can be laid out contiguously" (§40.3, Tip)
- The worked example file system (vsfs) sits on a tiny disk of 64 blocks. "Assume we have a really small disk, with just 64 blocks" (§40.2; added in figure review)

## My notes

- vsfs is a teaching model; real file systems (ext4, XFS, btrfs) differ,
  but the pieces (superblock, inodes, bitmaps or trees for free space,
  directories as name-to-inode maps) carry over.
