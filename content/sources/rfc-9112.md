## Summary

The 2022 spec (STD 99) for HTTP/1.1's wire format and connection
handling: the start line, header field syntax, how the length of a
message body is worked out (Content-Length, chunked, or connection
close), persistent connections, pipelining, closing, and the parsing
rules added to make request smuggling harder. It obsoletes the
HTTP/1.1-specific parts of RFC 7230; meaning lives in RFC 9110.

## Key claims

- A message is a start line, header field lines, an empty line and an optional body. "An HTTP/1.1 message consists of a start-line followed by a CRLF and a sequence of octets in a format similar to the Internet Message Format [RFC5322]" (2.1)
- The usual parse: start line, headers into a table until the empty line, then decide on the body. "The normal procedure for parsing an HTTP message is to read the start-line into a structure, read each header field line into a hash table by field name until the empty line" (2.2)
- Parse as bytes, not Unicode text. "A recipient MUST parse an HTTP message as a sequence of octets in an encoding that is a superset of US-ASCII [USASCII]." (2.2)
- Bare LF may be accepted as a line end. "a recipient MAY recognize a single LF as a line terminator and ignore any preceding CR." (2.2)
- Bare CR is forbidden outside content. "A sender MUST NOT generate a bare CR (a CR character not immediately followed by LF) within any protocol elements other than the content." (2.2)
- Request line: method, target, version separated by single spaces. "A request-line begins with a method token, followed by a single space (SP), the request-target, and another single space (SP), and ends with the protocol version." (3)
- Lenient whitespace parsing leads to smuggling when recipients differ. "However, lenient parsing can result in request smuggling security vulnerabilities if there are multiple recipients of the message and each has its own unique interpretation of robustness" (3)
- Request lines of at least 8000 octets should be supported. "It is RECOMMENDED that all HTTP senders and recipients support, at a minimum, request-line lengths of 8000 octets." (3)
- Host is required in HTTP/1.1; missing or duplicate Host gets 400. "A server MUST respond with a 400 (Bad Request) status code to any HTTP/1.1 request message that lacks a Host header field and to any request message that contains more than one Host header field line" (3.2)
- Clients should ignore the reason phrase. "A client SHOULD ignore the reason-phrase content because it is not a reliable channel for information" (4)
- No whitespace between field name and colon; servers reject it. "No whitespace is allowed between the field name and colon." (5.1)
- Line folding is deprecated. "This specification deprecates such line folding except within the \"message/http\" media type" (5.2)
- A request has a body only if Content-Length or Transfer-Encoding says so. "The presence of a message body in a request is signaled by a Content-Length or Transfer-Encoding header field." (6)
- Chunked exists to frame content whose size isn't known in advance. "because it plays a crucial role in framing messages when the content size is not known in advance." (6.1)
- Transfer-Encoding is a property of the message, not the representation. "Unlike Content-Encoding (Section 8.4.1 of [HTTP]), Transfer-Encoding is a property of the message, not of the representation." (6.1)
- Why TE overrides CL: old senders sent both for progress bars. "This is why Transfer-Encoding is defined as overriding Content-Length, as opposed to them being mutually incompatible." (6.1)
- A server that gets both may reject or use TE, and must close the connection afterwards. "Regardless, the server MUST close the connection after responding to such a request to avoid the potential attacks." (6.1)
- Senders must not send both. "A sender MUST NOT send a Content-Length header field in any message that contains a Transfer-Encoding header field." (6.2)
- The body-length rules are an ordered list. "The length of a message body is determined by one of the following (in order of precedence):" (6.3)
- Responses to HEAD and 1xx, 204, 304 responses end at the empty line. "Any response to a HEAD request and any response with a 1xx (Informational), 204 (No Content), or 304 (Not Modified) status code is always terminated by the first empty line after the header fields" (6.3, rule 1)
- Both TE and CL is a possible smuggling attempt. "Such a message might indicate an attempt to perform request smuggling (Section 11.2) or response splitting (Section 11.1) and ought to be handled as an error." (6.3, rule 3)
- Invalid Content-Length is an unrecoverable framing error. "then the message framing is invalid and the recipient MUST treat it as an unrecoverable error" (6.3, rule 5)
- A request with neither has no body. "If this is a request message and none of the above are true, then the message body length is zero" (6.3, rule 7)
- A response with neither runs until the server closes. "so the message body length is determined by the number of octets received prior to the server closing the connection." (6.3, rule 8)
- Close-delimiting exists for HTTP/1.0 compatibility. "The close-delimiting feature exists primarily for backwards compatibility with HTTP/1.0." (6.3)
- Requests are never close-delimited. "Request messages are never close-delimited because they are always explicitly framed by length or transfer coding" (6.3)
- Chunked: a series of chunks each with its own size, then optional trailers. "The chunked transfer coding wraps content in order to transfer it as a series of chunks, each with its own size indicator, followed by an OPTIONAL trailer section containing trailer fields." (7.1)
- Chunk sizes are hex; a zero-size chunk ends the body. "The chunked transfer coding is complete when a chunk with a chunk-size of zero is received, possibly followed by a trailer section, and finally terminated by an empty line." (7.1)
- Parsers must guard against huge chunk sizes overflowing. "recipients MUST anticipate potentially large hexadecimal numerals and prevent parsing errors due to integer conversion overflows" (7.1)
- A chunked body is incomplete without the zero-size chunk. "A message body that uses the chunked transfer coding is incomplete if the zero-sized chunk that terminates the encoding has not been received." (8)
- HTTP/1.1 has no request ID; responses match requests by order. "Hence, it relies on the order of response arrival to correspond exactly to the order in which requests are made on the same connection." (9.2)
- Persistent connections are the default. "HTTP/1.1 defaults to the use of \"persistent connections\", allowing multiple requests and responses to be carried over a single connection." (9.3)
- To stay persistent every message needs a self-defined length, and the whole body must be read. "A server MUST read the entire request message body or close the connection after sending its response; otherwise, the remaining data on a persistent connection would be misinterpreted as the next request." (9.3)
- Pipelining is allowed, responses must come back in order. "it MUST send the corresponding responses in the same order that the requests were received." (9.3.2)
- Don't pipeline after a non-idempotent request. "A user agent SHOULD NOT pipeline requests after a non-idempotent method, until the final response status code for that method has been received" (9.3.2)
- No fixed connection limit any more; be conservative. "this specification does not mandate a particular maximum number of connections but, instead, encourages clients to be conservative when opening multiple connections." (9.4)
- Multiple connections exist to avoid head-of-line blocking on one. "Multiple connections are typically used to avoid the \"head-of-line blocking\" problem" (9.4)
- Idle timeout race: a client can start a request as the server closes. "For example, a client might have started to send a new request at the same time that the server has decided to close the \"idle\" connection." (9.5)
- Connection: close signals the last request/response on a connection. "The \"close\" connection option is defined as a signal that the sender will close this connection after completion of the response." (9.6)
- An abrupt close can make the client lose the last response to a TCP reset. "If a server performs an immediate close of a TCP connection, there is a significant risk that the client will not be able to read the last HTTP response." (9.6)
- Servers close in stages: half-close, keep reading, then close. "First, the server performs a half-close by closing only the write side of the read/write connection." (9.6)
- Request smuggling exploits parsing differences between recipients. "Request smuggling ([Linhart]) is a technique that exploits differences in protocol parsing among various recipients to hide additional requests" (11.2)
- HTTP/1.0 Keep-Alive broke through proxies that forwarded Connection. "if an HTTP/1.0 proxy server doesn't understand Connection, it will erroneously forward that header field to the next inbound server, which would result in a hung connection." (C.2.2)
- An intermediary forwarding a TE+CL message must drop Content-Length first. "An intermediary that chooses to forward the message MUST first remove the received Content-Length field and process the Transfer-Encoding (as described below) prior to forwarding the message downstream." (6.3, rule 3)
- Forwarding such messages is dangerous if any recipient downstream parses differently, especially an HTTP/1.0 one. "if any downstream recipient fails to parse the message according to this specification, particularly when a downstream recipient only implements HTTP/1.0." (6.1)
- An HTTP/1.0 message with Transfer-Encoding has faulty framing. "A server or client that receives an HTTP/1.0 message containing a Transfer-Encoding header field MUST treat the message as if the framing is faulty, even if a Content-Length is present, and close the connection after processing the message." (6.1)
- The spec tightened framing rules on purpose to fight smuggling. "This specification has introduced new requirements on request parsing, particularly with regard to message framing in Section 6.3, to reduce the effectiveness of request smuggling." (11.2)

Added for `http-1-1`:

- Intermediaries send their own HTTP version, not the one they received. "Intermediaries that process HTTP messages (i.e., all intermediaries other than those acting as tunnels) MUST send their own HTTP-version in forwarded messages" (2.3)
- Chunked must be the final coding in a request; in a response, chunked last or close the connection. "the sender MUST either apply chunked as the final transfer coding or terminate the message by closing the connection." (6.1)
- Recipients may remove or add transfer codings along the chain. "Any recipient along the request/response chain MAY decode the received transfer coding(s) or apply additional transfer coding(s) to the message body" (6.1)
- A proxy forwarding a TE+CL message must drop CL first. "An intermediary that chooses to forward the message MUST first remove the received Content-Length field and process the Transfer-Encoding" (6.3, rule 3)
- Chunked not last in a request: 400 and close. "the server MUST respond with the 400 (Bad Request) status code and then close the connection." (6.3, rule 4)
- Invalid Content-Length in a response at a proxy: close upstream, 502 downstream. "the proxy MUST close the connection to the server, discard the received response, and send a 502 (Bad Gateway) response to the client." (6.3, rule 5)
- Some services refuse chunked request bodies with 411. "some existing services respond to chunked with a 411 (Length Required) status code even though they understand the chunked transfer coding." (6.3)
- Recipients ignore chunk extensions they don't know. "A recipient MUST ignore unrecognized chunk extensions." (7.1.1)
- Trailers carry things known only at the end, like an integrity check. "such as a message integrity check, digital signature, or post-processing status." (7.1.2)
- The server may process pipelined requests in parallel only if all are safe. "A server MAY process a sequence of pipelined requests in parallel if they all have safe methods" (9.3.2)
- Earlier revisions had a fixed connection limit. "Previous revisions of HTTP gave a specific number of connections as a ceiling, but this was found to be impractical for many applications." (9.4)
- Many connections cost the server and can congest the network. "However, each connection consumes server resources." (9.4)
- No idle timeout number is required. "The use of persistent connections places no requirements on the length (or existence) of this timeout for either the client or the server." (9.5)
- Unicode parsing is dangerous because of how libraries treat invalid sequences containing LF. "Parsing an HTTP message as a stream of Unicode characters, without regard for the specific encoding, creates security vulnerabilities due to the varying ways that string processing libraries handle invalid multibyte character sequences that contain the octet LF (%x0A)." (2.2)
- Whitespace-preceded lines before the first header must be rejected or ignored. "A recipient that receives whitespace between the start-line and the first header field MUST either reject the message as invalid or consume each whitespace-preceded line without further processing of it" (2.2)
- Whitespace before the colon in a request gets 400. "A server MUST reject, with a response status code of 400 (Bad Request), any received request message that contains whitespace between a header field name and colon." (5.1)
- With both TE and CL, a server may reject or go by TE alone. "A server MAY reject a request that contains both Content-Length and Transfer-Encoding or process such a request in accordance with the Transfer-Encoding alone." (6.1)
- Invalid Content-Length (unless it's a list of identical valid values) in a request: 400 and close. "If the unrecoverable error is in a request message, the server MUST respond with a 400 (Bad Request) status code and then close the connection." (6.3, rule 5)
- Servers should frame by length or coding whenever they can. "a server SHOULD generate encoding or length-delimited messages whenever possible." (6.3)
- A client that pipelines retries unanswered requests when the connection closes. "A client that pipelines requests SHOULD retry unanswered requests if the connection closes before it receives all of the corresponding responses." (9.3.2)
- HTTP/1.0: one request per connection. "In HTTP/1.0, each connection is established by the client prior to the request and closed by the server after sending the response." (C.2.2)

## My notes

- Rule 3 in 6.3 plus "MAY reject" in 6.1 is the root of smuggling: two
  implementations can each follow the spec and still disagree if one
  of them is lenient elsewhere.
- Section 9.5 doesn't give idle timeout numbers.
