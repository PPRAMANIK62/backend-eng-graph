## Summary

The 2005 overview of DNSSEC, the first of the three core documents
(4033, 4034, 4035). What DNSSEC adds to DNS (signatures on record sets,
public keys in the DNS, delegation signer records, signed proof that a
name doesn't exist), what it deliberately doesn't do (confidentiality,
DoS protection), how a validating resolver builds a chain of trust from
a trust anchor, and the new failure modes it brings.

## Key claims

- DNSSEC gives origin authentication and integrity, including signed denial of existence. "The Domain Name System (DNS) security extensions provide origin authentication and integrity assurance services for DNS data, including mechanisms for authenticated denial of existence of DNS data." (3)
- Four new record types and two header bits. "DNSSEC adds four new resource record types: Resource Record Signature (RRSIG), DNS Public Key (DNSKEY), Delegation Signer (DS), and Next Secure (NSEC)." (3)
- The new header bits are CD and AD. "It also adds two new message header bits: Checking Disabled (CD) and Authenticated Data (AD)." (3)
- Needs EDNS0 for the bigger messages, and the DO bit to ask for DNSSEC records. "In order to support the larger DNS message sizes that result from adding the DNSSEC RRs, DNSSEC also requires EDNS0 support" (3)
- Signatures cover record sets and live in RRSIG records. "DNSSEC provides authentication by associating cryptographically generated digital signatures with DNS RRsets." (3.1)
- The signing key belongs to the zone, not to the servers. "the key that signs a zone's data is associated with the zone itself and not with the zone's authoritative name servers." (3.1)
- DNSSEC secures the data, not the channel. "DNSSEC itself is concerned with object security of DNS data, not channel security of DNS transactions." (3.1)
- Private keys should be offline when practical. "the private keys used to sign zone data must be kept secure and should be stored offline when practical." (3.1)
- A resolver needs at least one trust anchor. "Therefore, the resolver must be configured with at least one trust anchor." (3.1)
- DS in the parent points at the child's key; the chain alternates DNSKEY and DS. "The typical authentication chain is therefore DNSKEY->[DS->DNSKEY]*->RRset" (3.1)
- The chain normally starts from the root's key. "A security-aware resolver normally constructs this authentication chain from the root of the DNS hierarchy down to the leaf zones based on configured knowledge of the public key for the root." (3.1)
- NSEC records sign the gaps between names, so "no such name" can be proven. "Chains of NSEC records explicitly describe the gaps, or \"empty space\", between domain names in a zone" (3.2)
- NSEC relies on a canonical order of names and lists the types present at each name. "Use of NSEC records requires a canonical representation and ordering for domain names in zones." (3.2)
- Each NSEC also lists the record types at its name. "list the types of RRsets present at existing names." (3.2)
- DS lives in the parent zone at the delegation point. "The DS RRset resides at a delegation point in a parent zone" (3.1)
- No confidentiality. "Accordingly, DNSSEC is not designed to provide confidentiality, access control lists, or other means of differentiating between inquirers." (4)
- No protection against DoS. "DNSSEC provides no protection against denial of service attacks." (4)
- Four validation states: secure, insecure, bogus, indeterminate. "A validating resolver can determine the following 4 states:" (5)
- Bogus: a signed delegation, but the answer fails to validate (missing or expired signatures, unsupported algorithms). "the response fails to validate for some reason: missing signatures, expired signatures, signatures with unsupported algorithms" (5)
- Bogus is reported to non-validating stubs as SERVFAIL. "using RCODE=2, \"Server Failure\"; see [RFC4035]" (5)
- A stub that doesn't validate has to trust its recursive server and the channel to it. "the stub resolver must trust both the recursive name servers in question and the communication channels between itself and those name servers." (7)
- The AD bit is only a hint about whether the recursive validated. "The stub resolver can use this flag bit as a hint to find out whether the recursive name server was able to validate signatures for all of the data" (7)
- Signatures have inception and expiration times. "The RRSIG records that accompany zone data have defined inception and expiration times that establish a validity period for the signatures and the zone data the signatures cover." (8)
- TTLs can't extend a signature's validity. "TTL values cannot extend the validity period of signed RRsets in a resolver's cache" (8.1)
- Signed zones need regular re-signing. "A signed zone requires regular maintenance to ensure that each RRset in the zone has a current valid RRSIG RR." (8.2)
- Every zone on the path must be signed for validation to work. "all zones along the path from the trusted starting point to the zone containing the response zones must be signed" (12)
- NSEC lets anyone list every name in a zone. "DNSSEC introduces the ability for a hostile party to enumerate all the names in a zone by following the NSEC chain." (12)
- Validation errors can make whole zones unreachable. "enabling DNSSEC signature validation in a resolver may cause entire legitimate zones to become effectively unreachable due to DNSSEC configuration errors or bugs." (12)
- The DO bit is how a resolver asks for DNSSEC records. "DNSSEC requires support for the DNSSEC OK (DO) EDNS header bit ([RFC3225]) so that a security-aware resolver can indicate in its queries that it wishes to receive DNSSEC RRs in response messages." (3)
- Bigger answers can be truncated over UDP and fall back to TCP. "Because inclusion of these DNSSEC RRs could easily cause UDP message truncation and fallback to TCP" (9)
- A new DoS class: making a validator burn resources on bad signatures or long chains. "by tampering with RRSIG RRs in response messages or by constructing needlessly complex signature chains." (12)
- Glue and NS records at zone cuts aren't signed. "Non-authoritative data at zone cuts (glue and NS RRs in the parent zone) are not signed." (12)
