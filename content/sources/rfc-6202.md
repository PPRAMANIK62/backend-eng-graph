## Summary

An informational IETF RFC (2011) that describes how HTTP long polling
and HTTP streaming push events from server to client, and the problems
each runs into: header overhead, latency after each response, held
resources, timeouts, proxies and caching. Written against HTTP/1.1
(RFC 2616); it takes no side on whether you should do this at all.

## Key claims

- Plain HTTP can't push, so the client has to poll. "In the standard HTTP model, a server cannot initiate a connection with a client nor send an unrequested HTTP response to a client; thus, the server cannot push asynchronous events to clients." (1)
- Long polling defined: the server holds the request until there's something to send. "The server attempts to "hold open" (not immediately reply to) each HTTP request, responding only when there are events to deliver." (1)
- Short polling's cost depends on how fresh you need the data. "If the acceptable latency is low (e.g., on the order of seconds), then the polling frequency can cause an unacceptable burden on the server, the network, or both." (2.1)
- The server answers on an event, a status, or a timeout. "The server achieves these efficiencies by responding to a request only when a particular event, status, or timeout has occurred." (2.1)
- The client usually re-polls right away. "Once the server sends a long poll response, typically the client immediately sends a new long poll request." (2.1)
- Persistent connections avoid a new TCP connection per poll. "The use of persistent HTTP connections will avoid the additional overhead of establishing a new TCP/IP connection [TCP] for every long poll request." (2.1)
- Every poll carries full HTTP headers. "every long poll request and long poll response is a complete HTTP message and thus contains a full set of HTTP headers in the message framing." (2.2, Header Overhead)
- Average latency is about one transit, worst case over three. "while the average latency of long polling is close to one network transit, the maximal latency is over three network transits (long poll response, next long poll request, long poll response)." (2.2, Maximal Latency)
- Each waiting client holds a connection and a request. "The HTTP long polling mechanism requires that for each client both a TCP/IP connection and an HTTP request are held open." (2.2, Allocated Resources)
- The per-request resources are the expensive part. "Frequently, the resources allocated to HTTP requests can be significant, and scaling the total number of requests outstanding can be limited on some gateways, proxies, and servers." (2.2, Allocated Resources)
- Under load, messages queue and go out in batches. "If multiple messages are queued for a client, they might be delivered in a batch within a single long poll response." (2.2, Graceful Degradation)
- Browsers of the time allowed 6 or 8 connections per server. "In fact, recent browsers have increased this limit to 6 or 8 connections; however, it is still not possible to discover the local limit, and usage of multiple frames and tabs still places 8 connections within easy reach." (5.1)
- Page scripts can't see or share connections. "Note that the available JavaScript APIs in the browsers hide the connections, and the security model inhibits the sharing of any resource between frames." (5.1)
- Sharing one poll is hard. "However, the security constraints of the browsers make such sharing difficult." (5.1)
- One long poll per browser, shared across tabs, is the ideal. "Web applications need to limit the number of long poll requests initiated, ideally to a single long poll that is shared between frames, tabs, or windows of the same browser." (5.1)
- Proxies that share backend connections can starve. "If long polls are sent on those shared connections, then the proxy can be starved of connections, which means that other requests (either long poll or normal) can be held up." (5.3)
- Synchronous request handling is why long polling looks expensive. "Asynchronous proxies and servers can handle long polls using slightly more resources than normal HTTP traffic." (5.3)
- Timeouts too long get cut by the network. "problems can occur if this value is set too high (e.g., the client might receive a 408 Request Timeout answer from the server or a 504 Gateway Timeout answer from a proxy)." (5.5)
- 30 seconds is the safer timeout. "Several experiments have shown success with timeouts as high as 120 seconds, but generally 30 seconds is a safer value." (5.5)
- Turn caching off. "As a best practice, caching is always intentionally suppressed in a long poll request or response, i.e., the "Cache-Control" header is set to "no-cache"." (5.6)
- Many open requests make denial of service easier. "the number of open connections that needs to be maintained by a server in HTTP long polling and HTTP streaming could more easily lead to denial-of-service (DoS) attacks" (6)

  the time. HTTP/2 multiplexing changes the connection-limit part.
