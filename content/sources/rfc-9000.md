## Summary

The QUIC transport spec. Noted here only for how its streams avoid
head-of-line blocking across streams, and the limit of that.

## Key claims

- A loss blocks only the streams whose data was in the lost packet. "When a packet loss occurs, only streams with data in that packet are blocked waiting for a retransmission to be received, while other streams can continue making progress." (13)
- A packet carrying several streams blocks all of them when lost. "Note that when data from multiple streams is included in a single QUIC packet, loss of that packet blocks all those streams from making progress." (13)
- So implementations should put few streams in each packet. "Implementations are advised to include as few streams as necessary in outgoing packets without losing transmission efficiency to underfilled packets." (13)

Added for `head-of-line-blocking` audit:

- QUIC runs over UDP. "QUIC packets are carried in UDP datagrams [UDP] to better facilitate deployment in existing systems and networks." (Abstract)
- Each stream is its own ordered byte stream. "Streams in QUIC provide a lightweight, ordered byte-stream abstraction to an application." (2)
- Avoiding head-of-line blocking across streams is a stated goal. "One of the benefits of QUIC is avoidance of head-of-line blocking across multiple streams." (13)

Added for `quic`:

- QUIC is connection oriented and folds the TLS handshake into its own. "QUIC integrates the TLS handshake [TLS13], although using a customized framing for protecting packets." (1)
- 0-RTT needs a previous connection. "This includes an option for clients to send data immediately (0-RTT), which requires some form of prior communication or configuration to enable." (1)
- Packets are authenticated in full and encrypted as far as possible. "QUIC authenticates the entirety of each packet and encrypts as much of each packet as is practical." (1)
- Only clients can migrate in version 1. "Only clients are able to migrate in this version of QUIC." (1)
- Migration also covers NAT rebinding. "This design also allows connections to continue after changes in network topology or address mappings, such as might be caused by NAT rebinding." (1)
- There's no ordering between streams. "QUIC does not provide any means of ensuring ordering between bytes on different streams." (2)
- One STREAM frame can open, fill and close a stream. "For instance, a single STREAM frame (Section 19.8) can open, carry data for, and close a stream." (2)
- Stream IDs are 62-bit; the low bit says who opened it, the next bit whether it's one-way. "The least significant bit (0x01) of the stream ID identifies the initiator of the stream." and "The second least significant bit (0x02) of the stream ID distinguishes between bidirectional streams (with the bit set to 0) and unidirectional streams (with the bit set to 1)." (2.1)
- Flow control per stream and per connection, and a limit on streams. "streams are flow controlled both individually and across a connection as a whole." (4)
- Connection IDs keep packets reaching the right connection when addresses change. "The primary function of a connection ID is to ensure that changes in addressing at lower protocol layers (UDP, IP) do not cause packets for a QUIC connection to be delivered to the wrong endpoint." (5.1)
- Each endpoint picks the IDs its peer uses, so a load balancer can route by them. "Endpoints using a load balancer that routes based on connection ID could agree with the load balancer on a fixed length for connection IDs or agree on an encoding scheme." (5.1)
- Several IDs stop observers from linking a migrated connection. "Multiple connection IDs are used so that endpoints can send packets that cannot be identified by an observer as being for the same connection without cooperation from an endpoint" (5.1)
- One combined handshake for crypto and transport. "QUIC relies on a combined cryptographic and transport handshake to minimize connection establishment latency." (7)
- The handshake can be as few as four datagrams. "this handshake could consist of as few as four UDP datagrams" (7.1)
- The application protocol must be negotiated (ALPN). "Endpoints MUST explicitly negotiate an application protocol." (7)
- Before an address is validated, a server may send at most three times what it received. "an endpoint MUST limit the amount of data it sends to the unvalidated address to three times the amount of data received from that address." (8)
- A client's Initial datagrams are padded to at least 1200 bytes. "Clients MUST ensure that UDP datagrams containing Initial packets have UDP payloads of at least 1200 bytes, adding PADDING frames as necessary." (8.1)
- Migration can't start before the handshake is confirmed. "An endpoint MUST NOT initiate connection migration before the handshake is confirmed" (9)
- Any change in peer address triggers path validation. "An endpoint MUST perform path validation (Section 8.2) if it detects any change to a peer's address, unless it has previously validated that address." (9)
- The idle timeout is the smaller of the two sides' values, and the connection closes silently. "the connection is silently closed and its state is discarded when it remains idle for longer than the minimum of the max_idle_timeout value advertised by both endpoints." (10.1)
- PING frames can keep a connection from idling out. "With this option, an endpoint could send a PING frame (Section 19.2) periodically, which will cause the peer to restart its idle timeout period." (10.1.2)
- Middleboxes forget UDP flows much sooner than TCP ones; about every 30 s is needed. "experience shows that sending packets every 30 seconds is necessary to prevent the majority of middleboxes from losing state for UDP flows" (10.1.2)
- Several QUIC packets can share one UDP datagram. "Using the Length field, a sender can coalesce multiple QUIC packets into one UDP datagram." (12.2)
- Three packet number spaces. "Packet numbers are divided into three spaces in QUIC:" (12.3)
- The path must carry 1200-byte datagrams. "QUIC MUST NOT be used if the network path cannot support a maximum datagram size of at least 1200 bytes." (14)
- No IP fragmentation. "UDP datagrams MUST NOT be fragmented at the IP layer." (14)
- Long headers carry the version and both connection IDs and are used until 1-RTT keys exist; then short headers. "Once 1-RTT keys are available, a sender switches to sending packets using the short header (Section 17.3)." (17.2)
- Connection IDs are at most 20 bytes in version 1. "In QUIC version 1, this value MUST NOT exceed 20 bytes." (17.2)

- The first client packet is an Initial carrying the TLS ClientHello in a CRYPTO frame. "the first packet is of type Initial, with packet number 0, and contains a CRYPTO frame carrying the ClientHello." (7.1)
- The server's first flight can already carry application data. "the server's first flight contains Initial packets, Handshake packets, and "0.5-RTT data" in 1-RTT packets." (7.1)
- New connection IDs are handed out with NEW_CONNECTION_ID frames. "These connection IDs are supplied by the endpoint using the NEW_CONNECTION_ID frame (Section 19.15)." (5.1)
- A migrating endpoint switches to a fresh connection ID so observers can't link the paths. "An endpoint MUST NOT reuse a connection ID when sending from more than one local address" (9.5)
- Path validation checks the peer really receives at its new address. "Path validation is used to ensure that packets received from a migrating peer do not carry a spoofed source address." (8.2)
- NAT rebinding after idle time can move a connection to a new path without the client choosing to. "after a period of network inactivity, NAT rebinding might cause packets to be sent on a new path when the client resumes sending." (9.5)
- Packets during the handshake are Initial and Handshake packets. "The cryptographic handshake is carried in Initial (Section 17.2.2) and Handshake (Section 17.2.4) packets." (7.1)

- The server's Handshake packet carries EncryptedExtensions, Certificate, CertificateVerify and Finished; the client's 1-RTT request follows its own Finished. (7.1, figure 5)
- Each packet number space uses different keys. "As described in [QUIC-TLS], each packet type uses different protection keys." (12.3)
- NAT rebinding can give a client a new port or address. "a change of address due to a middlebox, usually a NAT, allocating a new outgoing port or even a new outgoing IP address for a flow." (9)

- Stream IDs are 62-bit integers. "A stream ID is a 62-bit integer (0 to 2^62-1) that is unique for all streams on a connection." (2.1)
