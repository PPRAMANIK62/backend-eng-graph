## Summary

The 2010 spec that adds PATCH: a request that carries instructions for
changing a resource, instead of a whole new version of it as PUT does.

## Key claims

- PUT only replaces the whole thing. "The existing HTTP PUT method only allows a complete replacement of a document." (Abstract)
- PATCH carries a set of changes, PUT a new version. "With PATCH, however, the enclosed entity contains a set of instructions describing how a resource currently residing on the origin server should be modified to produce a new version." (2)
- PATCH is neither safe nor idempotent. "PATCH is neither safe nor idempotent as defined by [RFC2616], Section 9.1." (2)
- It can be made safe to repeat with a conditional request. "Clients using this kind of patch application SHOULD use a conditional request such that the request will fail if the resource has been updated since the client last accessed the resource." (2)

Added for `idempotency`:

- A PATCH can be sent in a way that makes it idempotent. "A PATCH request can be issued in such a way as to be idempotent, which also helps prevent bad outcomes from collisions between two PATCH requests on the same resource in a similar time frame." (2)
- Some patch formats corrupt the resource if applied to the wrong base. "some patch formats need to operate from a known base-point or else they will corrupt the resource." (2)
